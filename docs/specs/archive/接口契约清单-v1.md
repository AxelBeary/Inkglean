### 1.3 鉴权模式（从代码读出）

**会话载体：httpOnly Cookie（主路径）＋ Bearer 兜底**

- 登录成功（`POST /api/auth/verify`）后写入 `artist_token` Cookie：`path=/`、`httpOnly: true`（JS 不可读，防 XSS）、`sameSite: lax`、`secure: NODE_ENV==='production'`、`maxAge: 7 天`。
- `shared/middleware/auth.ts#extractToken`：优先读 `request.cookies.artist_token`；无则兜底 `Authorization: Bearer <token>`（注释明确为「测试 / 旧客户端兼容」）。

**requireAuth（登录校验，94 个端点）**

校验顺序（失败即 401，直接 `reply.send`，不经全局 handler）：

| 检查 | 失败 code / HTTP |
|---|---|
| 无 token | `NOT_LOGGED_IN` / 401 |
| `verifySession(token)` 无效 | `SESSION_EXPIRED` / 401 |
| 画师不存在 | `ACCOUNT_NOT_FOUND` / 401 |
| `deleted_at` 已标记 | `ACCOUNT_DISABLED` / 401 |
| `token_version` 不匹配（登出/被吊销） | `TOKEN_REVOKED` / 401 |
| 通过 | `request.artist` 挂载完整画师行 | |

**requireAdmin（管理员校验，48 个端点）**

在 requireAuth 全部检查通过后追加：`artist.qq_number === getAdminQq()`；不匹配返回 `ADMIN_REQUIRED` / 403。管理员判定 = **QQ 号等于 `platform_config` 表 `admin_qq` 键的值**（无则回退环境变量 `ADMIN_QQ`，`getAdminQq()` 实现于 `middleware/auth.ts:13`）。注意：**系统里没有独立的「管理员角色表」，管理员只是 QQ 号被配置为 admin_qq 的画师账号**。

**可选登录（tracking 专用）**

`tracking.routes.ts#getOptionalArtist`：与 requireAuth 相同提取规则（cookie 优先、Bearer 兜底），但解析失败一律静默返回 `null`（不 401）。`POST /api/events` 借此区分「登录画师」（记 artist_id）与「匿名访客」（必须带匿名凭证 anon token）。

**公开端点（无鉴权）**

23 个公开端点全部无 preHandler；依赖 IP 级内存限流（`rateLimit`，同 IP 计数，见各端点列）。`/uploads/images/*` 公开可读；`/uploads/references|deliverables|notes/*` 需 `?sig=` 签名（`file-sign.ts` 校验，15 分钟级过期语义）。

### 1.4 错误响应统一结构

全局错误处理器（`app.ts:279`）：

```json
{ "code": "ERROR_CODE", "error": "中文友好消息", "detail": { ...可选 } }
```

- JSON Schema 校验失败 → `400 { code: 'VALIDATION', error: '请求参数格式不正确（<字段>）' }`
- HTTP ≥ 500 → `500 { code: 'INTERNAL', error: '服务器内部错误' }`（不透传内部 message）
- 4xx 业务错误 → `ERROR_MESSAGES[code]` 查表，命中即中文文案；`detail` 参与 `{key}` 占位符插值（如 `STAGES_RESET_BLOCKED` 的 `{count}`）；未命中回退 `error.message`。
- 例外：中间件 401/403、若干路由手写 `reply.code(...).send({ error })`（无 code 字段，详见 §5 缺口）。

## 2. 按域端点明细

> 表格列含义：
> - **鉴权**：公开 = 无鉴权（限流另注）；登录 = `requireAuth`；管理员 = `requireAdmin`；管理员+存在性 = `[requireAdmin, requireExistingArtist]`；归属 = 挂载 `requireOwnOrder`/`requireOwnStyle`/`requireOwnTemplate` 等前置校验。
> - **body schema**：只写必填字段 + 关键类型/约束，可压缩；「无」= 该路由无 body schema（含 multipart）。
> - **响应形态**：从 handler 实际 `return` 读出的关键字段；「透传 service」= handler 直接返回 service 结果，字段以服务层为准（关键结构已抽查并注明）。
> - **可能错误码**：收录路由层显式 `throw new AppError` / `guardRateLimit` / 直接 `reply.code` 的错误；服务层 AppError 仅在有明确观测处标注，未逐 service 全量审计（见 §5.4）。

## 3. 错误码总表

### 3.1 映射机制

- **源文件**：`server/src/shared/errors.ts`（TypeScript 源；各文件以 `import { AppError, E } from '../../shared/errors.js'` 引用，编译产物为 `errors.js`——任务背景中的「errors.js」即指该文件）。
- `AppError(code, statusCode=400, detail=null)`：code 为机器可读错误码，statusCode 默认 400。
- `E`：131 个错误码常量（`as const`）。
- `ERROR_MESSAGES`：131 条 code → 中文文案映射，支持 `{key}` 占位符插值。
- 全局处理器（`app.ts:279`）：Schema 校验失败 → `400 VALIDATION`；≥500 → `500 INTERNAL`（隐藏细节）；4xx → 查 `ERROR_MESSAGES` 取文案（未命中回退 `error.message`），`detail` 用于插值，响应 `{code, error, detail?}`。
- 前端侧（`web/src/api/index.js` 拦截器）：优先 `i18n.global.t('errors.'+code, detail)`；401 且非 LOGIN_CODES 时清本地登录态并跳登录页；错误对象附加 `status/code`。

## 5. 缺口清单（只记录，不修复）

### 5.1 无 response schema 的风险点位

**全部 165 个端点 response schema = 0**。Fastify 不校验也不序列化过滤响应，任何 handler/service 改动都会静默改变前端契约。风险优先级最高的端点：

1. **enrichOrderForArtist 家族（约 17 个端点）**：GET /api/artist/orders/:id、PUT status/priority/deadline/start-date/price/focus-image/stage/track-on/stage-back、POST notes/deliver/deliver-no-file/references/extra-items/payments/promote、DELETE notes/references/extra-items。响应 = OrderDetail + 签名 URL + stageInfo + speechInfo + camelCase 增强字段，字段由多个 service 拼装，最易漂移。
2. **公开大对象（4 个）**：GET /api/public/styles/:subdomain、GET /api/public/pricing/:subdomain、POST /api/public/calculate-style-price、GET /api/public/gallery/:subdomain —— 前端三步走/画廊直接消费，结构最复杂。
3. **客户端订单查询（2 个）**：GET /api/orders/track/:orderNo（20+ 字段大对象）、GET /api/orders/delivery/:orderNo。
4. **统计聚合（6 个）**：GET /api/artist/stats、GET /api/artist/dashboard/revenue|todo|activity、GET /api/admin/stats、GET /api/admin/tracking/summary、GET /api/artist/tracking/summary。
5. **分页列表（7 个）**：GET /api/artist/orders、GET /api/artist/queue、GET /api/artist/artworks/paged、GET /api/public/artworks/:artistId、GET /api/admin/artists/:id/orders、GET /api/admin/recycle-bin、GET /api/artist/orders/:id/logs。
6. **multipart/文件（6 个）**：4 个 upload 端点（无 body schema）、GET /api/artist/tools/export.csv、GET /api/admin/health/download。

### 5.2 前端无类型约束的点位

- `web/src` **没有任何 `.ts/.d.ts` 文件**（Vue 纯 JS 项目）；`web/src/api/index.js` 所有函数返回 `any`（axios data）。
- 无 OpenAPI/Swagger、无代码生成；前后端共享 0 个类型定义。
- 字段命名双轨制是最高风险：后端大量返回 **snake_case**（orders 列表/队列行、guestbook 行、styles/art-styles、activity_logs、平台行），部分端点/服务返回 **camelCase**（enrichOrderForArtist 增强字段、tools 系列、platforms DTO、dashboard）；前端在若干组件里手工再映射（如 `currentStageId`、`startDate`、`focusImageUrl`、`paidTotalCents`），后端改一个列名即静默破契约。
- 错误码无共享类型：前端 i18n 键 `errors.<code>` 与后端 `E` 常量是两套独立字符串，新增/删除错误码无编译期联动。

### 5.4 其他如实记录

- **非标准错误响应**：约 20+ 处路由手写 `reply.code(...).send({ error })` 或 429 `{error}`（无 `code` 字段），包括：artworks 404/400、guestbook 404、transfer 400/401/404/429、upload 429/400、like/unlike 429/404、rules 400、admin status 400、totp 400 等。前端拦截器依赖 `data.code` 的 i18n 分支在这些场景失效，只能显示后端明文。
- **服务层错误码未逐端点穷举**：本清单「可能错误码」列以路由层显式抛出为主，服务层 AppError（order/pricing/style/discount/workflow 等 service 内 throw）仅在有明确观测处标注；若要全量枚举需逐行审计 30+ service 文件（约 1.1 万行），不在本任务范围。
- **限流状态不一致**：`guardRateLimit` 抛 `RATE_LIMITED(429)`（带 code），而 upload/like 等直接 `reply.code(429).send({ error })`（无 code），前端无法统一按 code 处理。
- **统计口径偏差**：`getRevenue`（orders 完成价）与 `getIncomeSummary`（order_payments 实收±退款）口径不同，前端重构时需显式区分，避免误用。
- **公开隐藏规则不完全一致**：多数公开端点对 hidden/管理员账号返回 404，但 `POST /api/orders` 只校验 `status !== 'open'`（hidden 画师若 status=open 仍可下单，随后 `ARTIST_NOT_OPEN` 语义由其它校验承接）；`GET /api/public/pricing|styles|gallery` 只校验 hidden；`validate-discount/calculate-style-price` 使用 `requireVisibleArtist`。这些规则分散在各端点，无统一层。
