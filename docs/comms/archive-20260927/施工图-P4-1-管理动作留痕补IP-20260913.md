### 1.3 ⚠ 与计划书口径的差异（以代码为准，须你确认）

计划书原文写「取 IP 考虑 TRUST_PROXY 与 `CF-Connecting-For`，**别裸取 `req.ip`**」。实地核查后此口径**与代码现状相反**，本图按代码走：

1. **真实头名是 `CF-Connecting-IP`**（计划书里的 `CF-Connecting-For` 是笔误，仓库内不存在该头）。
2. **CF 头 → 真实 IP 的换算已在反代层做完，不在后端**：
   - `Caddyfile:21-23`：`reverse_proxy web:3000 { header_up X-Forwarded-For {http.request.header.CF-Connecting-IP} }`（注释写明：用 CF 的真实用户 IP **覆盖** XFF）。
   - `docker-compose.yml:43`：`TRUST_PROXY=172.16.0.0/12,10.0.0.0/8,192.168.0.0/16`（只信 Docker 内网三段）。
   - `docs/OPS.md §12.1` 与 `docs/维护说明书.md` 同口径，并注明「后端 trustProxy 会自动采纳这个唯一值作为 request.ip」。
   - `server/tests/cf-real-ip.test.ts` 已用两个用例把这条链路锁死（TC-IP-01 单值透传取到真实 IP；TC-IP-02 伪造前缀不被采纳）。
3. **结论：`request.ip` 就是本项目的既定取 IP 口径**，v72 登录留痕（`auth.routes.ts:216/269/378`、`invite.routes.ts:94`）与全站限流用的都是它。
4. **后端自己读 `CF-Connecting-IP` 反而更危险**：那是未经 trust 判定的裸请求头，在「CF → Caddy → 容器」链路之外（本地直连、源站 IP 泄露被绕过 CF）可被任意伪造，等于给伪造留痕开后门。

→ 待你确认：**采用 `request.ip`**（与 v72 登录留痕、全项目限流同源）。计划书那句判为不实项、不采纳。

## 2. 取 IP 的落地写法

- 4 个 handler 各把 `request.ip` 传进 service，**不新建 helper、不做二次解析**。
- service 侧只做长度钳制（防超长头灌库）：存 `String(ip).slice(0, 45)`（IPv6 最长 45 字符），取不到存 `NULL`。
- **不写 `'unknown'` 之类占位串**：「没取到」与「取到了什么」在追溯时是两件事，NULL 更诚实。

## 3. 迁移 v75 草案（新建文件，**尚未落盘**）

`server/src/db/migrations/v75-admin-actions-ip.ts` —— 照 `v72-artists-last-login-ip.ts` 同范式（`PRAGMA table_info` 幂等守卫）：

```ts
import type { ColumnInfo, Migration } from './types.js'

export const migration: Migration = {
  version: 75,
  name: 'admin_actions_ip',
  up(database) {
    // 管理动作留痕补 IP（9/12 路 3 登记）：admin_actions 加 admin_ip，幂等守卫照 v72 先例
    const cols = database.prepare('PRAGMA table_info(admin_actions)').all() as ColumnInfo[]

      database.exec('ALTER TABLE admin_actions ADD COLUMN admin_ip TEXT')
    }
  }
}
```

- `noTransaction` **不需要**（纯 `ADD COLUMN`，事务内安全，同 v41/v61/v63/v68/v72 判定）。
- 列取 `TEXT`（可空、无 DEFAULT），与 v72 `last_login_ip TEXT` 同形。

**D. 读取侧与查看入口（C2 已定“要做”，以下为必做）**
