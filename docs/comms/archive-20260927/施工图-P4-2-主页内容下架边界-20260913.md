## 0. 人话摘要（给拍板用）

现在有客户举报「某画师主页内容有问题」。管理员处理时手里的工具只有两把：

- **整户封禁**（连人带号一起关，画师本人也登不进去）—— 太重；
- **什么都不做，只标记"已处理"** —— 太轻。

缺的是中间档：比如"只把这张有问题的作品图撤下来"、"只把主页隐藏一段时间，账号其他功能照用"。

要补哪一档、撤的时候客户看到什么，这是**平台规则**而不是技术活，所以列了三个粒度选项给你拍（§4），每个都写清了改动面和客户侧表现。**你拍完我再出细化的施工图纸。**

## 1. `hidden` 态现有语义核查（计划书要求的"先核清"）

**结论：`hidden` 是「画师自己关店隐身」，不是「平台下架」。拿它当下架会出三个致命问题（§1.3）。**

### 1.1 语义定位（代码 + 拍板依据）

- `v38-artists-status-check-add-hidden.ts:12` 注释：hidden 是「BUG-8 第三项（用户拍板补 admin 设 hidden 能力）」—— 即管理员**可以代设** hidden，但语义仍是"隐身"而非"处罚"。
- `artist-account.service.ts:71-76` 注释：**方案 A（2026-08-21 拍板）** —— 建号默认 `hidden`，"画师备好作品与价格后**自行**在「设置 → 主页展示」开关开业，杜绝空店对外可见"。
- `setup.service.ts:217,232-235` 管理员账号建号同样默认 `hidden`；`schema.ts:22` 对 `is_banned` 的注释才写着"主页下架+登录拒绝"。
- → **`hidden` = 营业状态四态之一（open/full/break/hidden），归属画师自己**；`is_banned` = 平台强制态。

### 1.2 读写点全表（逐个核实）

**写入点（谁能把 status 改成 hidden / 改回来）**

### 1.3 复用 `hidden` 承担"下架"的冲突（实证）

1. **画师可自助解除**（A1/A2 无任何闸门）→ 管理员刚下架，画师点一下「小店展示」开关就复活，下架形同虚设。
2. **文案与语气错位**：现行 hidden 提示页写的是"如你是店主请去设置里开启"，把处罚读成了自助歇业，客户和管理员都得不到正确信息。
3. **状态位被复用后无法区分来源**：`status` 只有一个值，无法表达"画师自己隐藏 + 平台又下架"的叠加情形（自己隐身的号被举报下架、解除下架后该回到哪个态？无解）。
4. 附带：hidden **不踢登录、不失效 token**（对照 `compliance.service.ts:110-113` 封禁才 `bumpTokenVersion`）→ 被下架者仍能进后台继续操作。

→ **本图建议：不要复用 `hidden` 承载下架**（详见 §4 选项 A 的实现口径）。

### 1.4 顺带发现：现有两条管理动作**没有留痕**

- `PUT /api/admin/artists/:id/status`（A3，含"管理员把谁设成 hidden"）→ **不写 `admin_actions`**；
- `DELETE /api/admin/artists/:id`（软删号，`admin-artist.routes.ts:84-94` → `deleteArtist()` 设 `deleted_at` + 递增 token_version，`artist-account.service.ts:280-286`）→ **同样不写留痕**。

即：留痕表目前只覆盖 4 类动作（report_resolve / content_remove / artist_ban / artist_unban）。**「谁把这家店藏起来了 / 谁把谁的号移除了」现在查不到账**。这与 P4-1 是同一件事的两面（P4-1 管字段，本条管覆盖面），须你定性（§5-Q4）。

## 2. 现有处置手段光谱（"只能整户封禁"的全貌）

| 手段 | 入口 | 力度 | 客户侧 | 画师侧 | 留痕 | 可恢复 |
|---|---|---|---|---|---|---|
| 画师自助隐身 `status=hidden` | 画师设置 | 最轻 | 提示页"暂未开放"（§1.2） | 可自助改回 | **无**（A1 自助不计） | 是 |
| 管理员设 `status=hidden` | `PUT /api/admin/artists/:id/status` | 轻 | 同上 | **可自助改回** ← 漏洞 | **无** | 是 |
| 留言下架 | `POST /api/admin/content/message/:id/remove` | 单条 | 该留言消失 | 不影响登录 | 有 | 是（`guestbook_messages.deleted_by_admin=1` 软删，`schema.ts:385`） |
| **作品下架** | `POST /api/admin/content/artwork/:id/remove` | 单条 | 该作品图消失 | 不影响登录 | 有 | **否 —— 物理 `DELETE FROM artworks`**（`artist-artwork.service.ts:105-107`；仅图片文件在 72h 后进回收站，DB 行含标题/描述/点赞数/尺寸标注**永久丢失**） |
| 整户封禁 `is_banned=1` | `POST /api/admin/artists/:id/ban` | 最重 | 404「画师不存在」全链路隐身 | **拒登录 + 旧 token 立即失效** | 有 | 是（unban） |
| 移除画师 `deleted_at` | `DELETE /api/admin/artists/:id` | 最重 | 不存在（查询全带 `deleted_at IS NULL`） | 拒登录 | **无** | 是（`restoreArtist()`，`admin-artist.routes.ts:100` 有清单口） |

**缺口定位**：中间档（比"隐身"重、比"整户封禁"轻）完全空白；且已有的"作品下架"是**不可恢复的硬删**，与"下架"这个词应有的语义（临时撤下、可复原）不符。

**举报侧现状**：`reports.target_type` 的 CHECK **已含 `artist_home`**（`schema.ts:392`），`target_id` 存的就是画师 id（`compliance.test.ts:97-107` TC-CMP-01 实证）。但 `removeContent` 的 type 枚举**只有 `artwork` / `message`**（`compliance.routes.ts:115`），管理后台 `ReportManage.vue:66-71,105-116` 对 `artist_home` 举报**只渲染"封禁"一个按钮** —— 病灶登记属实。

**好消息（降低改动面）**：`admin_actions.action` / `target_type` 无 CHECK 约束 → 新增"主页下架"类动作**不需要为留痕表加迁移**。

## 4. 下架粒度选项（🔴 核心拍板项）

### 选项 A：整户主页下架（新增「平台下架」独立态，不复用 hidden）

**做法**：`artists` 加独立列（建议 `home_takedown_at TEXT NULL` + `home_takedown_reason TEXT NULL`，或单列 `home_takedown INTEGER DEFAULT 0`），**由平台独占写入** —— 画师自助口（A1/A2）**无权清除**；新增 `POST /api/admin/artists/:id/home-takedown` / `/home-restore`，均写 `admin_actions`（action=`home_takedown`/`home_restore`，target_type=`artist`）。

- 与 `is_banned` 的分工：**只藏主页，不动账号** —— 不 bump token_version、不拒登录（画师能登录看通知、整改、申诉）；`is_banned` 仍是"连人踢出"。
- 改动面：
  - 迁移 v76（幂等 ADD COLUMN，照 v72 范式）+ `schema.ts` 同步 + `types/entities.ts` + `publicArtistDTO` 口径（参照 `last_login_ip` 的"DTO 剔除 + 后台两处显式重附"范式：`admin-artist.routes.ts:26-32`、`admin-artist-settings.routes.ts:22-28`）
  - 读取侧**逐端点补判定**：目录 / 主页 / workflow / pricing / styles / gallery / guestbook / public artworks / OG / requireVisibleArtist / isArtistVisibleById（约 **10 个判定分支**，§1.2 那张表就是清单）
  - 新增 2 个管理端路由 + service 函数；`ReportManage.vue` 对 `artist_home` 举报多给一个"下架主页"按钮（P3 领地）
  - 测试：迁移 3 例 + 各端点 404/提示页断言 +「画师自助改不回」专项 1 例（防回归的核心）
- 客户侧：选 P-404 或 P-TAKEDOWN
- 风险：**低**（独立态，不碰现有 status 语义，零历史行为变更）；工作量：**中偏大**（判定分支多、跨端协调）
- 关键：**必须加"自助口不得清除该态"的闸门 + 专项测试**，否则复现 §1.3-1 的漏洞。

### 选项 B：单作品下架（把现在的"硬删"改成"软下架"）

**做法**：`artworks` 加 `hidden_at TEXT NULL` / `hidden_reason TEXT NULL`；`removeContent('artwork')` 从 `DELETE` 改为标记，另加 restore 口；所有作品读路径（主页 `getArtworks`、`getPublicArtworksPaged`、`getPublicGallery`、`/api/public/artworks/:artistId`、点赞守卫、档位标注 `artwork_size_tags`、封面 / `image_artwork_id` 引用）过滤 `hidden_at IS NULL`。

- 改动面：迁移 v76（若 A/B 同做则 v77）+ schema.ts + `artist-artwork.service.ts`（读路径最集中的文件）+ `style.service.ts` / `style.public.service.ts` 对 `image_artwork_id` 的引用处理 + 后台作品列表加"已下架"态与恢复按钮（P3 领地）
- 客户侧：P-PARTIAL（图位显示占位）或直接不出图
- 附带收益：**顺手修掉"下架 = 永久删数据"这个真问题**（§2 表加粗那行）
- 风险：**中** —— `artwork_size_tags`、`style_sizes.image_artwork_id`、订单快照都引用作品行，改软下架后这些关联的显示口径要逐个定（"已下架作品能不能当档位示例图"）；工作量：**中**
- 注意：改成软下架**不删除既有数据**，对存量零影响，属行为变更而非结构破坏。

### 选项 C：主页板块级下架（只撤某个板块）

**做法**：`artists` 加 JSON 列（如 `admin_hidden_sections TEXT`，存 `["gallery","guestbook","rules"]`）；主页各数据接口按该列表裁剪。

- 现状可借的范式：画师自控板块开关只有 `guestbook_enabled`（820-L v68，`schema.ts:29`）一个先例；**没有现成的"平台强制板块隐藏"机制**，等于从零建。
- 改动面：迁移 + schema.ts + 板块白名单常量 + **每个板块各自的读路径与前端渲染分支**（客户主页板块：作品画廊 / 价格画风 / 约稿须知 / 工作流 / 留言板 / 公告 / 外链 / CTA 浮窗，共 8 块）+ 后台板块勾选 UI（P3 领地）
- 客户侧：P-PARTIAL
- 风险：**高** —— 粒度最细、组合最多（哪几块能撤？撤了 CTA 还能下单吗？下架原因与板块如何对应？`artist_home` 举报现在**只有整户粒度**，没有板块级 target_type，要扩 `reports` CHECK → **重建表级迁移**，属高风险搬动）；工作量：**大**
- 本图判断：在举报链没有板块级目标类型之前，C 缺输入侧支撑，**不建议先做**。

### 选项 D：只做「举报 → 下架」的链路衔接，不新增粒度

`resolveReport` 处理 `artist_home` 举报时允许同时指定"封禁 / 隐身"（复用现有 A3 / 封禁口）并补留痕。改动最小，但**没解决粒度缺失**，只是把现有两把锤子接上举报线。

| §二 决策 1 | 先发后审 + **举报/抽查驱动下架** | 举报有；**抽查驱动的下架只能靠封禁** ❌ |
| §三 B | **违规阶梯：警告 → 内容下架 → 封禁** | 三级里**中间那格缺失** ❌ |
| §三 C「内容级下架」 | 管理员对具体内容下架（**作品/留言/主页**），客户端立即不展示 | 只做了作品 + 留言，**主页那一格没做** ❌ |
| §三 C「封禁独立态」 | 封禁 = 主页强制下架 + **登录拒绝** + 后台标记 | ✅ 已做（正因如此，主页只剩“连人踢出”一档可用） |
| §七 验收 2/3 | 下架/封禁客户端立即生效 | 作品那格生效方式是**删数据** ⚠ |

→ **重新定位**：本项不是“选一个产品边界”，而是**把 REQ-042 已拍的中间格补齐 + 把已做的作品下架做对**。性质从“产品决策”降为“需求回归”，不需要你重新拍边界，只需要你确认按原需求落实。

## 8.2 推荐方案：A + B 同批（一次迁移 v76），不做 C

**一句话**：新增一个**平台独占、不碰账号**的「主页下架」态（补 REQ 中间格），同时把现有的「作品下架」从物理删除改成可恢复软下架（把已做的那格做对）。

| 项 | 做法 | 为何这样而不是那样 |
|---|---|---|
| 主页下架 | `artists` +`home_takedown_at TEXT` +`home_takedown_reason TEXT`（v76） | 不用 `status='hidden'`（§1.3 四条冲突），也不用 `is_banned`（那是“连人踢出”，REQ §三 C 已定口径）；**独立列天然免疫画师自助口**，无需额外闸门也能成立，但仍要加断言防回归 |
| 不踢登录 | 置列时**不** bump token_version | 画师必须能登进来“看到自己被下架了”并整改；这是与封禁的唯一分工线 |
| 作品下架 | `artworks` +`takedown_at TEXT` +`takedown_reason TEXT`（同一个 v76）；`removeContent('artwork')` 从 `DELETE` 改为置列 + 新增恢复口 | 止住“下架就在删数据”（§2 加粗行）；对存量零影响 |
| 不做 C | 板块级 | REQ 原文无此要求，举报侧也无板块级 target_type，要改 `reports` CHECK 得重建表（高风险）；**将来真需要再单独立项** |

**三个必做工程护栏（计划书未提，但它们是本项目真正会翻车的地方）**

1. **可见性判定必须先收口成 2 个 helper，再加列。** §1.2 实测：hidden/banned 的判定**散落 10+ 处**，且已经不一致（主页 200 vs 其他 404 vs 日历订阅完全漏判）。直接加列就得再改 10+ 处 → 必漏。先封 `isArtistHomeVisible(artist)` / `isArtworkVisible(artwork)` 两个函数收拢现有判定（**行为零变更**），再把新态接进去。
2. **区分“删除”与“下架”两个动作。** `deleteArtwork()` 现有 **3 个调用者**：画师自删（`artist.routes.ts:380`）、管理端删作品（`admin-artist-settings.routes.ts:102`，**且不留痕**）、合规下架（`compliance.service.ts:88`）。只改第三个——**画师自删继续物理删**（他的意图就是删），否则语义错乱。
3. **作品软下架的引用连带（最易漏网）**：`style_sizes.image_artwork_id` 是**实时引用**（`style.public.service.ts:326-329`）、`artwork_size_tags` 是画廊档位筛选数据源 → 两处必须过滤已下架作品，否则“被下架的图仍然在价格表示例图上挂着”。

## 8.3 客户侧表现（代替 Q2）：建议「中性无法访问」，既非 404 也非公开宣判

- **不推荐 P-404**：客户以为店倒了，画师申诉时平台无从开口。
- **不推荐原样 P-TAKEDOWN**（“因违规已被平台下架”）：小圈子里这是**公开挂牌示众**，会被截图挂社交平台，把平台拖进不必要的冲突。
- **推荐（新选项 P-NEUTRAL）**：客户侧只说「该主页暂时无法访问」（不提原因、不提“违规”），**具体原因只给画师本人在后台看**。既满足 REQ “客户端立即不展示”，又不公开宣判。可复用现有 UI-8 提示页机制（§1.2），改动量最小。
- ⚠ 文案与提示页在 `web/**` = **P3 领地**，须另批或派 P3。

## 8.4 不给自动到期（代替 Q3）

建议**不带期限、靠管理员手动恢复**：① **通知通道实测未接通**（`preferences.notifyDesc` 实文含“开发中”“不会真的”，9/12 已立诚实测试 `honestyCopy.p1-0912.test.ts` 锁死）——到期静默恢复 = 画师和客户都不知道发生了什么；② 到期判定又得插进那 10+ 处读路径，漏判风险变大；③ 平台是单人运营，本就走人工处置。
→ 补偿措施：**画师后台加一条下架横幅**（“主页已被平台暂时下架 + 原因 + 如何处理”）——这是通知通道未接通下**唯一能送达画师**的手段，也间接实现了 REQ §三 B 阶梯里“警告”那格的可感知性（属 P3 领地）。
