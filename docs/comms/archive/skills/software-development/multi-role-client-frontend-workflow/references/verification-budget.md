# 验证预算纪律 — 别把自动化门禁拖到最后

## 事故记录（2026-08-04，v0.36 波1）

作为二号执行"时间条四档缩放+撤销toast+L0/L1/L3/L5小修"：侦察→编码全部顺利（6 项改动全部落盘），但会话的**工具调用迭代额度在 `npm install` 刚成功时耗尽**——vitest/eslint/build 一个都没跑，浏览器自测没做，git commit 没提交。结果：代码完成但**零验证证据、不可交付**，只能留一份"待验证清单"给下一轮。这是本角色系统里最贵的失败模式：一号收到的是半成品，三号/五号的配套工作被阻塞。

## 规则

1. **门禁不是收尾仪式，是贯穿步骤**。vitest + eslint + build 必须拆散到过程中跑：
   - 侦察结束、动手改第一行代码前：跑一次基线（vitest 基线数 + eslint 干净 + build 通过），同时完成 `npm install`（worktree 的 node_modules 不共享，见 windows-agent-environment）。
   - 每完成一个独立条目（如 TL-1 完成、TL-2 完成）后：至少 `npx vitest run` 快速回归（~10s 级），别攒着。
   - 全部编码完成后：完整三件套 + 浏览器自测。
2. **预算启发式**：侦察+编码通常消耗会话调用量的 ~60%。当你估计已用一半额度而编码还没完时，立即评估砍掉可选项（浏览器自测可降级为"交付报告中标注未实测"），**保住三件套门禁 + commit + 交付报告**这条最小交付线。
3. **额度将尽时的优先级**（从高到低）：① 已改动文件的 git add + commit（哪怕验证不全，commit 消息注明"门禁未跑完"比不 commit 强——但本角色系统要求门禁绿才交付，所以更优先的是 ②）② 跑完三件套门禁 ③ 交付报告写清"已完成/已验证/未验证"三分清单。**绝不允许**的结局：改动躺在工作区、无 commit、无验证、无报告。
4. **诚实上报**：真撞了额度墙，交付报告/摘要必须逐条列明哪些验证没跑（本次总结格式可复用：已完成清单 + 遗留步骤 + 下一轮起手命令）。

## 下一轮起手模板（接力未完成验证时）

```powershell
cd "<worktree>/web"
# install 若已跑过可跳过；三件套一次跑完再谈其他

```
