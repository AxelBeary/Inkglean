# Multi-Role Client-Frontend Workflow (二号/客户页面前端)

> **支持文件**（接派工先读）：references/ 下 delivery-handoff-patterns.md、client-ui-implementation-patterns.md、browser-selftest-patterns.md、i18n-locale-audit.md、verification-budget.md、visual-reskin-token-scoping.md、totp-api-integration.md、template-health-check.md

<user> runs a five-role collaboration system (一号主理人 / 二号客户前端 / 三号后端画师 / 四号需求 / 五号Bug修复). He is the relay hub: he hands you tasks as 一号 and you produce output he can copy-paste to the next role. This skill is for when you are dispatched as **二号 (client-page frontend engineer)** — feature branches in the client worktree, pre-submission verification, and structured review materials.

## Trigger

- User says "二号，开工" or addresses you as 二号
- Task involves `web/src/views/client/**`, client-facing components, or a `feat/client-frontend-*` branch
- User asks to submit a local commit for review ("提交审核")
- User says "等迁移 vN 后" + a SPEC doc to read for upcoming frontend work
- 一号 sends a multi-batch dispatch where every batch has a 前置 on 三号's backend ("等三号接口合入后开工") — run the 开工准备 workflow below; do NOT write code yet
- 一号's dispatch says "先出方案" / "交互方案（不写代码）" / "方案确认后再动手" — proposal phase before implementation (see "Produce an interaction proposal" workflow below)
- 一号 dispatches Playwright E2E infrastructure ("搭建 Playwright 框架 + N 条核心路径 E2E 测试") — see "Playwright E2E test infrastructure" workflow below

## Hard rules

1. **Authorization boundary**: only modify `web/src/` files listed in the task book (typically `views/client/**`, `components/templates/**`, client composables, `styles/templates.css`, `styles/palettes.css`, `embed/**`). **Never touch `docs/`, `server/`, `.env`, `package.json`** — even if you find errors there. Report in submission notes instead. **Exception**: `package.json` CAN be explicitly authorized for specific tasks (e.g. test-infra: adding devDependencies + scripts) — check the dispatch's 授权文件 list. When unsure whether a file is authorized, treat it as NOT authorized and ask 一号. **Implicit authorization** (v0.16 precedent): `web/src/locales/zh-CN.js` and `web/src/locales/en.js` are in the "需要一号协调" list, but **pure-additive** i18n key changes (appending new keys, not modifying existing ones) are implicitly authorized for any frontend task that needs them — note it in the submission's "是否修改非客户前端文件" field, no separate coordination round needed. Similarly, `styles/theme.css` is implicitly authorized for CSS-only additions (new variables, new global rules, media queries) when the dispatch explicitly includes CSS quality work. Modifying existing keys/values, restructuring locale files, or changing existing theme.css rules still requires coordination.
2. **i18n**: every user-visible string goes through `$t()`/`$tm()`. New keys MUST be added to BOTH `zh-CN.js` and `en.js` in the same commit. Zero hardcoded Chinese/English in templates.
3. **XSS**: any `v-html` must pass through `sanitizeHtml()` (`web/src/utils/sanitize.ts`). No exceptions.
4. **ESLint**: `npx eslint .` in `web/` — zero errors, zero warnings. No new `eslint-disable` without 一号's approval.
5. **No residue**: zero `console.log`, zero commented-out code blocks, zero untracked TODO/FIXME in changed files.
6. **禁止 `git add -A` / `git add .`** — stage only specific authorized files. Worktrees accumulate stale docs/lock changes from other roles; sweeping them in gets the whole branch rejected.
7. **Comms protocol**: 开工前读 `docs/comms/STATUS.md`. Written deliverables go to `docs/comms/02-to-01-{主题}-{日期}.md`. 写下来才算交付 — verbal answers without a file = not delivered. (Note: writing comms files requires 一号's authorization since docs/ is normally out of scope — the STATUS.md read is always allowed; confirm before writing comms files if the task book doesn't explicitly authorize them.)
8. **🔴 主 worktree 是共享的——一律在自己的专属 worktree 里干活。** The main worktree (`workspace/artist-commission`) is used by multiple roles concurrently. While you edit files there, another role can `git checkout` a different branch — then your `git add` + `git commit` lands on **their** branch and sweeps in **their** staged files. (2026-07-30 incident: 二号's R39 commit landed on 三号's `feat/backend-artist-v014` as an 11-file commit — his 7 staged docs + her 4 frontend files. His branch was unpushed, so recovery was clean; a pushed branch would have been a real mess.) Rules:
   - Session start: `git worktree list`. If your dedicated worktree doesn't exist, create it: `git worktree add ../artist-commission-client-<batch> feat/client-frontend-<batch>` (branch per dispatch instructions). ALL edits and commits happen there.
   - **Before EVERY commit**: `git branch --show-current` + `git diff --stat --cached` — confirm the branch is yours and ONLY your files are staged. If the branch is not yours, STOP. Do not commit, do not `git checkout` (that would move someone else's state) — assess first.
   - **Recovery if your commit landed on someone else's branch** (safe only while their branch is unpushed — check `git branch -r` / origin state first): `git reset --soft <their-previous-HEAD>` → `git restore --staged .` (their staged changes return to their working tree intact) → copy YOUR files into your dedicated worktree and commit there → in the main worktree `git restore` your modified files and delete your new untracked files (return it to exactly their state). Then write an incident comms file (经过 → 修复步骤 → 根因 → 预防) — 一号 needs to know, and the report documents that nothing was lost.
9. **🔴 按受众分工（用户拍板 2026-08-01）。** 二号只负责客户端全部前端（4 模板 + OrderForm + TrackOrder + 共享 Tpl* 组件）。画师后台页面（Dashboard、Settings、QueueBoard 等）和管理后台页面（AdminDashboard、HealthCheck 等）归三号——三号写完 API 直接写对应 Vue 页面。二号不接画师/管理后台前端任务，即使派工误派了也要向一号确认。共享组件（Tpl*.vue）归二号所有，三号只消费不修改。
10. **🔴 共享逻辑，不共享皮肤（用户拍板 2026-08-01）。** 共享组件（Tpl*.vue、ArtworkLikeButton.vue 等）**只输出内容和状态，不写任何布局/装饰样式**——无默认 margin/padding/background/border-radius/font-size。颜色继承 `currentColor`，大小跟随 `1em`（模板通过 class 控制）。视觉完全由各模板的 class 决定，4 模板适配时每个模板必须有自己的视觉处理，不允许 4 个模板用同一套 class。这是防同质化的底线，不是建议。一号审核时会检查组件内是否有装饰性 CSS，有则打回。
11. **🔴 切了分支就必须当轮写完代码 + commit，不留半成品。** Once you `git checkout -b`, you MUST write the code AND commit it in the SAME turn. Never end a turn with a freshly-cut branch that has zero commits and only "I read the file / located the i18n keys" as progress. Never end a turn with a freshly-cut branch that has zero commits and only "I read the file / located the i18n keys" as progress. (UI-8 incident: branch `feat/client-frontend-ui8-hidden` was cut, ArtistHome.vue was read, then the turn ended with no code and no commit — 一号 flagged it as a 5-minute job left hanging and had to finish it himself; user said 「下次别漏」.) A half-started branch is worse than not starting: it looks like work-in-progress to the next person but contains nothing. If you genuinely cannot finish in the turn, do NOT cut the branch yet — read/plan first, cut + implement + commit as one atomic block.

## Workflow: Submit a local commit for review

When 一号 says a commit is sitting in the worktree and asks you to submit it for review:

1. **Read `docs/comms/STATUS.md`** — confirm master HEAD, your branch state, and what 一号 expects.
2. **Inspect the worktree**:
   ```powershell
   git worktree list
   cd <worktree-path>
   git log --oneline -5
   git diff --stat master...HEAD   # what the branch actually changes
   git status --short              # uncommitted stragglers
   ```
3. **Handle unauthorized uncommitted changes.** Other roles' work often leaves modified `docs/*.md` or lock files in your worktree. Do NOT commit them, do NOT discard them — **stash with a descriptive message** so nothing is lost:
   ```powershell
   git stash push -m "docs-soul-uncommitted" -- docs/soul/
   ```
   Report the stash in your submission notes so 一号 knows it exists and can route it to the right role.
4. **Rebase onto latest master.** Master moves constantly (other roles commit docs directly to master). Never submit a stale-based branch:
   ```powershell
   git fetch origin
   git rebase master        # after stashing, working tree is clean
   git log --oneline -3     # confirm your commit sits on top of master HEAD
   ```
   If rebase conflicts, resolve conservatively (your feature code wins for your files; master wins for everything else) and re-verify.
5. **Run the verification chain** (all must pass before submission):
   - `npx eslint .` in `web/` → zero errors/warnings
   - Production build (see pitfall: use `node node_modules/vite/bin/vite.js build`, NOT `npx vite build`)
   - Grep changed files for residue: `console\.(log|warn|error|debug)`, `TODO|FIXME|HACK`, `v-html` (each must return 0, or v-html must be paired with sanitizeHtml)
   - i18n key parity: every new key in `web/src/locales/zh-CN.ts` exists in `web/src/locales/en.ts` and vice versa
   - **API method existence**: grep every `artistApi.XXX(` / `orderApi.XXX(` / `uploadApi.XXX(` call in changed files, then confirm each method name exists in `web/src/api/index.ts`. ESLint and Vite build do NOT catch missing API methods (it's a runtime TypeError, not a syntax error). This caught a P0 in R39: `artistApi.trackOn()` was called but never defined — the "启用跟踪" button would crash on click. One-liner check:
     ```powershell
     # Extract all api method calls from changed files, then verify each exists in web/src/api/index.ts
     git diff master...HEAD -- '*.vue' '*.js' | Select-String 'artistApi\.(\w+)' | ForEach-Object { $_.Matches[0].Groups[1].Value } | Sort-Object -Unique | ForEach-Object { $m=$_; $found = Select-String -Path web/src/api/index.ts -Pattern "${m}:" -Quiet; if (-not $found) { "MISSING: $m" } }
     ```
   - `git diff --stat master...HEAD` → every path inside the authorized list
6. **Review your own diff** before asking 一号 to. Read the full diff of each changed file. Catch obvious problems yourself — a self-reviewed submission that comes back clean builds trust.
7. **Produce 审核提交材料** (see format below). Copy-paste ready for 一号. Include honest "需人工验证项" — you cannot click through a browser; list exactly which UI behaviors need human eyes.

### 审核提交材料 format

**Use the 12-field format** (角色/工作分支/任务编号/修改模块/修改内容/涉及文件/是否修改非客户前端文件/接口依赖/自测情况/可能影响/待确认问题/申请) — the shape is documented inline below. The template file `docs/templates/submit-client-frontend.md` was ARCHIVED in the 2026-08-01 docs cleanup (8390b2e) — do NOT go looking for it, this section is now the source of truth. R21 was flagged by 一号 for free-form submissions that skipped the template — the 12 fields are a compliance item, not a style preference. For quick single-fix submissions (review 必修项), a shortened version is acceptable but must still end with 「申请一号审核合并」. Typical content shape:

```markdown
## R<N> 审核提交（请转交一号）

**分支**：`feat/client-frontend-<id>`（worktree: `<path>`）
**Commit**：`<hash>`（已 rebase 到 master `<master-hash>`）

### 改动说明
**任务 ID**：R<N>（需求来源）
**影响范围**：<files + one-line scope>
1. <numbered change list, each item = one user-visible behavior>
2. ...
**i18n**：新增 N 个键 × 2 语言（列出键名）

### 自测情况
| 检查项 | 结果 |
|--------|------|
| ESLint | ✅ 零错误零警告 |
| Vite build | ✅ 通过 |
| Rebase master | ✅ 无冲突 |
| console.log / TODO / v-html | ✅ 无残留 |

**需人工验证项**（无浏览器环境）：
- <specific UI behavior 1>

<stashed files, open questions, things 一号 should know>
```

## Workflow: Produce an interaction proposal (方案阶段 — no code yet)

When 一号's dispatch says "先出 2~3 个方案（文字描述 + 布局示意即可），写入 comms 交一号转用户拍板。方案确认后再动手写代码":

1. **Do NOT cut a branch.** A docs-only deliverable goes straight to `docs/comms/02-to-01-<topic>-proposal-<date>.md` and is committed **directly on master** (comms files follow the project convention of committing to master; only CODE goes on feature branches). `git add` only that one file, commit as `docs(client): <主题> 交互方案（待用户拍板）`.
2. **Read the requirement doc section + the CURRENT implementation fully** before proposing. The proposal must be grounded in what the code actually does today, not in the requirement's paraphrase of it.
3. **🔴 Verify backend behavior before designing interactions — this is where proposals earn their keep.** For every button/action the proposal includes, read the actual `server/src/features/**` service + route code and confirm:
   - Does the endpoint exist at all? (A proposed "启用流程跟踪" button had NO backend endpoint — existing `advanceStage` on an untracked order would reset status to `pending`, i.e. a state regression. Surfacing this in the proposal turned it into an explicit 后端协调项 for 三号 instead of a mid-implementation blocker.)
   - Does the endpoint silently reject the call in some states? (e.g. `updateStatus` throws `INVALID_TRANSITION` for orders with `currentStageId` — meaning the existing fixed-status buttons are already dead code on workflow orders; that fact reshapes the whole proposal.)
   - Does the action auto-cascade? (stage advance auto-maps to `status` via `mapStageToStatus` — the proposal must not offer redundant manual status buttons.)
   - Is the data field already returned? (e.g. `updated_at` for "最后活动时间" — already in the GET response, so no backend ask needed.)
   List these as a "已核实的后端规则" section at the top of the proposal — shared fact base for all options — and any gap as a "后端协调项（请一号安排三号）" section at the bottom with the exact endpoint + behavior spec.
4. **Structure the proposal for a non-programmer decision-maker** (the user, relayed via 一号):
   - 现状问题 in one plain sentence (use the user's own complaint wording)
   - 公共部分 (already-decided C-items, not up for debate — list them so the user sees what's locked)
   - 2~3 options, each with an **ASCII layout sketch** (boxes, buttons in `[方括号]`, current state marked) + 优点/缺点 — ASCII, not screenshots; 一号 relays text
   - One explicit recommendation with numbered reasoning
   - End with a single crisp question: "选 A、B 还是 C？（推荐 B）" — no other open items unless unavoidable
5. **Flag dispatch-file path shorthand.** 一号's authorization list may use shorthand paths (e.g. `artist/src/views/OrderDetail.vue` when the real path is `web/src/views/artist/OrderDetail.vue`). Verify real paths with a file search before touching anything; note the mapping in your comms if it differs. Intent is clear — don't block on it, but never edit a guessed path.
6. **Then stop.** Do not implement. The proposal commit + a short reply summarizing options/recommendation/blocker is the deliverable. Implementation starts only after the user picks.

## Workflow: Implement a dispatched feature batch (R-series)

When 一号 sends `01-to-02-*.md` with "前端可开工" + a task list + branch instructions:

1. **Read the dispatch + any referenced review replies** (e.g. `01-to-02-r21-review-0730.md` may contain icon-scheme decisions and answers to your earlier questions). Batch the reads.
   **Design-decision confirmations (T-items):** dispatches may include "前置：确认 T3/T5" — design questions 一号 wants YOUR professional judgment on before implementation (e.g. "公告在 4 模板的具体位置" / "0 赞是否显示数字"). These are NOT optional: answer them in the delivery comms with a per-item conclusion + one-line reasoning, then implement accordingly. If you agree with 一号's pre-judgment, say so explicitly ("同意一号预判") — silence is not confirmation. The T-item answers go at the TOP of the delivery comms so 一号 sees them before the implementation details. **🔴 Before composing a fresh answer, grep the target files for the T-number or '拍板' — the decision may already be made and documented in code comments by a prior session** (v0.22: ArtworkLikeButton.vue:8 read 'T5（用户拍板）：0 赞不显示数字' and the templates carried 'F3: announcement at ...' position comments answering T3 — the dispatch re-asked questions that were settled in v0.19). If found, the answer is 「已拍板已实现（依据：file:line）」, not a new proposal.
2. **Cut the branch exactly as instructed** (usually `git checkout -b feat/client-frontend-<id> origin/master` in the existing worktree).
3. **Read the backend contract before writing any frontend.** For every endpoint you'll call, read the actual route file in `server/src/features/**` to confirm field names, response shapes, `additionalProperties: false` constraints, and new endpoints (e.g. `POST /api/upload/note-image`). Batch these reads. The dispatch's 接口速查 table is a summary — the route files are truth.

   **Contract-first parallel work (when backend isn't merged yet):** if 一号's dispatch fixes the contract (endpoint names, request/response field names) in a SPEC doc + instruction file but 三号's backend branch hasn't merged to master, you can still implement in parallel — PROVIDED every frontend change is **optional-field + backward-compatible** (e.g. `v-if="order.currentStageId != null"` so missing fields fall back to old behavior; `stageProgress || <frontend-computed fallback>`). This is low-risk because a contract mismatch degrades gracefully, not into a crash. Before doing this: (a) confirm the contract is genuinely frozen (SPEC + 一号 instruction both state field names), (b) verify the backend branch's actual state — `git worktree list` shows 三号's worktree/branch; then `git log --oneline master..<branch>` — NON-empty output = commits ahead of master = still unmerged/in progress (the correct signal); empty output = merged or nothing. Also check `git branch -r` — 三号 often works on a LOCAL branch that was never pushed, so `origin/<branch>` may not exist at all (v0.15: `feat/v015-backend` was local-only). If the branch isn't on the remote, that itself means unmerged., (c) flag in your comms that you implemented against the contract and list any endpoint you INVENTED that the SPEC didn't define (e.g. R30d's `PUT /stage-off` — SPEC-002 never specified it; I chose `PUT` no-body and asked 三号 to confirm). Never invent contract terms silently.
4. **Read every file you'll modify fully** before editing (batch reads in one turn). Match existing structure and style.
5. **Implement in dependency order**: composables → components → views → api layer → i18n keys. Requirements that touch the same file (e.g. R18+R19 both edit OrderDetail.vue) get one pass per file, with logical commits kept separable.
6. **Verify**: ESLint zero/zero + production build (use `npm run build` — see the `npx vite build` false-positive pitfall) + a FRESH ad-hoc `.mjs` script under `C:\Users\<user>\AppData\Local\Temp\hermes-verify-<name>.mjs` (run it, show PASS/FAIL, `Remove-Item` it). The Hermes UI checker requires the `hermes-verify-` artifact; separate terminal calls don't satisfy it. **If the task's code is covered by the frontend test suite** (vitest, `npm run test:web` — exists since v0.18), run it and report "suite green" for those paths; for UI behaviors with no test coverage, still summarize as "ad-hoc verification, not suite green".
7. **Commit** per logical unit: `type(client): 简述` (feat/fix/style/refactor/perf/docs).
8. **Write the submission** to `docs/comms/02-to-01-<topic>-<date>.md` **using the 12-field format** (角色/工作分支/任务编号/修改模块/修改内容/涉及文件/是否修改非客户前端文件/接口依赖/自测情况/可能影响/待确认问题/申请 — full shape in the 审核提交材料 format section; the docs/templates file no longer exists). **R21 was flagged for skipping the 12 fields — always follow them.** End with 「申请一号审核合并」.

## Workflow: 联调 after the backend merges (parallel-period follow-through)

Contract-first parallel work (above) builds the frontend against an inferred/frozen contract. When 一号 notifies "三号接口已合入 master，可以联调", the deliverable is a **field-alignment pass**, not new features:

1. **Rebase onto master** (`git rebase master` in your worktree) so 三号's service/route files are present. Confirm with `git log --oneline -3`.
2. **Read the ACTUAL backend service file line-by-line** (`server/src/features/**/<name>.service.ts` + its `.routes.ts`) — not the dispatch's 接口速查, not your inference. For each endpoint your module calls, write down the EXACT return shape: top-level keys, nested object keys, and the type/language of each value.
3. **Diff every field your `normalize()` touches against the real return.** The mismatches that survive a lenient normalize are three specific kinds — check all three:
   - **A different WORD you didn't guess**: you fallback-chained `orderCount`/`changePct`, backend ships `summary.completedCount`/`summary.changePercent`. A chain can only include names you thought of.
   - **A different LANGUAGE**: backend returns display TEXT in the source language (`tag: '逾期'`) not an English key. `$t('dashboard.tag_' + tag)` then renders the nonexistent key `tag_逾期`. Fix: a `TAG_KEY_MAP = { '逾期': 'overdue', ... }` mapping source-language text → i18n key suffix, applied in normalize so BOTH the i18n lookup AND the CSS class (`todo-item--${tag}`) get the English key. (Inverse cousin of the "variable tokens stay in source language" pitfall: there the frontend keeps Chinese for the backend to match; here the backend sends Chinese and the frontend maps to a key.)
   - **A field you omitted entirely**: backend's activity item uses `content`, your chain had `description ?? text ?? event` — add `content` first.
   Also handle fields the backend does NOT return but the UI shows (e.g. 环比 `prevLabel` "vs X") — compute them frontend-side from available data (period → previous-period name).
4. **Re-verify** (ESLint + build + a fresh `.mjs` ad-hoc script that feeds a MOCK of the backend's real return shape through each normalize() and asserts the mapped output — see the ad-hoc section). Commit as `fix(client): 联调对齐三号XX API实际字段`.
5. **Update the submission comms in place** (append a 联调 table: 组件 × 后端实际字段 × 修复), don't write a new file — 一号 expects one submission doc per batch.

Rule of thumb: the normalize() written during the parallel period is a BEST-EFFORT guess; the 联调 pass is where it becomes correct. Never report "已联调" having only rebased — you must have read the service file and diffed fields.

## Workflow: Frontend test infrastructure (技术债 P1)

The frontend NOW HAS a test suite (established v0.18: vitest + happy-dom, `npm run test:web` in `web/`). When dispatched to set it up or extend it:

1. **Fresh worktree + `npm install`** (new worktrees have no node_modules). Install test deps as devDependencies: `npm install -D vitest @vue/test-utils happy-dom`.
2. **`web/vitest.config.ts`** — MUST be fully isolated from the backend's `server/vitest.config.ts` (different directory, different env: backend uses `node` + `:memory:` DB + UPLOAD_DIR isolation; frontend uses `happy-dom`, no env vars needed). Minimal known-good config:
   ```js
   import { defineConfig } from 'vitest/config'
   import vue from '@vitejs/plugin-vue'
   export default defineConfig({
     plugins: [vue()],
     test: {
       globals: true,
       environment: 'happy-dom',
       include: ['src/**/__tests__/**/*.test.ts'],
       setupFiles: ['src/test-setup.ts']
     }
   })
   ```
3. **`package.json`**: add `"test:web": "vitest run"` to scripts (do NOT touch the backend's `test` script or anything in `server/`).
4. **🔴 Pure logic trapped inside `<script setup>` CANNOT be imported by tests.** The dispatch will say "test the normalize functions" — but functions defined in an SFC's `<script setup>` are module-private. The correct move is a **testability refactor**: extract the pure functions (normalize/tagKey/guessTag/relativeTime/prevPeriodLabel — anything with no Vue reactivity or component refs) into `web/src/utils/<domain>-normalize.ts` with named exports, then change the SFCs to `import` them. This touches files beyond the strict authorization list (the utility file + the SFCs) — it is a NECESSARY prerequisite for the stated deliverable; list every such file in comms' 授权外文件说明 with one line of reasoning. Keep the refactor behavior-identical (no logic changes in the same commit that introduces tests, so a failure is unambiguous).

6. **Test-writing pitfalls hit live**:
   - **Import depth**: a test at `src/components/artist/dashboard/__tests__/x.test.ts` needs FOUR `../` to reach `src/utils/` — `../../../` (three) resolves to `src/components/` and fails with "Failed to resolve import". Count the levels.
   - **UTC vs local date in deadline tests**: `new Date().toISOString().slice(0,10)` gives the UTC date; on a UTC+8 host before 08:00 local it's YESTERDAY — a "today's deadline" fixture then asserts overdue. Build dates with local components (`getFullYear/getMonth/getDate`) when the function under test compares local dates.
   - **i18n `t` mocks must be lazy**: a mock like `{'key': `${params.n} 分钟前`}` evaluates `params.n` at object-construction time — a key called WITHOUT params (`timeJustNow`) crashes the whole mock with "Cannot read properties of undefined". Store thunks: `{'key': () => `${params.n} ...`}` and invoke.
   - **Fake timers**: `vi.useFakeTimers()` + `vi.setSystemTime(new Date(...))` for date-dependent logic; ALWAYS `vi.useRealTimers()` in `afterEach` or later tests in the file inherit frozen time.
   - **DOMPurify + happy-dom is incompatible — mock it, don't test it.** Running the REAL `sanitizeHtml` under happy-dom produces garbage: whitelisted tags (`<p>`, `<h1>`, `<table>`) get DELETED while `<script>`/`<form>`/`<svg onload>` SURVIVE, and the `afterSanitizeAttributes` link-hardening hook never fires. This is a happy-dom DOMParser limitation, NOT a production bug (real browsers sanitize correctly). For the sanitize test file, `vi.mock('dompurify')` and test the INTEGRATION CONTRACT instead: empty-input short-circuit (DOMPurify not called), the ALLOWED_TAGS/ALLOWED_ATTR/ALLOW_DATA_ATTR:false config passed through (assert dangerous tags/`on*` attrs are EXCLUDED), and the link-hardening hook behavior (capture the hook fn registered at module load via `vi.hoisted`, invoke it with a fake `{tagName:'A', setAttribute}` node, assert `target=_blank`+`rel=noopener noreferrer`). DOMPurify's own tag/attr filtering is guaranteed by its test suite in real browsers.
   - **`vi.mock` factory overrides win over pre-set mocks — order your setup.** A `createForm()` helper that calls `setupMocks()` (setting `mockResolvedValue` on every api method) will SILENTLY OVERWRITE a rejection you set in the test body BEFORE calling it. Symptom: a "calculatePrice 失败 → pricePreview 回退 null" test gets the default resolved value and fails. Fix: call `createForm()` FIRST, then override the specific mock (`artistPublicApi.calculatePrice.mockRejectedValue(...)`) AFTER. Same for any helper that bulk-configures mocks.
   - **Pre-seeding `sessionStorage` before mount triggers the draft-restore dialog.** `useOrderForm`'s `onMounted` reads `sessionStorage` and pops `ElMessageBox.confirm` if a draft exists. A test that pre-seeds a draft to check "empty form clears it" instead gets the restore flow (confirm resolves → draft restored, not cleared). To test draft CLEARING, mount with an empty form, fill it (writes a draft via the debounced watcher), then empty it and assert the key is gone. To test restore, seed the draft + let the default `confirm.mockResolvedValue('confirm')` run.
   - **happy-dom `ClipboardEvent` carries no `clipboardData` — attach it to a plain `Event`.** `usePasteUpload` reads `event.clipboardData.items`. `new ClipboardEvent('paste')` under happy-dom has no usable `clipboardData`, so the handler no-ops. Fix: `const e = new Event('paste', { bubbles: true, cancelable: true }); e.clipboardData = { items }; document.dispatchEvent(e)` — then assert `e.defaultPrevented`, the `onFiles` call args, and `pasteError.value`. Build image items as `{ kind:'file', type:'image/png', getAsFile: () => new File([...], name, {type:'image/png'}) }`.
7. **Verify**: `npm run test:web` (all green) + `npx eslint . --max-warnings 0` + `npm run build`. Commit message type is `feat(client):` for the infra itself.

The Hermes UI flags "stale/unverified" evidence unless you produce a temp script under the OS temp dir with a `hermes-verify-` prefix. **Preferred: `.mjs` (Node.js)** — avoids all PowerShell pitfalls (comma binding, CJK mangling, escape issues). Pattern: write `C:\Users\<user>\AppData\Local\Temp\hermes-verify-<task>.mjs`, run `node <path>`, show PASS/FAIL, `Remove-Item` it. Fallback: `.ps1` with `pwsh -ExecutionPolicy Bypass -File <path>` (bare `pwsh -File` intermittently exits 126 on this host). **If the approval system blocks script execution** (terminal returns BLOCKED / "user has NOT consented" timeout — happened twice in one session), do NOT retry the same command; fall back to running the same checks inline (`npx eslint .`, `node node_modules/vite/bin/vite.js build`, targeted `Select-String`/regex greps for the structural checks) and state honestly in the 提交材料 which checks ran inline vs via script. Before writing the script, `Test-Path` the worktree you're verifying — after a version merge 一号 may have deleted it; verify from the main worktree (master) instead. Summarize explicitly as "ad-hoc verification, not project suite green" for code paths the vitest suite doesn't cover (since v0.18 the frontend HAS a suite — `npm run test:web`; run it first and cite it for covered paths; ESLint + Vite build remain the always-on gates).

**🔴 PowerShell pitfall #1 — comma binds tighter than `-match`.** A check written as
`@('R30a grid', $qb -match 'repeat\(auto-fill')`
does NOT do what you think. The comma (array construction) binds tighter, so PowerShell evaluates `('R30a grid', $qb) -match 'repeat\(auto-fill'` — a FILTER over the array — which returns the matching ELEMENT (the entire file contents), not a boolean. Your PASS/FAIL logic reads garbage and dumps the whole file into the output (this happened live: a 54KB transcript of false FAILs). **Fix: always use `[regex]::IsMatch($str, 'pattern')` for boolean checks** (returns a clean `$true/$false`), or wrap in explicit parens `@('label', ($qb -match 'pat'))`. Prefer `[regex]::IsMatch`.

**🔴 PowerShell pitfall #2 — branch-awareness.** If your unmerged changes span MULTIPLE branches (e.g. R34 on `feat/...-r34-links`, R30 on `feat/...-r30-board`), a single script reading files from the working tree only sees the CURRENT branch. Checking R34's template edits while checked out on the R30 branch → false FAILs. **Fix: `git checkout <branch>` before reading that branch's files, run its checks, then move on; structure the script per-branch and return to the primary branch at the end.**

**🔴 PowerShell pitfall #3 — multi-line commit messages with `\"` escapes.** `git commit -m "feat: ...\n\n- 工具栏\"管理\"按钮..."` breaks: PowerShell's `\"` inside double quotes does not escape for the native git process the way you expect — git receives the message split on spaces and treats each fragment as a pathspec (`error: pathspec '多选模式下...' did not match any file(s)`). The `git add` already succeeded, so you're left staged-but-uncommitted. **Fix: use single-quoted strings for any commit message containing quotes or special chars** — `git commit -m 'feat(client): ...'`. Single quotes pass everything literally. (If the commit fails this way, just re-run `git commit` with single quotes — files are still staged.)

**🔴 PowerShell pitfall #4 — CJK literals inside inline regex checks false-fail (R58).** `[regex]::IsMatch($zh, "artistQqLabel: '画师QQ'")` returned FAIL in an inline terminal command while the content provably existed (`search_files` found the exact line) — CJK characters in the command string can be mangled in terminal transmission. **Fix: match ASCII key names only** (`'artistQqLabel:.+jumpQq:.+copyQq:.+qqCopied:'`) and verify CJK values via `search_files` (file-based, encoding-safe). Same class as pitfall #1 and the R53/R46 comment-vs-attribute false positives: when the check medium can't faithfully represent what you're matching, change what you match.

Other script notes: use `Push-Location`/`Pop-Location` around `npx eslint .` and the build. For the build, prefer `npm run build` (the npm-script form is NOT misclassified); the direct binary `node node_modules/vite/bin/vite.js build` also works; bare `npx vite build` triggers the "long-lived process" false-positive. Check `$LASTEXITCODE` immediately after each. End with `exit 1` if any FAIL so the run's exit code is honest.

**🔴 `.mjs` script pitfall — git cwd when comparing against master.** If the verify script shells out to `git show "master:<path>"` (for the "judge new against master" residue check), do NOT derive the cwd from the source-tree root with relative math like `resolve(ROOT, '../../..')` — from `web/src` that lands on `web/`, not the worktree root, and git exits with `fatal: not a git repository`. The `try/catch` swallows it, `masterContent` stays empty, every pre-existing line looks "new" → false FAIL + a retry loop. **Fix: hardcode the absolute worktree root as the cwd** (`cwd: 'D:/Hermes Agent CN Desktop/workspace/artist-commission-02'`). Same class as the other verify-script pitfalls: the check medium (a detached script) has no ambient cwd, so pin it explicitly.

**🔴 `.mjs` script pitfall — don't parse `vite build` stdout for chunk sizes; read the dist file.** A size check that regexes the build output (`out.match(/main-[\w-]+\.js\s+([\d,.]+)\s*kB/)`) silently returns null when the format doesn't match (vite's `computing gzip size:` table layout, padding, or a re-run that prints differently) — the `?: 9999` fallback then reports a bogus `9999 kB` FAIL even though the build succeeded. **Fix: stat the actual emitted file** — `readdirSync(WEB+'/dist/assets').find(f => f.startsWith('main-') && f.endsWith('.js'))` then `statSync(...).size / 1024`. The file on disk is truth; the human-readable table is not. (v0.20: this produced the lone FAIL in an otherwise 22/23 run; switching to statSync gave a clean 23/23.)

**🔴 `.mjs` script pitfall — double path-constant concatenation.** Defining both `const WT = '.../artist-commission-wt-02'` and `const WEB = WT + '/web'`, then writing `readFileSync(WEB + '/web/src/main.js')`, yields `.../web/web/src/main.js` — ENOENT on every structural check. When you have a parent/child path pair, pick ONE as the base for each read and never re-append a segment that's already in the constant. Grep your own script for `/web/web/` (or any doubled segment) before running. Same class as the git-cwd pitfall: detached scripts have no ambient path context, so a wrong constant poisons every line that uses it.

## Pitfalls

- **Designing interactions against the requirement doc instead of the backend code (R39 proposal).** The requirement doc describes intent; the service code describes truth. A proposal that includes a button with no backing endpoint (or one that silently 400s in certain states, or cascades status changes you didn't account for) gets rejected or blocks mid-implementation. Always read `server/src/features/**` for every action the proposal offers — see step 3 of "Produce an interaction proposal". Backend gaps found at proposal stage are cheap (one 协调项 line); found at implementation stage they stall the whole batch.
- **el-image `preview-src-list` swallows parent clicks (R18 review rejection).** If a wrapper has `@click="handler"` and the inner `el-image` has `preview-src-list` (+ `@click.stop`), the handler never fires — el-image's built-in preview intercepts the click. Fix: remove `preview-src-list`/`initial-index`/`@click.stop` from el-image; let clicks bubble to the wrapper. Move preview to a hover-revealed magnifier button (`@click.stop`) that opens a standalone `<el-image-viewer :url-list="..." :initial-index="..." @close="...">` (globally registered, usable directly in templates). Interaction semantics: single-click = business action · hover 🔍 = preview · hover ✕ = delete. This is the #1 most likely Element Plus click bug in this project — 一号 rejected R18 for exactly this (验收标准 #3 "点击图片=设为焦点" failed).

  $masterLines = (git show "master`:$f") | ForEach-Object { $_.Trim() }
  $added = git diff master...HEAD -- $f | Where-Object { $_ -match '^\+' -and $_ -notmatch '^\+\+\+' -and $_ -match 'v-html=' }
