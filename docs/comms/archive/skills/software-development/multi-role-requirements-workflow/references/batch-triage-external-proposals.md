# 外部建议批的拆解分桶（四桶法）

触发：四号收到一批外部功能建议——其他 AI 群组的模拟头脑风暴/模拟人格产出、真实用户反馈攒批、竞品功能清单等（一次多条、来源非正式需求）。

## 核心原则

1. **来源 ≠ 需求**：AI 模拟人格/第三方建议的痛点合理但未经验证。拆解归拆解，不急着立项——先分桶讨论，用户拍板后才决定进候选池（写 REQ）还是占位备案。
2. **拆解前逐条过三层撞车检查**（只做第一层会被用户当场纠正，2026-08-05 两次漏查均为实证）：
   - **代码层**：grep/扫一遍代码库，确认不是已实现功能（12 条逐一核实零撞车）。已实现的直接降级为"现状说明"，不进任何桶。
   - **备案层**：搜 docs/archive/requirements、STATUS 待办池、小工具集清单等备案处，看同类项是否已备案（见原则 5）。
   - **业务流程层（最易漏）**：推演现有真实业务流程是否已消化该需求——建议解决的痛点在现行手工流程里是否已被自然解决？实例：C3「收款平台结构化」——现有流程是下单→画师必然联系客户确认→线下付款→手动录入收款，付款信息聊天里就说清了，结构化展示无落点 → 用户问"所以这个暂时没用吗？"确认后丢弃。代码 grep 是本能，推流程不是——分桶前强制过一遍。
3. **核对排期协同**：对照 STATUS.md 版本计划与在途工作。能搭上现有批次的（例：分享按钮需要的域名白名单/链接安全校验，正好是已交付待合入的 F2 外链防投毒基础设施），明确标注搭哪班车。
4. **安全/形态冲突显式标出**：与近期已拍板的安全方向或产品形态冲突的建议（例："不用登录"vs 刚上线的 TOTP），不静默丢弃也不照单全收，提出保留大部分体验的缩减变体。
5. **核对既有备案归档防重复立项**：拆解前搜 docs/archive/requirements、STATUS 待办池、小工具集清单等备案处，看同类项是否已备案。实战：C1「客户标签」已在 FB-13 小工具集备案（2026-08-02 反馈汇总），差点立新 REQ——正确处置是合并进原备案条目，不新建。

## 四桶法

| 桶 | 判据 | 处理 |
|----|------|------|
| A：数据已在库里，只差出口 | 零/低成本，确定性高（如收款流水导出、凭证渲染） | 优先进候选池 |
| B：与已排期工作协同 | 可搭现有批次的便车 | 写明搭哪个班次、共享哪个基础设施 |
| C：独立新功能 | 需用户决定是否进候选池 | 附风险点 + 缩减变体 + 甲/乙选项 |
| D：改变产品形态 | 动状态机/核心流程/法律定位（如实物邮寄交付、合同自动生成） | 建议占位备案，不直接排期 |

## 呈现格式

决策项一次全呈现（用户偏好"你整个出来我一起看"）。每桶一张表：建议 / 现状核实 / 我的评估。末尾"需要你拍板"编号清单，一条一问。桶前声明大前提（来源性质 + 处理原则）。

## 用户批复模式（2026-08-05 实测）

用户用压缩批量回复："a桶可以 / b1可以 b2丢弃 / c3c4细说 / c5不稳定直接丢 / d1这个和a1是不是一样"。处理规则：

- **用户问"是不是已经有类似功能"** → 先读代码再回答：报出已覆盖的确切范围（组件名 + 行号 + 展示了什么）+ 剩余缺口清单 + 缩水建议。实例：ManualOrder.vue 已有 QQ 历史订单面板（92-106 行，防抖 500ms 查最近 5 单）→ C1 回头客需求缩水为"面板加一行汇总（几单/累计/最近），标签丢弃"，从新功能降级为面板增强。
- **用户说"细说"** → 结构化深挖：现状 / 做成什么样（ASCII 示意图或示例文案）/ 边界（不做什么）/ 风险点 / 我的建议（甲/乙选项 + 明确推荐项）。
- **用户设 kill criterion（"如果不稳定直接丢弃"）** → 诚实直答，不绕。外部依赖稳定性分两层评估：**数据源稳定性**与**部署可达性**是两回事（实例 C5 多币种：frankfurter.app 背后是欧洲央行官方汇率，数据源层面稳定；但国内 Docker 出网可达性未验证，不能假设通）。给甲（花 5 分钟让三号 curl 探测）/乙（直接丢）两个选项。
- **用户混淆两个概念（"d1 和 a1 是不是一样"）** → 对比表区分。凭证三分法见下。

## 落库（拍板后一次提交）

1. **进池项** → 一份「候选项清单」REQ：开头对齐记录（来源性质 + 拍板日期 + 排除项），每条含现状核实/方案轮廓/草稿验收标准，末尾同批分流去向表（参考 REQ-031）。
2. **D 桶** → 占位备案 REQ（格式照 REQ-030/032：用户原话 + 核心概念 + 明确不做 + 待未来展开）。
3. **与既有备案重合** → 更新原备案条目（如STATUS 待办池 FB-13 补合并说明），不立新 REQ。
4. **丢弃项必须留档写清原因**——写进候选清单的排除项，防同一想法日后被重新提出时无人知道已被否决（例：C3 丢弃原因 = 现有"下单→画师联系→线下付款→手动录入收款"流程已消化该需求）。
5. **comms 转交一号**：结论 + 待一号决策项，不重复需求文档已有内容。
6. **提交卫生**（并行窗口环境）：工作区常有其他窗口的未暂存改动——`git status --short` 核对后**显式 git add 自己的文件清单**，提交前再看一眼暂存区，禁 `git add -A`（实战：发现别窗口未提交的派工文件，避开未带入）。

## 可复用子模式

- **凭证三分法**：记录型（导出 CSV/收据 = "发生了什么"）vs 约定型（合同 = "应该发生什么"）。区分四维：时机（事后 vs 事前）/ 给谁看 / 内容 / 性质。平台渲染"合同"类凭证时收窄定位为「委托确认书」——只记录事实（谁/档位/价格/截稿日），不碰版权/违约/签署等法律字眼，平台不暗示法律保证。
- **安全冲突检测**：建议与刚立起来的安全 posture 冲突（例：扫码免登录 vs REQ-027 TOTP）→ 显式指出冲突，提缩减变体：保留 80% 体验（深链接省掉翻列表）但不开鉴权旁路。原则："为自己 convenience 开鉴权旁路的口子不开"。token 旁路技术上能做，列为乙方案但默认不推荐。
- **收款信息展示边界**：收款平台结构化管理 = 信息展示，不是支付集成；平台不经手钱、不碰订单状态；与外链功能划界（外链="我的其他平台"，收款="你怎么给我钱"）；收款账号内容须纳入现有内容审核范围。
- **时区显示是纯前端**：日期按绝对时间点存储，渲染层用浏览器 Intl.DateTimeFormat 换算客户时区，存储与后端零改动；夏令时 Intl 自动处理。存储不动是这类需求工程量小的关键判据。
- **零预算约束**（用户拍板）：外部服务选型只走免费路线；"免费"还要追问可达性（见上）。
