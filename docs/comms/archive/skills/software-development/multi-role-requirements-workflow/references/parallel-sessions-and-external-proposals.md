# 并行会话冲突与外部方案评审（四号）

## 1. Sibling 会话并发写文件（write_file 警告 "modified by sibling subagent"）

多角色系统下多个 Hermes 会话（一号/二号/三号/四号各一个）同时改 master。写 REQ/SPEC 时收到该警告 = 你上次读后有人改过同一文件。

**处置配方（2026-08-03/04 三次实战）**：
1. 不要慌，先验证自己写入的内容是否是最终版（grep 关键新增内容）
2. `git log --oneline -5 -- <该文件>` 看谁在你读后提交过、提交信息说了什么
3. `git show <那个commit> -- <该文件>` 读对方改了什么
4. 决定合并策略：对方只改了状态字段/小补丁 → 你的大重写基本安全，但必须把对方的改动意图吸收进来（如"已审通过"状态、对方拍板结论）；冲突的决策按"用户最新拍板 > 角色较早提交"
5. 提交信息里写明时间线关系（"晚于 X 的审核提交 `hash`"），comms 里给一号讲清谁先谁后，避免误会

**禁止**：看到警告就盲目重写覆盖、或假装没看见直接提交。

## 2. 用户推翻已提交决策（决策变更传播）

典型场景：一号审核通过旧版 REQ（含当时拍板），之后用户在与四号的对话里改主意。

**写法**：
- REQ 状态字段改精确：`🔄 F1-F5 已通过审核；F6 为用户后续新增，待一号确认范围`——不要退回"待审核"（否掉已审部分），也不要假装没变化
- 被推翻的旧拍板在"已确认事项"节标注推翻时间与新结论，用户原话逐字录入"用户原声"节（含日期）
- 全文搜索被推翻决策的所有引用点（正文/验收标准/已确认节/comms），一次全部同步，不允许改一处漏一处
- comms 转交文件开头写**时间线**（① 一号审核时用户原话 → ② 之后用户改主意的原话），按"最终拍板为准"，只留一个决策给一号（如排期归属），其余自己消化

## 3. 第三方 AI 方案评审（"吸其精华"工作法）

用户会拿其他 AI 的完整方案来问"你怎么看"。用户原话定调："我们只吸其精华，不要全信，他只是空头最优解"。

**评审四步**：
1. **先给总评**（强在哪、弱在哪，各一句），不逐条复述对方
2. **吸**：列出直接采纳的点（对方论证扎实、与系统兼容的）
3. **弃**：列出不能照搬的点，**每条给"基于我们代码现状"的理由**——外部 AI 的方案都是通用最佳实践，不认识我们的表结构/已有功能/版本计划。评审前必须先 search 代码核实对方提议新建的东西我们是否已有对应物（如对方提议建 Order_Items/Milestones/Transactions 表 → 查库发现 order_extra_items / order_workflow_stages+artist_workflow_stages / order_payments 已服役，照搬 = 平行新表屎山）
4. **给决策项**：把剩余分歧收敛成编号决策项（D1/D2/D3…）让用户一次拍板；推荐项标明推荐理由

**红线**：外部工时估算不采信（排期归一号+实施角色）；"推翻重建/双模式开关"类建议默认警惕（违反用户"统一模型>堆规则、不产屎山"底线）；不贬低对方也不假装没差距——用户要诚实分析。

## 4. 数值型需求的复算验证（守恒律）

用户口述计价/分摊/财务规则时，四号必须**自己逐步重算一遍**，不能只复述：
- 找到守恒量（如：总价 − 已收 = 剩余待收；SUM(条目) = SUM(节点) + 额外项），每步用它验算
- 用户例子里的算术笔误用守恒律抓（2026-08-04 实例：用户把 200×20/50 算成 180，守恒律推出只能是 140，一笔指出并给出修正公式）
- 金额类规则必须写死精度约定：以分为单位、取整方向、尾差归最后一个节点——外部方案常漏这条
- 主动补用户没说的边界：回退是否解锁、部分付款节点怎么算、所有节点都锁了再加价去哪（进"额外应收"桶，写成统一规则比多条特例干净）
