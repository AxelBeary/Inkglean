# 并行代码核实模式（反馈批次 ≥5 条）

反馈批次工作流的"逐条核实代码"步骤，条目多时用 delegate_task 并行。

## 分组策略

按主题分 2-3 组，每组 3-4 条：
- 组1：设置/模板/数据模型类（如 slotDisplay、图片裁切、档位字段）
- 组2：仪表盘/主页/作品展示类（如留言板、统计卡、快捷按钮、封面图）
- 组3：订单/话术/流程类（如手动录单、话术模板）

## 每组 prompt 模板

```
核实拾绘项目中以下功能的代码现状，输出每条的：当前实现方式、关键文件路径+行号、与画师反馈的差距。

**#N 功能名**：
- 读 [具体文件路径]，找 [关键函数/组件]
- 确认：[具体问题]
```

## 关键要点

- 每组给明确的文件路径线索（从 STATUS.md 或一号 comms 中获取），不要让子agent自己搜
- 要求输出格式统一：当前实现 + 文件路径行号 + 差距分析
- 3 组并行 ~4 分钟完成（vs 串行 15+ 分钟）
- 子agent context 中写明项目路径、技术栈、"用中文回复"

## 与用户交流的高效决策技巧

### ASCII 视觉对比 > 纯文字描述
用户是视觉思考者。展示柜方案用 ASCII 画出后用户秒回"很好"；纯文字描述的选项用户需要追问"细说"。

### 给 2-3 个具体选项 + 利弊表
用户决策模式：看到具体选项 → 选一个 → 微调细节。不要问"你想要什么样的"，要问"A/B/C 你选哪个"。

### 用户会微调而非全盘接受
典型模式：用户说"对！"或"很好"后紧跟修改。听到"对/好/行"+ 修改意见时，把修改意见视为最终决策，立即更新文档。

### 用户用现实隐喻思考
"像那种横幅""像小标签""像柜台"——先按隐喻推导设计，再翻译成技术实现。不要反问技术术语。
