# REQ 补丁 vs 在途派工文件冲突（四号）

> 教训日期：2026-08-04（REQ-024 F2/F5 补丁 vs v0.35 波1派工）

## 场景

REQ 已审通过、一号已按旧版本派工（波1/波2 分支在途）。之后用户追问/补拍板，暴露原 REQ 漏洞（例：F5 删旧档位后旧"增项"tab 的拖拽目标消失、页面逻辑断裂），四号打补丁修 REQ——**补丁内容与在途派工文件的明文指令冲突**（派工写"其他 tab 一字不动"，补丁要求删旧增项 tab）。

## 铁律

1. **四号不直接改派工文件**（`01-to-0x-*` 归一号维护，同"不直接改 STATUS"）。
2. **写 comms 转交请一号追加派工条目**：明确引用派工文件里冲突的原句 + 补丁要求 + 改动量评估（例"改动极小，TierManage.vue 删一个 el-tab-pane"）。一号看到后可决定口头追加还是重发派工。
3. **补丁全文档传播**：REQ 补丁不只改一处——功能描述、验收标准、用户原声节（新拍板原话+日期）、F5/迁移节等所有引用点一次改全。
4. **补丁也要做撞车检查**：同 `req-pre-delivery-overlap-check.md`，交付补丁前重读 STATUS + 在途派工，列出冲突点。

## 反模式

- ❌ 直接编辑 `01-to-0x-*.md` 派工文件加一句"另外还要删 XX"（越权，一号不知情）
- ❌ 只改 REQ 不写 comms（在途角色不会重读 REQ 补丁，冲突指令照旧执行）
- ❌ 补丁只改正文一处漏验收标准（五号日后按旧验收标准测）

## 附带教训：用户提问暴露需求漏洞是常态

用户问"增项和增项库是啥关系"→ 四号读代码解释关系 → 发现两套模型并存的入口在 REQ 补丁场景下会断裂。**用户提问 = 免费的需求审查**，回答时必须同时自查"这个现状在 REQ 实施后还成立吗"。
