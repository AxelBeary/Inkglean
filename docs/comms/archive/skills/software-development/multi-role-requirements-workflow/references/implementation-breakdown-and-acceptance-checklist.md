# 四号文档派工：实施拆解（plan）+ 验收操作清单

触发：一号派工让四号写「实施拆解文档」（放 `docs/plan-*.md`，如 `plan-req022-实施拆解.md`）或「验收操作清单」（放 `docs/comms/04-to-01-*.md`）。注意：plan-*.md  normally 归技术角色维护，四号只在**一号明确派工**时写，且只写文档、零代码、不改 REQ 原文。

## T1 实施拆解文档结构

1. **代码现状核实表**（第〇节，必须有）：拆解前直接读 master 源码核实，不凭记忆、不信 REQ 里的「现状」描述。每项写：现状（文件+行号）→ 对拆解的影响。
   - 必查：相关表的 CREATE TABLE 语句（server/src/db/init.js）、相关 service/routes 已有接口、前端字段引用（search_files 按字段名 grep）。
   - 三类改变拆解的发现模式：
     a) **已存在的表/接口覆盖了用户拍板**（例：artwork_size_tags 多对多表 v0.37 已建，「允许绑多个」天然支持 → 绑定档位后端近零新增，工时大头转前端）；
     b) **表名误导**（例：platform_config 听名字像平台列表，实为 key-value 表只存 admin_qq → 需新建表，不复用）；
     c) **REQ 词汇与 DB 字段语义不对应**（例：REQ 说「未读/已读」筛选，但 guestbook status 是审核态 pending/approved/rejected，无已读字段 → 标为开工前置阻塞，列 a/b/c 方向待用户/一号拍板，不自行决策）。
2. **逐项任务分解表**：按角色拆（二号前端/三号后端/五号 bug 域），每项估时，小计与 REQ 整体预估表校准——超预估要明确标注并待一号确认（例：防投毒测试单独立项导致 F2 3.5 天 > REQ 的 2~3 天）。
3. **API 契约草案**：新增表给 CREATE TABLE 草案 + 种子数据说明；新增接口给方法/路径/请求体/响应/失败码；**复用接口明确写「已存在，不改」**。
4. **校验职责结论**（凡涉及输入校验）：硬校验全放后端，前端只做体验层预检；关键一条——**后端不信任前端传来的推导结果**（如平台识别 platformId 必须后端从 URL 独立重推导）。依据铁律「前端校验只能是后端规则的子集」。
5. **依赖与顺序**：串行/并行关系 + 并行度结论 + 与其他在途批次的冲突分析（页面重叠 → 必须串行，视觉套后批 token）。
6. **风险点**：对照历史教训逐条过（snake_case 映射、i18n 双语同步、前端校验子集、批次冲突）；安全类风险（域名匹配、私有→公开目录文件复制）标为不可妥协项并要求测试向量先行。
7. **待确认清单汇总**（末节）：全文所有「待确认」编号汇总成一张表，方便一号逐条拍板。功能决策一律不自行拍板。

## T2 验收操作清单结构

把 REQ §验收标准逐条转成**可勾选的操作**，每条三要素：打开哪个路由 / 看什么元素 / 需要多主题多视口的写明清每遍。附加三块：

1. **语义核对表**：颜色/状态类规范做「颜料→语义→构造与查看操作→各主题勾选列」表格，外加**语义互斥检查**（A 状态元素没用 B 颜色、某颜色只出现在允许场景）。
2. **零影响抽查路由表**（凡声明「客户端零影响」类验收）：列全部客户端路由 + 每行检查重点；**附机器检查**——`git diff master...交付分支 -- web/src/views/client/` 输出为空、theme.css 无 `-` 行（现有变量值零改动）。数字引用量实测后写「N 行含 var(-- 引用」，不写含糊的「170+ 处」。
3. **验收结论模板**：留空给审核人填（通过/有条件通过/打回 + 未过项）。

### 预写清单场景（被验收批次尚未交付，F1/F2 案例 2026-08-05）

清单在实现完成**之前**撰写、备将来验收用时，在上述结构之上追加五条纪律：

1. **前提节钉死拍板**：把用户/一号已定案规则逐条写在文档开头并注明「不再列待确认」——清单是执行用的，不是再讨论用的。
2. **前提准备节**：写明要构造哪些测试数据（哪几种状态的订单各一单、每模板各备几个测试画师、需要什么账号），验收人不用现场想。
3. **改动位置用代码现状实锤**（文件+行号写进前言节）——防凭拆解文档臆写不存在的入口名（派工原话「别凭拆解臆写入口名」）；入口按钮文案等拿不准的标「以交付时界面为准」——预写清单是行为契约，不是像素规格。
4. **易漏边界态单独给一条**：如 done 是半终态 ≠ delivered（无发布入口）——用户拍板的边界值得专条防漏。
5. **安全/测试向量速查表与清单条目编号一一映射**：后端已全绿的向量前端批不必全复测，★ 标前端行为抽查重点；「4 模板逐一点名」类要求做成逐模板表格行，不许一条带过。

注意边界：属于改造范围的页面（如登录页）不要混进零影响抽查表，写注释说明其验收归属。

## 提交纪律

- 分支确认 + `git merge master` 后再动笔；只 add 这两个文档，逐个核对 git status。
- **派工文件找不到时先 `git merge master` 再下结论**：worktree base 可能落后 master（派工文件是后加进 master 的）。别急着认定「给错文件名」去拿相似文件凑（2026-08-05 实战：F1F2 派工文件在 worktree 不存在 → merge master 后原样出现）。
- Commit 格式 `docs(comms): …待一号审核`；不推送不合并，交付摘要给：文件路径 + 每项关键结论（校验职责结论、并行度结论）+ 重要代码现状发现 + 待确认项数量。
- REQ 原文只读；拆解中超 REQ 预估的工时、未定稿的语义全部标「待确认」。
