# 反馈批次处理增强模式（2026-08-01 REQ-013 实战总结）

## 批量代码核实：并行子任务

当反馈批次 ≥5 条时，用 `delegate_task` 的 tasks 数组并行派出 2~3 个子任务核实代码，每个子任务负责 3~4 条。

**子任务 goal 模板**：
```
核实拾绘项目中以下功能的代码现状，输出每条的：当前实现方式、关键文件路径+行号、与画师反馈的差距。

**#N 功能名**：
- 找 XX 组件，看 YY 逻辑
- 确认：ZZ 是否已实现
```

**context 模板**：
```
项目路径：D:\Hermes Agent CN Desktop\workspace\artist-commission。
Vue3 + Element Plus 前端在 web/src/，Fastify 后端在 server/src/。用中文回复。
```

一轮出全部结果（~4min），比逐条串行快 3 倍以上。

**注意**：子任务结果是 self-report，关键行号和结论在写文档前应抽查验证（至少对优先级最高的 2~3 条）。

## 用户发截图时：审计附加问题

用户可能发仪表盘/页面截图作为设计讨论的输入（如"你也看下上面的图再说"）。收到截图后：
1. 先回答用户问的具体问题
2. **主动审计截图中的附加问题**（命名不一致、功能重复、布局浪费等），作为发现提出
3. 审计发现写入文档的"代码现状"或"附加问题"段

实例：用户发仪表盘截图讨论按钮自定义，审计发现 6 个快捷按钮中 5 个与侧边栏重复且命名不一致（"图库管理" vs 侧边栏"作品管理"），写入 REQ-013 #3 方案。

## 设计讨论模式：A vs B + 推荐

与用户讨论 UI/UX 方案时，用"A vs B + 我推荐 X，理由是……"的格式。

**关键经验**：用户经常会提出更好的第三方案（如 REQ-013 #9 用户提出"展示柜"概念——左侧菜单+右侧大图切换——比四号的三个选项都好）。不要执着于自己的选项，用户提出第三方案时立即分析可行性并迭代。

每轮最多呈现 2~3 个决策点，等用户回复再推进。用户回复极简（"对！""可以""很好"）时视为确认，不要追问"你确定吗"。

## 用户拍板后的即时落文档

用户口头确认方案后，立即更新文档 + commit + push，不等攒批次。REQ-013 整理中用户分 3 轮拍板了 4 项决策，每轮确认后四号即时更新文档并提交，最终一次写 comms 转交。

## SPEC 文档结构（SPEC-005 模板）

经过 SPEC-005 日历视图验证的 SPEC 结构：

```markdown
# SPEC-00X：功能名

> 编号/作者/日期/状态/来源/定位

## 对齐记录
- 日期/参与/关键结论/排除项/待确认

## 1. 页面结构（ASCII 示意图）
## 2-N. 各视图/模块详细设计
  - 布局（ASCII 图）
  - 视觉区分（表格）
  - 交互规则
## N+1. 默认设置/配置
## N+2. 交互规则（本版本 vs 未来扩展）
## N+3. 数据需求（表格：字段/来源/说明）
## N+4. 验收标准（编号，按视图分组）
## N+5. 实施建议（波次表格）
## N+6. 与现有功能的关系（表格）
```

关键原则：
- ASCII 示意图比文字描述直观 10 倍，用户能"看见"最终效果
- 验收标准按视图/模块分组编号，不混在一起
- "与现有功能的关系"表格帮一号判断依赖和并行度
- 数据需求表格帮三号快速确认 API 是否够用
