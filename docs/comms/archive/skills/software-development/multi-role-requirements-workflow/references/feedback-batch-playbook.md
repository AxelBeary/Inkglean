# 反馈批次整理实战技巧

来源：REQ-013 画师反馈批次（2026-08-01），10 条反馈 ~4 分钟完成全部代码核实。

## 1. 并行子agent批量代码核实

收到 N 条反馈批次时，按代码区域分 3 组派并行子agent（每组 3-4 条），每条要求输出三件事：
- 当前实现方式（组件/路由/数据模型）
- 关键文件路径 + 行号
- 与反馈的差距（反馈说的 vs 代码实际的）

分组按**代码区域**（仪表盘类 / 主页模板类 / 订单流程类），不按条目编号——同一组件的多个问题放一组，避免重复读文件。核实结果回来后先建 todo 逐条跟踪，再批量写文档。

## 2. UI 截图交叉核实

用户发来当前界面截图时，不止看截图本身——和侧边栏、其他页面、代码交叉对比：
- 案例（REQ-013 #3）：截图显示 6 个快捷按钮，对比侧边栏发现 5 个与菜单重复 + 命名不一致（按钮"图库管理" vs 侧边栏"作品管理"）→ 需求从"加自定义"升级为"候选按钮池 + 命名统一"
- 截图还暴露内部术语文案：仪表盘"正式 3/5"画师看不懂，而客户端主页已有 slotDisplay 人话文案（"开放中 · 剩 N 席"）→ 方案直接复用，让画师端和客户端说同一种语言

## 3. 共享组件先确认再定方案

改 UI 组件前确认是否多模板共享（grep 组件名看几个页面引用）。共享 → 全模板统一生效，**不做模板级开关**。用户产品哲学："一个逻辑搞定多个场景"，反感逐场景堆规则/开关。旧设计如果是坏的（如固定高度裁切），没有"保留坏设计"的理由，不加兼容开关。

## 4. 后续专项备案

用户说"之后好好探讨 / 之后再说"的话题 → 需求文档末尾设"后续专项备案"表（专项 | 来源 | 说明），不塞当前批次也不丢失。comms 转交文件里同步提一句，让一号知道有排队中的话题。

## 5. 依赖关系写进实施建议

整理完多条需求后，给一号的实施建议要标明批次依赖：
- 天然耦合的同批做（如展示柜菜单需渲染档位三态 → #9+#10 同批，分开做要改两遍）
- 有前置的标出来（如按钮候选池依赖留言管理页面先存在）
- 极小项（~30min 级）标注"可随任意批次捎带"
