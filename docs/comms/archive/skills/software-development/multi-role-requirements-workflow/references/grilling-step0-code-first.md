# 需求拷问 Step 0：先摸底代码现状，再开口问

> requirements-grilling 本体是受保护 skill（created_by=None，后台策展人 patch 会被拒），拷问流程的所有改进落本 skill。
> 教训日期：2026-08-03（artist-commission 画风/档位页面合并需求）

## 为什么需要 Step 0

用户口头需求几乎都基于"页面上看到的现象"，但现象背后的真因可能是：功能缺失、字段不存在、两个功能互斥、或纯粹是 Bug。不读代码就直接拷问 = 拿猜测当事实，问出来的问题用户听不懂、选项也列不准。

**原则：复述和提问必须建立在核实过的代码事实上，不建立在猜测上。**

## 操作清单

1. **定位相关组件/页面**：`search_files(target='files')` 按功能关键词（style/tier/gallery/order…）找 .vue/.js 文件。
2. **读展示层**：页面组件的 template 段——实际渲染了什么（图/文字/价格/按钮）、哪些分支互斥（v-if/v-else-if）。
3. **读数据模型**：server 端建表 SQL（`CREATE TABLE` + 字段），确认"用户想要的东西"在库里有没有对应字段。没有字段 = 功能缺失（需求），有字段不显示 = Bug。
4. **读配置侧**：画师/管理员后台的编辑组件，确认"用户有没有上传入口"。
5. **把事实写进复述**："我看到的现状是：X 页面显示 A，Y 页面显示 B，两者互斥（v-if）；表里没有 C 字段"——用户一听就能纠正或确认。
6. **每个追问带 a/b/c 可点选选项**，选项从代码事实推导，不让用户从零描述。

## 实战例（2026-08-03）

用户原话："现在主页只能显示画风的图片吗？不能显示我自己上传的图？？是不是应该把画风和档位的两个页面放在一起，图片要对应"

**摸底结果**（约 5 次 search/read）：
- `TplStyleGrid.vue`（新模型画风柜）：画风有 1 张封面图（cover_image），画风下的尺寸档位只有文字+价格，**无图字段**
- `TplTierGrid.vue`（旧模型档位柜）：每档位有 example_image
- `ArtistHomeAtelier.vue`：`v-if="styles.length"` → 画风柜，`v-else-if="tiers.length"` → 档位柜，**两者互斥**
- `init.js`：art_styles 表有 cover_image，style_sizes 表**没有任何图片字段**；tiers 表有 example_image
- `ArtStyleManager.vue`：后台只有画风封面上传入口，尺寸没有上传入口

**由此产出的复述**：一句命中——"每个画风只有一张封面，档位全是干巴巴的文字+价格，没法给每个档位配图，且画风/档位两套展示割裂"。

**由此产出的 3 个追问**（全部带选项）：
1. "自己上传的图"指什么？(a) 想给每个档位各配一张图但系统没这功能 (b) 已经传了但没显示（那是 Bug，说哪个画师哪一步）(c) 其他
2. "两个页面放一起"指哪侧？(a) 客户端主页 (b) 画师后台配置入口 (c) 两侧都要
3. 旧模型画师（无画风）怎么办？统一迁成"默认画风+档位带图"彻底消灭两套模型，还是保留兼容？——附注：按用户"统一模型 > 逐场景堆规则"原则倾向前者，但先听用户拍板

## 用户笼统规则撞上已有数据现状：摆矛盾，让用户裁（2026-08-03 REQ-024）

拷问中常遇到：用户给一条笼统规则（"一律默认关""全部清掉重来"），但 Step 0 摸到的代码现状显示某条既有数据会被这条规则误伤。

**处置**：
1. 明确指出矛盾，给出具体受影响的例子（"alice 已经有 2 个画风在展示，一律默认关会立刻隐藏她正在用的第二画风"）。
2. 给两个选法 + 自己的倾向，但让用户裁。
3. 用户选了与自己倾向相反的选项——照办，原话记入文档，不反复劝。

**实战例**：用户定"多画风开关一律默认关"。摸底发现 alice 已有 2 画风正在展示，于是给出 选1（一律关，alice 自己进后台打开恢复）vs 选2（已有多画风的画师迁移时自动开）并倾向选2。用户拍"一律默认关，alice 自己去打开"——与我的倾向相反，照办并逐字记入 REQ-024"用户原声"节。

**反模式**：
- ❌ 自作主张把规则改成"智能默认"悄悄绕过矛盾
- ❌ 不提矛盾直接按字面写文档（用户不知道副作用，事后算 Bug）
- ❌ 用户已拍板后还在文档里夹带自己的倾向（文档只记用户决定，倾向只存在于拷问对话中）

## 内部解决优先，不上交（用户 2026-08-03 明确要求）

> "一号太忙了 我们能内部解决的讨论别交给他。"

拷问产生的"待确认"项分两类：

- **技术事实问题**（外键级联行为？有没有兜底？字段存不存在？）→ **自己读代码定案**，写入文档"已确认事项"节并标注"四号代码核实+日期"，不写"待三号确认"上交。
- **真决策问题**（产品取舍、语义变化要不要提示）→ 给用户 a/b/c + 推荐，一次问清。

实战例（REQ-024）：历史订单档位显示——核实 `orders.tier_id` 外键 `ON DELETE SET NULL` + 查进度页已有 `tierName || '定制'` 兜底 + 价格存 quote_snapshot 不依赖档位表 → 直接定案"迁移无需特殊处理"，未打扰一号/三号。

## 用户反提方案时的处理

用户不选你给的选项、反提自己的想法时（如"直接画师的作品管理里可以加档位等描述"）：

1. 先读代码核实该想法落点的现状（目标页面/数据表现在缺什么能力）
2. 给诚实评价：好在哪、工程量多大、与已对齐需求协同还是冲突
3. 给实施选项（甲/乙/丙）+ 推荐 + 理由，让用户一句话定

拷问后段用户常推翻先前拍板（REQ-024 中 showcase 先拍"不提示"、后改"选乙丢弃"）。**以最终拍板为准**，决策变更全量传播到文档所有引用处（正文/用户原声/验收标准/已确认事项节），交接文件写清时间线。

## 反模式

- ❌ 不读代码直接复述用户原话（没有信息量，用户会觉得你没听懂）
- ❌ 开放式追问让用户从零描述（"你说的'图片要对应'是什么意思？"）→ 换成带选项的封闭式追问
- ❌ 把"疑似 Bug"直接写进需求文档——先问用户是功能缺失还是已有功能没生效，两者处理路径完全不同（需求走 REQ，Bug 走待修复清单）
- ❌ 技术事实问题标"待确认"上交——先读代码核实，能内部定案的别麻烦别人
