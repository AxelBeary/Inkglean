# 多话题深聊批工作流（四号）

一号一次派多个待对齐话题（如"QQ Bot / ManualOrder / REQ-022 待确认 / v038 需求稿"）时的执行模式。案例：2026-08-05 需求深聊批。

## 执行顺序

1. **一轮预核实全部话题**（不边聊边查）：
   - 每个话题的代码现状：字段有无消费方、开关是否兑现、TODO 位置——search_files/read_file 实锤，不凭派工转述
   - 相关 REQ/comms/STATUS 已拍板记录与待确认清单
   - 例：client_notify 字段存在但无消费方；OrderForm 的 notifyEnabled 在 useOrderForm.js composable 里（页面模板搜不到定义时查 composables/）
2. **按派工优先级逐题深聊，一次只开一个话题**。未轮到的高级话题（如"备案不急"类）即使用户提了也要克制，除非用户主动展开。
3. **每个话题的开场结构**：
   - 先交代已核实的现状（"现状一/二/三"），用人话 + 说清影响（如"没有它平台没法开门"），让用户知道哪些不用操心
   - 再列决策项 D1/D2/D3…：**一次全呈现**，每条附我的建议 + 理由 + 明确排除项
   - 用户偏好：决策项不挤牙膏（"你整个出来我一起看"）；但单个话题内仍按 grilling 节奏推进
4. **收尾纪律**：全部话题聊完统一出稿、统一转交一号审核；**不边聊边合入、不自行 commit 推送**（派工明确要求时）。每题产出写清拍板记录（日期+原话要点）。

## 与 requirements-grilling 的差异

- grilling 说"每轮最多 3 个问题"——那是单话题拷问节奏；深聊批的决策项呈现按用户偏好一次给全（每条带建议，用户只需逐条确认/否决）
- grilling 的反模式"问 10 个问题"针对的是无建议裸追问；带建议的决策清单不算
- 预核实（step 0）两边一致：拷问前必须摸底代码现状

## 常见坑

- 派工文件的"现状实锤"也可能有偏差（如写"客户下单时勾选"但勾选实际在两处页面）——仍以自己核实的代码为准，发现偏差在需求稿/转交报告中注明
- 文档里"备案"的远期清单（如开发自参考的"Phase 2 待做"）是现成的排除项素材——本轮不做的明确写"建议排除"让用户确认，不要假装不存在
