# Deferred Improvement REQ 文档模板（先记录，下一轮改）

当用户发现问题但明确推迟（"先记录下来 下一轮改进"），REQ 文档应作为**未来 sprint 的即用简报**。

## 结构

1. **对齐记录** — 日期、参与者、关键结论、已确认/待确认项
2. **问题诊断表** — 编号问题（P1-P7）+ "用户感受"列（非技术语言描述影响）
3. **建议方案** — 具体重组方案，含 before/after 对比表
4. **待拍板** — 决策项表格（决策项 | 选项 | 建议），标注"下一轮排期时确认"
5. **现状快照** — 当前状态清单（菜单项、Tab 结构、路由），实施者无需重新调研
6. **涉及文件** — 需修改的确切文件路径

## 核心原则

文档必须**自足可实施**——两周后接手的开发者不需要重读代码库就能理解要改什么。显式写出"改之前是什么样"。

## 状态标记

🔴 待排期（不是 🟡 规划中——后者暗示正在主动规划）

## 实例

REQ-016（画师后台界面逻辑重组）：7 问题诊断 + 设置页四 Tab 重划方案 + 侧边栏瘦身 + 6 项待拍板。
