# 深聊批工作流（一次派工多话题，逐题聊透落稿）

> 2026-08-05 五话题深聊批验证（QQBot/ManualOrder/REQ-022/v0.38/REQ-014）。派工形态：一号发"与用户逐题深入交流"批，四号不写代码、不 commit，产出需求稿后统一转交。

## 总体节奏

1. **读派工 → 确认 master**（`git branch --show-current`；深聊批零代码不需要 worktree）
2. **内部核实先行、一次并行收齐**：所有话题的代码现状（读源文件拿 file:line 证据）、编号占用（`rg -o "REQ-0\d\d" docs` 查重，派工可能已预留编号）、波及面（`rg -l 关键词 docs` 列出会受决策影响的文档）。用户没问到的技术细节自己定案，不转交一号
3. **逐题循环**：呈现核实过的现状（人话）→ 给出决策项（格式见下）→ 用户拍板 → **当题落稿**（写完该题 REQ 再继续下一题，不攒到最后）
4. **决策变更传播**：拍板推翻旧方案时，同步所有引用文档（见下清单），同批内改完
5. **统一转交**：全部聊完后写一份 comms（`04-to-01-…交付-<日期>.md`），不边聊边转交；不 commit 不 push（派工明确由一号审核后合入）

## 决策项呈现格式（实测高效）

- **编号 + 选项 + 推荐 + 一句理由**：`M1. … a) 保留（我推荐）——理由 b) 砍掉`。用户回复极省（"M1. a) / M2. 细说 / M3.要"）
- 每轮最多 3 个决策项；能内部定的先定并说明
- **用户回"细说"**：只展开那一项，给方案对比表（维度×方案）+ 明确推荐，其余项挂起
- **用户反问/补新点子**（"两个输入区要不要统一？""要防投毒"）= **需求扩容信号**：先读代码核实再回应，扩容结论写回 REQ 并附拍板日期与原话
- **用户主动提技术方案**（"扫码刷新的动态码能做吗"）：先核实代码可行性与成本再评价；涉及最终用户端的（如验证器 App）主动核实国产/获取渠道——用户在意画师用得上用不上
- 用户拍板原话逐字进 REQ 的"对齐记录"节（标注日期）

## 单话题 REQ 稿结构（本批验证好用）

对齐记录（日期+原话要点）→ 现状核实（file:line 实锤，"开发不用重新侦查"）→ 核心规则（编号 R1/R2…）→ 边界案例表 → 验收标准（当……时，应该……；具体到布局/行为/交互方式）→ 范围外 → 待确认问题（标注谁确认、是否阻塞定稿）→ 传播影响表（若决策推翻旧方案）

## 决策变更传播清单（话题 1 实例：QQ 发码 → TOTP）

- `STATUS.md 待办池`：受影响条目加删除线 + "已消解/已变更"注记（**不删原文**，留痕可追溯），指向新 REQ
- 其他 REQ 中引用旧方案的表述：原地更新并注明"决策变更：<日期>，见 REQ-XXX"
- 无权限改的（技术文档/CONTEXT 术语表/代码注释）：写进新 REQ 的"传播影响"节 + 转交 comms 点名"转一号/三号处置"

## 转交 comms 模板

交付清单表（话题→产出→状态）→ 重大决策变更专节（连锁影响 + 已传播/待处置清单）→ 需一号排期拍板项（编号汇总）→ 零待确认项说明 → 申请审核。给用户的结束语必须含"四号转交一号，文件：<comms 路径>"。

## 踩坑

- 派工说"已排期 REQ-XXX 二阶段后"时，**重读该 REQ 现状**再开聊（排期/依赖可能已变）
- 新 REQ 编号先查重再建文件；派工预留的编号（如 026）直接用
- 聊到一半用户说"卡死了"：上轮回复丢失是常态，**接着上文继续**，不重新开场
