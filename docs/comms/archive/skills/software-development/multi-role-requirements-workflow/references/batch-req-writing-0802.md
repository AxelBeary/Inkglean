# 批次 REQ 写作实战要点（2026-08-02 会话）

## 编号查询

**必须搜两个目录**：`docs/requirements/`（活跃）+ `docs/archive/requirements/`（已归档）。
只看活跃目录会拿到过期编号。例：活跃只有 REQ-014，但归档已到 REQ-016 → 下一个应是 REQ-017。

搜索命令：
```
search_files(target='files', pattern='REQ-*', path='docs')
```
一次搜 `docs/` 根目录即可覆盖两个子目录。

## 批次 REQ 分组策略

一号派工 B 类 21 条时，按优先级分 3 个 REQ 文件（高/中/低），不按功能逐条出文件。
- 高优先（画师日常痛点）：搜索/加钱/总价/收款 → 一个 REQ
- 中优先（功能补全）：日志/上传/主图/去重等 → 一个 REQ
- 低优先/大工程：链路设计/外链/分页等 → 一个 REQ
- 产品模型级（如多画风）：单独出 REQ，标注"需用户深度参与设计"

每个 REQ 内部按 F1/F2/F3... 分功能块，各自有验收标准和工时估算。

## 用户原话引用

四条硬约束等用户拍板原话必须**逐字引用**（blockquote 格式），不改写不概括。
在 REQ 文件顶部单独一节"用户硬约束（原话逐字引用）"。

## 工时估算格式

每个功能块末尾写"预估工时：X 天"，REQ 末尾汇总表。
一号据此排期，不写工时 = 无法排期。

## 待确认问题

每个 REQ 末尾必须有"待确认问题"节，编号列出。
四号不替用户拍板，但可以给"建议"（标注"建议"字样）。

## 依赖关系

每个 REQ 末尾写清：
- 前置：什么必须先完成
- 关联：哪些 REQ 之间有联动
- 技术：需要哪个角色确认什么

## 提交规范

- 多个 REQ 文件一次 commit：`docs(req): REQ-017~023 简述`
- 显式列出每个文件路径 `git add`，不用 `git add -A`
- commit 后立即 push
- 口头告知一号即可（纯 docs 改动不需要正式 comms 文件，除非一号派工另有要求）

## 产品模型级 REQ 的特殊处理

当需求是"模型重设计"而非"功能补丁"时（如多画风 #26）：
- 状态标 🟡 需用户深度参与设计（不是 🟢 待审核）
- 只记录问题现状 + 方向性思考 + 需用户拍板的问题清单
- **不写验收标准**（写不出可验证的标准，模型都没定）
- 工时写"待模型确定后评估"
- 不替用户选方案，列出选项和问题
