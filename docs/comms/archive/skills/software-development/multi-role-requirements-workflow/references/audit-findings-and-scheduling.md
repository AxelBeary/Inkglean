# 审计发现处理 + 排期定稿模式（2026-08-01 会话）

## 一、第三方审计发现 ≠ Bug（P1-4 模式）

第三方审计报告的"不一致"经常比实际情况更简单化。四号必须**先代码核实再呈现选项**，不能照搬审计描述。

### 典型案例（P1-4）

- 审计说："代码限 5 张，README 写 20 张，不一致"
- 代码核实后：实际是**两层限制**（客户下单单次 5 张 + 订单图库总量 20 张），SPEC-001 已写明"两者不冲突"
- 真正的问题：UI 文案没解释两层关系，客户不知道下单后画师还能加图
- 用户拍板：不改功能、不改基础文案，加 hover tooltip 说明（el-tooltip，~15 分钟）

### 教训

1. **审计描述 ≠ 事实**。四号的价值是翻译——把审计的技术发现翻译成用户能理解的选项
2. 呈现选项时先写代码核实的真实情况（"实际是两层限制，不矛盾"），再给 A/B/C
3. 用户倾向**最小侵入方案**：不改现有行为 > 改文案 > 改功能。tooltip/提示 > 修改界面
4. 分类新增第三类：代码行为符合需求且用户没觉得不好用，只是第三方觉得不一致 → **文档/表述问题**（改文档或加 UI 提示，不改功能）

## 二、v0.19 排期定稿模式

### 用户决策风格（本次验证）

- 用户说"一次做"= 全做不分批，不要自作主张建议分批
- "如果能不阻塞同时多人同时开工最好"= 并行策略是加分项，呈现时给并行波次表
- 问"你的看法是什么"= 要你给明确建议+理由，不是列菜单。给完建议后用户说"ok 做"= 拍板

### 排期定稿文档结构（plan-v019 §9 模式）

```
## N. 排期定稿（用户拍板 日期）
### N.1 范围（表格：项/工时/负责）
### N.2 优先级与并行策略（波次表：阶段/三号/二号/说明）
### N.3 关键决策记录（用户原话 + 四号研判理由）
### N.4 下一步（一号审核 → 三号/二号确认 → 四号更新）
```

### 并行策略呈现方式

用波次表，每行一个阶段，列是各角色同时做什么：

| 阶段 | 三号（后端） | 二号（前端） | 说明 |
|------|-------------|-------------|------|
| 第 1 波 | 小活后端 | 纯前端 0 依赖项 | 前端不等任何人 |
| 第 2 波 | 大活后端 | 消化第 1 波产出 | 交错不阻塞 |
| 收尾 | 补测试 | 统一回归 | 一轮覆盖全部 |

## 三、技术债占位备案模式

五号转达"vue-i18n v9 停维，未来需迁移 v11"时的处理：
- 不写 comms、不估工时、不单独文档
- 在 `STATUS.md 待办池` 加一条：来源 + 说明 + 处理方向 + 状态"占位备案"
- 一次 commit 完事
- 用户/五号说"占一行即可"= 字面意思，不要过度展开
