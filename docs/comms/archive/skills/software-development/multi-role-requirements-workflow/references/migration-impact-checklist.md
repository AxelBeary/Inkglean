# 迁移类需求：待确认项事实核查配方 + 拷问冲突处理

> 来源：REQ-024 画风档位统一（2026-08-03）。用户指令："一号太忙了 我们能内部解决的讨论别交给他。"
> 适用：四号整理涉及数据迁移/模型统一的需求时，产出"已确认事项"节的核查方法。

## 核心原则

REQ 提交后遗留的待确认项，默认不上交：
- **事实类**（数据库行为、前端兜底、旧功能使用情况）→ 四号自己读代码定案，写进 REQ"已确认事项"节（结论+证据+核实日期），补 commit
- **产品拍板类** → 保留为待确认，但必须把选项做成选择题（含四号推荐项），不让用户开放回答
- 只有两类都处理完，才转交一号审核

## 事实核查四点配方（迁移类需求通用）

1. **外键级联行为**：查 schema 里被删表的外键定义。`ON DELETE SET NULL` = 引用自动置空不报错；`ON DELETE CASCADE` = 引用行一起删（危险，必须上报）；无外键/RESTRICT = 删除会失败。
   - REQ-024 实例：`orders.tier_id REFERENCES price_tiers(id) ON DELETE SET NULL` → 删旧档位后历史订单档位引用置空，不报错。
2. **前端空值兜底**：搜索消费该字段的页面有没有 fallback。
   - REQ-024 实例：TrackOrder.vue `order.tierName || $t('common.custom')` → 档位空时显示"定制"，无空白。
3. **金额/关键字段是否快照化**：查价格等关键数据是存订单自己的快照字段（quote_snapshot/price_snapshot）还是实时 join 被删的表。存快照 = 不受迁移影响。
4. **旧功能的实际使用率**：迁移会改变语义的旧功能（如 showcase"展示专用"档位），先查种子/演示数据是否用过、代码路径是否活。没用过 → 风险降级为理论风险，可以简单处理（REQ-024：carol 三档均 visible，showcase 未使用 → 三选一给用户拍板即可，不阻塞审核）。

四点查完，大部分"待确认"会变成"已确认+证据"或"选择题"。

## 拷问中的拍板冲突处理

用户拍板与现有数据/状态冲突时：**不默默照办、不替他圆场，把具体后果摆出来让他显式选择**。

REQ-024 实例：用户拍板"多画风开关一律默认关"，但 alice 已有 2 个启用画风在生产展示。四号把后果写明（"迁移后 alice 第二画风立刻对客户不可见，要她自己进后台打开开关才恢复"），用户明确答"接受"。三样都要进文档：拍板原话 + 后果陈述 + 用户确认。

## 验收标准写法（迁移类）

- 幂等复跑不重复不丢数据（v0.33 教训：清理与种子显式区分归属）
- 迁移后既有周边数据（订单/作品/增项/倍率）不受影响
- 受影响用户的恢复路径要可测（如 alice 打开开关后第二画风恢复显示）
