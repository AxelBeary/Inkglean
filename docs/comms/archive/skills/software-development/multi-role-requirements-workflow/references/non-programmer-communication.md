# 与非程序员用户对齐需求时的沟通模式

> 来源：v0.21 规划对齐会话（2026-08-01），用户原话："实际上我都看不太懂，四号和我交流时麻烦多解释一下。"

## 核心原则

1. **先人话后术语**：每个技术概念第一次出现时必须给现实比喻
   - Sentry = "给网站装报警器，客户遇到报错你第一时间收到通知"
   - Playwright = "雇一个机器人假装客户，自动把每个页面点一遍看有没有坏"
   - TypeScript = "给代码加错别字检查，写的时候就能发现传错参数"
   - 环境变量开关 = "监控摄像头——电源线插着就录，拔了就不录，不影响店里营业"

2. **每轮最多 2-3 个问题**，不甩 10 个决策项

3. **推荐式提问（选择题 > 填空题）**：
   - ✅ "Sentry 用免费版还是自己搭？我建议免费版——每月 5000 条够用，不用自己维护。你 OK 吗？"
   - ❌ "Sentry 你打算怎么部署？"

4. **每批问题后附决策汇总表**（已确认 ✅ / 待确认 ⏳），让用户随时知道进度

## 推荐第三方服务/新依赖时：主动覆盖三个顾虑

非程序员用户几乎必然产生以下顾虑。**不要等用户追问才解释，在推荐方案时主动覆盖：**

| 顾虑 | 用户原话示例 | 正确回应模式 |
|------|------------|------------|
| 法律/版权/许可 | "会不会有版权问题？" | 先一句话结论（"MIT 许可，零风险"），再解释 MIT 是什么 |
| 数据隐私 | "数据去哪了？" | 说清数据流向 + 给"介意/不介意"两条路（对比表） |
| 可拆卸性/锁定 | "不要了能拆掉吗？" | 用"开关"比喻：环境变量开=启用，删=消失，业务代码零残留 |

**回应格式**：先一句话结论 → 类比解释 → 对比表（用 vs 不用 / 方案 A vs B）。不要上来就讲技术细节。

## 分批提问节奏（实战验证）

v0.21 对齐用了两批：
- **第一批**（定方向）：优先级排序 + 方案选型 + 工程量范围
- **第二批**（定细节）：具体覆盖范围 + 具体模块选择

第一批有结论后再问第二批。不要跳级。

## 用户确认模式

<user>的确认方式极简：
- "可以" / "好的" / "采纳你的建议" = 确认
- 追问 = 有顾虑，必须解答到位再继续
- "这个提醒我们不是有qq机器人备案么" = 在问能否复用已有设施，要正面回答能不能 + 为什么
