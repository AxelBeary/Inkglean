# 多轮深入对齐 + 后台 UX 审计模式（2026-08-02 REQ-014 实战）

## 多轮深入对齐（Multi-round deep-dive）

当大功能有 6+ 个开放问题时，不要试图一轮解决：

1. **先呈现全部开放问题为表格**，每条附你的建议。用户扫一遍，挑想聊的，搁置不确定的。
2. **逐条：场景 → 选项 → 建议 → 确认。** 抽象功能（数据迁移、多设备同步）先画具体用户场景：
   > "画师小林用了两年，攒了 87 条记账、43 个委托文件夹共 12GB。有一天她换了新电脑……"
   然后给 2-3 个方案带利弊表，再给建议。用户确认或纠偏。
3. **每轮结束立即落盘。** 更新 REQ 文档 → commit → push → 报告变更。不攒批次。
4. **REQ 文档维护两张表**："已关闭问题"（附确认日期）和"开放问题"。跨会话时用户一眼看到进度。
5. **难度量化给非程序员**：用 ★ 分级 + 具体类比（"像是简化版 Canva" / "这就是在做一个小型 Figma"），不用抽象估时。让用户选档位，你填后果。
6. **状态同步 comms ≠ 审核请求**：规划期的深入对齐不进入开发，comms 文件明确标注"状态同步，无需审核/排期" + "不需要回复（除非你觉得有问题）"。不触发审核周期。

## 后台 UX 全面审计

当用户说"后台界面逻辑让我们优化"或报告具体困惑（"莫名其妙的接稿设置"）：

1. **先读完所有页面** — 路由表、每个 view、侧边栏菜单配置。不要从一张截图诊断。
2. **画完整清单表**（菜单项 → 路由 → 里面装了什么），让用户看到全貌。
3. **按"心智模型错位"诊断**：把每个字段/功能按用户心智分组（"我是谁" / "客户看到什么" / "系统怎么用"），然后展示当前 UI 哪里违反了分组。
4. **问题编号列表**（P1-P7），每条带用户感受原话，然后建议表格（你的建议加粗）。
5. **不实施** — 四号的活是诊断 + 建议 + 写 REQ。实施交一号排期。

## 关键教训

- 用户问"难度有多大"时，不要只回答"中等"——给档位让用户选。REQ-014 约稿条排版：用户听完 A/B/C 三档后秒选 A（"他们自己就是搞艺术"），比直接推荐 A 更有说服力。
- 用户说"这个我们把其他确定好了再展开"= 搁置，不是拒绝。标记为开放问题，不追问。
- 用户纠正你的事实错误时（"你还记得我们的码是建立在qq机器人的基础上吗"），立即承认 + 搜索代码验证 + 修正文档。不辩解。
- 用户说"好的"= 确认落盘。不需要再问"你确定吗"。直接写 → commit → push。
