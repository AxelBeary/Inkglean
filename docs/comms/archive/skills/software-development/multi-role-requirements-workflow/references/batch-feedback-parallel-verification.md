# 批量反馈并行核实技术

> 来源：REQ-013 整理（2026-08-01），9 条画师反馈的代码核实

## 何时用

反馈批次条目 ≥ 5 时，串行逐条读代码太慢（~15min/9条）。用 delegate_task 并行分组核实。

## 分组原则

按**功能域**分，不按条目编号分。同一组件/页面相关的条目放一组：

| 组 | 示例条目 | 共同点 |
|---|---|---|
| 模板渲染组 | #4 slotDisplay、#9 图片裁切、#10 档位三态 | 都涉及 Tpl* 组件 + 客户端渲染 |
| 仪表盘组 | #1 留言、#2 待处理、#3 按钮、#5 封面 | 都在 Dashboard/主页布局内 |
| 数据模型组 | #6 录单、#8 话术 | 都涉及后端 service + DB schema |

## 子任务 prompt 模板

```
核实拾绘项目中以下功能的代码现状，输出每条的：当前实现方式、关键文件路径+行号、与画师反馈的差距。

**#N 功能名**：
- 读 [具体文件路径]，找 [具体函数/变量/CSS类]
- 确认：[具体问题]

项目路径：[workspace路径]。技术栈：[前端框架+后端框架]。用中文回复。
```

**关键**：prompt 必须给出具体文件路径和函数名（从派工文件或已知信息提取），不能让子任务自己猜。子任务没有上下文，猜错率高。

## 实测数据

- 9 条反馈，3 路并行：~4min（含子任务启动开销）
- 串行逐条：预估 ~15min（每条约 1.5min 读代码+分析）
- 子任务数上限：当前配置 max_concurrent_children=3，不要超过

## 注意事项

- 子任务结果是 self-report，关键结论（如"4模板全部渲染"）需要抽查验证
- 子任务之间不能共享发现——如果条目之间有依赖（如 #4 的设置项影响 #10 的渲染），放同一组
- 条目 < 5 时不值得拆，直接串行
