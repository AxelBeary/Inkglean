# 引入第三方服务/SDK 的需求对齐要点（非程序员用户）

四号在整理涉及外部 SaaS / SDK / 云服务（Sentry、支付、地图、统计……）的需求时，非程序员用户几乎一定会问下面几类问题。**主动先答，别等用户追问**——用户追问时往往已经带着担忧。v0.21 Sentry 规划验证有效。

## 必答题清单

- **法律/版权/许可**："用了会不会有法律、版权、许可问题？"
  → 查许可证类型。MIT/Apache = 商用免费、零风险、不用开源自己代码；GPL = 有传染性，要警惕。直接给结论 + 一句人话解释。
- **数据去哪了/隐私**："数据传到哪？"
  → 说清是 SaaS（数据在对方服务器，可能出境）还是自建。给"介意 vs 不介意"两个方案对比表，并给推荐。
- **能不能模块化/拆掉**："不要的时候能拆掉吗？未来只留一部分功能时怎么办？"
  → 标准答案是**环境变量开关式设计**：设了 DSN/KEY 就启用，留空就完全禁用，业务代码零侵入。强调"不影响现有 Docker/构建/业务逻辑"。
- **要不要自建/进 Docker**：默认推荐 SaaS 免费版（零维护），除非有强数据合规要求。给"自建 vs SaaS"对比表。

把"开关式、不侵入业务、不碰现有体系"写进需求文档的**全局约束**章节，而不只是口头承诺。

## 用户现场注册第三方账号时

用户常一边聊天一边在第三方网站操作，把屏幕内容贴过来问"选哪个"。处理方式：

- **给明确的选项**，不要让用户自己判断（"选 Fastify"、"选 Vue"、"Alert 选 I'll create my own alerts later"）。
- **主动 dismissing 无关示例代码**：第三方站常贴一段示例代码，但版本/框架往往和项目不符（如 Sentry 给 Vue 2 写法但项目是 Vue 3）。明确告诉用户"这段示例不用管，DSN/密钥本身是通用的，实际接入由技术角色按项目写法来"。
- **只收集关键凭据**：让用户把 DSN/API key 发过来即可，其余配置是技术活。
- **凭据脱敏**：用户贴出完整 DSN/key 时，记录到文档时打码（`https://***@...`），不要明文落库。
- 用户完成操作后，立即把需求文档里"待用户操作"条目标记为 ✅ 已完成 + 日期，并 commit。

## 需求文档标准结构（工程基建/多功能类）

1. 背景 → 2. 用户已确认决策（表格：决策项/结论/确认日期）→ 3. 全局约束（适用所有项）→ 4-N. 每个功能独立章节（概述/需求明细表/验收标准表/前置条件）→ 排期建议（拆 PR）→ 待确认/待用户操作（谁做/状态）→ 风险与缓解。

每个功能的验收标准用"当……时，应该……"格式，且必须可测（含具体数字：30 秒内、退出码 0、零类型错误）。"明确不做"章节和"需求明细"同等重要。
