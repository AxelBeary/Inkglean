# 并行会话冲突与过期状态（四号必读）

多角色系统同时跑多个 Hermes 会话：一号在主 worktree 持续合入 master、维护 STATUS；四号也直接在 master 上改文档。两类事故反复发生（2026-08-03/04 共 4 次）。

## 1. 过期状态（写文档前必查）

- 症状：用户说"我们现在在新版本了，要写文件别在老文件改哦"；或基于两轮前读的 STATUS 写文档，实际一号已派新工/合了新代码。
- 配方（每个涉及写文档的新用户轮次开头）：
  1. `git fetch origin && git log --oneline -5 origin/master`
  2. 读最新 `docs/comms/STATUS.md` + `git ls-files docs/comms/` 看在途派工
  3. 基于最新 tip 写，不信任记忆里的版本状态

## 2. sibling 写冲突（write_file 返回 "modified by sibling subagent" 警告）

- 含义：文件在你上次读取后被并行会话改过，你的写入**已覆盖**那份改动。
- 处理（不能无视警告）：
  1. `git log --oneline -3 -- <file>` 看 sibling 是否已提交
  2. 已提交 → `git show <hash> -- <file>` 读它的 diff
  3. 合并：保留 sibling 内容（尤其一号的审核/处置状态字段）+ 叠加你的新内容；若误覆盖，立即 patch 恢复
  4. commit message 写明合并了什么
- 实例（2026-08-04）：四号重写 REQ-024 覆盖了一号并发提交的"审核通过+showcase 拍板"；靠警告发现，git show 读一号改动后合并进状态字段（F1-F5 已审/F6 新增待审），comms 写清时间线。SPEC-025 同款，误覆盖"已由一号处置"节后再 patch 恢复。

## 3. 拍板变更发生在审核被消费之后

- 用户新拍板推翻一号已消费（已审核/已派工）的旧拍板时：
  1. REQ 正文全量同步（功能描述/验收标准/用户原声/已确认事项），一次提交不留遗漏引用
  2. comms 写时间线：一号何时基于什么原话拍板 → 用户何时改为什么原话 → 最终结论以新为准
  3. 给一号只留 1 个决策项（通常是排期），不让它重审全文
- 实例：REQ-024 showcase"直接迁不提示"（一号据用户原话"不提示 我们测试环境无所谓"拍板）→ 用户后改"选乙丢弃"+新增 F6。

## 4. 内部解决原则（用户明说）

- 用户原话："一号太忙了 我们能内部解决的讨论别交给他"。
- 判断标准：
  - **技术事实问题**（代码行为/字段存在性/兜底逻辑）→ 四号自己读代码定案，写结论+证据行号，不转三号
  - **用户拍板问题**（留/丢/提示与否）→ 直接问用户，不经一号中转
  - **只有范围/排期/跨角色冲突** → 上交一号
- 实例：历史订单档位显示原标"待三号确认"，四号读代码核实 ON DELETE SET NULL + TrackOrder `tierName || '定制'` 兜底 + quote_snapshot 存价后直接定案写入 REQ。
