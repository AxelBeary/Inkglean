# 四号工作流补充经验（2026-08-02 会话）

## patch 工具 Windows 路径陷阱

V4A patch 模式（`*** Update File: path`）在 Windows 上**必须用绝对路径**。
相对路径（如 `README.md`）会静默失败：报 "File not found" 但工具不报错退出，
改动丢失且不易察觉。单文件 replace 模式的 `path` 参数同理。

**检测方法**：改完后立即跑 `git diff --stat` 或 `git status --short`，
确认目标文件出现在修改列表中。

## 截图驱动的需求重分析

用户发仪表盘截图后，#3 按钮自定义的分析从"要不要做"变成了
"6 个按钮中 5 个和侧边栏重复"——截图暴露了纯代码阅读看不到的 UX 问题
（命名不一致："图库管理" vs 侧边栏"作品管理"）。

**规则**：收到截图时，对照截图重新检查每条已有结论。
截图是用户视角的真实画面，比代码结构更能暴露体验问题。

## 文档维护审计工作流

一号会周期性派"文档维护"任务。标准流程：

1. 读 STATUS.md 获取最新测试数/版本号/迁移号（这是 ground truth）
2. 派子任务并行检查 soul 文件（找过时描述）和 changelog/specs/requirements（找状态滞后）
3. 用 `git log --oneline --since=... --until=...` 还原缺失的 changelog 条目
4. 批量 patch（**绝对路径！**）
5. 一次 commit（`docs: 文档维护——{具体改了什么}`）
6. 写 comms 简述改了什么（表格：文件 / 改了什么）

注意：
- changelog 从 git log 还原时个别日期可能有一天偏差（标的是 commit 日期）
- 不移动文件到 archive/（只标归档状态，避免链接失效）
- 不确定的数据标"待确认"，不猜

## 需求讨论中的选项呈现

用户（非程序员）对抽象描述（"规划""信息架构"）理解困难。
有效做法：先读代码，用 ASCII 图/表格展示具体结构，再给 2-3 个选项 + 利弊对比表。
用户说"你说的'规划'我不是很懂"后，改为展示设置页的实际结构树 + 两个方案对比表，
用户立刻拍板。

**规则**：每轮最多问 3 个问题。每个问题给具体选项（A/B/C），附一句话利弊。
不用抽象术语，用"你打开XX页面会看到XX"的具象描述。
