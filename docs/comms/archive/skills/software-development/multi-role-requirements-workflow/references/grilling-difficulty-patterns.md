# 难度/可行性批量追问的应对模式

用户经常一次抛出多个"这个难度有多大？"——这不是要工时估算，而是要**做产品决策的信息**。

## 有效回应模式

1. **分档呈现**（A/B/C 或 ★ 评级），每档用用户能"看见"的语言描述体验差异，不用技术术语
2. **每档给明确推荐**——"我建议 A，因为……"，用户拍板效率极高（原话模式："你说的对！A档性价比最高"）
3. **技术实现一句话带过**，放在引用块里，不展开。用户不需要知道 Konva.js 是什么
4. **追问使用场景而非技术偏好**——"画师是每次都要全新设计，还是改改就行？"比"你要 Canvas 还是 DOM？"有效一百倍
5. **批量回复末尾放决策汇总表**——每条标注 ✅已拍板 / ⏸搁置 / 待确认，用户一眼扫完

## 搜索纪律：宣称"X 不存在"之前

教训（2026-08-02）：四号宣称"发码机制不存在"，只搜了 server/src 代码。实际上 QQ Bot 发码在 `docs/开发→生产切换指南.md` Phase 2 章节有完整描述（BOT_WS_URL、NapCat、OneBot 11 协议），只是尚未实现。用户纠正："你还记得我们的码是建立在qq机器人的基础上吗"。

**搜索顺序**：
1. `docs/*.md`（设计文档、切换指南、开发自参考、CONTEXT.md）
2. `server/src/**`
3. `web/src/**`
4. 配置文件（.env.example、docker-compose.yml）

已设计未实现 ≠ 不存在。文档里有的就是"已规划"，不能对用户说"不存在"。

## 用户决策风格观察

- 用户倾向性价比最高的方案（"A档多几个模板性价比感觉最高"）
- 对"保留但不优先"的辅助功能接受度高（"保留手绘签字功能吗？"→ 保留，低优先）
- 技术细节完全信任四号判断（"这个我不太懂"→ 直接用大白话给结论）
- 一次拍多条，不逐条磨（6 个问题一次全回）
