# 评估分流 + 外部干系人反馈（2026-08-01 会话总结）

## 评估分流（Evaluate-before-spec）

当一号派工"展开评估 X/Y/Z"时，**先验证代码实现状态，再决定写什么**。

### 流程

1. **并行代码验证**：用 delegate_task 批量派子任务检查每项的代码实现状态（路由是否存在、前端页面是否存在、关键函数是否实现）
2. **分流**：
   - ✅ 已完整实现 → 写"已实现确认"spec（记录验证证据 + 建议从候选清单移除），不写设计
   - ⚠️ 部分实现 → 写差距分析 + 剩余工时
   - ❌ 未实现 → 写正式 spec（数据模型 + API + 前端 + 验收标准 + 工时）
3. **一次提交**：所有 spec 文件 + comms 回复一个 commit

### 陷阱

- ❌ 不验证代码就写 spec → 可能给已实现的功能写"待开发"设计（B5/B6 教训：系统自检和 SPEC-002 §八 都已完整实现，代码验证后确认无需排期）
- ❌ 因为"已实现"就跳过不写文件 → 仍需写确认文件作为验证记录，一号需要证据
- 验证方法：search_files 搜关键文件名/函数名 + delegate_task 并行读代码确认

### 实例（B5/B6/B7 评估）

| 项 | 代码验证结果 | 产出 |
|---|---|---|
| B5 系统自检 | health.routes.js + health.service.js + HealthCheck.vue 全部存在 | 确认文件，建议移除候选 |
| B6 SPEC-002 §八 | 4 个拍板项逐行验证全部已实施 | 确认文件，建议移除候选 |
| B7 额度池 | orders 表无 paid_total_cents，无收款 API | 正式 spec（~13h） |

## 外部干系人反馈处理

当用户转达外部人员（画师、客户等）的需求反馈时：

### 流程

1. **能力对照表**：逐条对照现有平台能力，标注 ✅已有 / ⚠️部分 / ❌没有 / 🚫超出产品边界
2. **判断分类**：
   - 平台已解决（用户没用起来）→ 不是新需求，标"已有"
   - 平台内可做的新功能 → 正常 REQ 流程
   - 超出产品技术边界（如 Web 做本地文件管理）→ **产品方向问题**，标"待用户拍板"，不自己定
   - 用户已明确不做的 → 备案，标"用户已拍不做"
3. **澄清问题**：如果反馈模糊，拟问题清单给用户转达（见 requirements-grilling 的外部干系人变体）
4. **落文档**：写 REQ 文件，每条标注澄清结果 + 判断 + 行动项

### 陷阱

- ❌ 把外部人员的原声直接当需求写 → 必须先对照现有能力，很多"需求"平台已经有了
- ❌ 自己拍产品方向（如"要不要做桌面端"）→ 这是用户决策，四号只给选项和建议
- ❌ 一次问外部人员太多问题 → 通过用户转达的问题要精简，"挑能说的说就行"
- 产品方向讨论时：给选项 + 建议 + 理由，让用户拍。用户拍板后逐字落文档标日期。

### 实例（REQ-012 画师工具需求）

画师 6 条需求澄清后：
- 2 条平台已有（防错漏、约稿收款）→ 不是新需求
- 1 条用户已拍不做（时间统计）→ 备案
- 1 条待拍板（个人记账）→ 用户倾向不做
- 1 条真正新需求（排期日历视图）→ 可排期
- 1 条超出 Web 边界（本地文件管理）→ 产品方向问题，用户拍板"未来考虑桌面端伴侣应用"
