# 文档维护与 REQ 归档（四号）

> 派工形态：一号派文档维护单（docs 低风险，四号直接 master 提交，commit message `docs: 文档维护——{具体改了什么}`）。
> 授权范围 README.md + docs/；不改代码文件；不碰 docs/comms/STATUS.md（一号维护）。
> 交付：做完聊天里说一声即可，纯文档通常不写 comms。

## 硬坑：git mv 不 stage 内容修改（2026-08-03 实战踩中）

**事故序列**：patch 改文件内容（工作区未暂存）→ git mv 归档 → commit。
**结果**：commit 输出显示 `rename ... (100%)`——内容修改没进 commit，留在工作区。
git mv 以 index（HEAD）内容 stage 改名，不会捎带工作区的内容修改。

- **检测**：commit 输出里 `rename "a" => "b" (100%)` 而你改过内容 = 修改丢了
- **验证**：commit 后跑 `git status --short`，看到 `RM`（R 已暂存改名 / M 工作区有修改）= 内容未提交
- **补救**：`git add <目标目录>` + 补一次 commit（message 用"补……"说明）
- **预防（推荐）**：先 git mv，再在新路径下 patch 内容，最后一次 `git add` + commit

## 硬坑：占位备案随父 REQ 沉入 archive——需求搜索必须覆盖归档区（2026-08-05 实战）

**事故**：用户问"系统对画师定制单文件 HTML 的兼容性"，四号只搜活跃区
（docs/requirements/ + server 代码），得出"功能不存在、之前没记下来"的错误结论。
用户纠正后才查到：2026-07-30 已备过占位备案，藏在已归档的
`docs/archive/requirements/REQ-009-主页定制第一层.md` 尾部"占位备案"节——
父 REQ 主体（头像+取色+预览）完成归档时，未展开的占位段被一起带走了。

**规则**：
- 判断"某需求是否记录过/讨论过"时，搜索范围必须含 `docs/archive/requirements/`：
  `rg` 对 docs 全目录搜，不要只限定 `docs/requirements`
- 用户口头提及"之前聊过 X"而活跃区搜不到时，**结论不能是"没记下来"**，
  先搜 archive + `git log --all --grep` 再下结论
- 归档父 REQ 前检查尾部是否有未展开的占位备案段；有则先提升为独立
  REQ 占位稿（如 REQ-030 形态）再归档，或在待修复清单/STATUS 留指针——
  占位备案不随父 REQ 归档消失

## REQ 实施状态核实方法（归档前置，禁止凭猜）

逐 REQ 按序核实：

1. `git log --oneline --all | Select-String "REQ-0xx"` —— 找带 REQ 标签的 feat/merge commit
2. 关键词 grep（中文功能词，如 "加钱|主图|增项|回收站"）——部分实现不带 REQ 标签，
   甚至功能早已存在（实例：REQ-021 F5 增项点击编辑、F6 作品主图实为既有能力，靠代码核实确认）
3. 代码验证：`git grep` UI 文案 / 组件名 / 迁移号，确认功能真在 master 上
4. `git show <旧commit>:docs/comms/STATUS.md` 读历史合入清单（当前 STATUS 只保留最新版本信息）
5. `git log -S "标识符"` / `git blame -L` 定位某行/某函数引入时点，判断"是否顺带实现"
6. 注意区分：`--all` 搜到的 commit 未必在 master 上，最终以 master 线性历史为准

状态行写法（归档时更新文件头部状态行，附 commit 号与关键备注）：

- ✅ 已实施 → `git mv` 到 `docs/archive/requirements/`；状态行含版本 + commit 号 + 偏差备注
  （实例："F2 修改加钱实为设计缺口，按方案A实现为改价按钮"——忠实记录与需求的偏差，不粉饰）
- 🟡 部分实施 → 留原地，状态行逐条列已做/未做的 F 项及依据
- 🟡 规划中/未启动 → 留原地，不改动

归档前跑 `git grep -rn "requirements/REQ-0xx"` 确认无文档路径引用（防断链）。

## docs 归档盘点清单（只盘点不动文件的派工形态，2026-08-05 实战）

一号可能派"盘点 docs/ 顶层，出归档清单但不移动文件"。交付报告里用五段结构：

1. **建议移 `docs/archive/requirements/`**：已全量实施的 REQ（核实方法见上节）
2. **建议移 `docs/archive/specs-done/`**：已收口的 spec/plan。注意：spec 里若有
   ⚠️ 未覆盖/待跟进条目，建议"先转待修复清单再归档"，写进清单让一号定
3. **建议保留**：长期在用文件（CONTEXT/待修复清单/changelog/三份用户文档），一句话理由
4. **建议保留但标注状态**：未来版本的输入材料（如 v0.38 视觉重设计的设计书/视觉规范/
   提案 HTML/审计截图基线）——标注"vX 前保留"；以及已消费但含未决项的反馈汇总
5. **待一号决定项**：明确列出需要拍板的点

**硬坑：反馈汇总类文件归档前查未决项落点**——体验反馈汇总（如 feedback-20260802）
通常 A/B 类已修完，但"待详细商讨"类条目（如 #56）、小工具集清单、技术债清单可能
从未落入STATUS 待办池。`search_files` 在待修复清单里 grep 这些关键词，搜不到 =
未决项无落点，归档会丢需求——必须在清单里标出"建议未决项先转待修复清单再归档，
或继续保留"，交一号拍板，不自己决定。

  （实例：列 server/src 顶层文件确认"TS 迁移剩余入口"描述仍准确，不改）
