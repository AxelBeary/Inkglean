# 执行手册 / 测试剧本类文档派工（A 测执行手册等）

> 2026-08-05 实战：四号产出 `（A测已结束，手册已删——A测反馈经五号排查/四号整理 REQ）`（A 测首轮真实画师测试）。派工铁律与四段式结构在此固化，下次同类派工（验收手册/操作指南/回归剧本）直接套用。

## 触发条件

- 一号派工文件里出现「执行手册」「测试剧本」「检查单」等词，交付物是**单文件 docs/xxx手册.md**。
- 典型铁律（派工原文）：纯文档零代码零配置改动；引用的每个现状断言读代码/读 STATUS 实锤；不写未合入的功能；commit 到分支 + 交付报告 `docs/comms/04-to-01-*.md`；不推送不合并。

## 四段式手册结构（A 测类派工默认骨架）

1. **测试剧本**：真实用户从 0 到 1 全链路，按场景分组（前置准备/账号与登录/资料设置/开稿与价格/接单/工作流推进/收款/交付/客户侧/视觉反馈）。**每步三要素：操作 → 预期 → 记录位**。预期必须可验证（「提示已绑定动态口令；列表该行出现重新绑定」✓，「体验要好」✗）。
2. **环境开关检查单**（如 AUTH_DEV_MODE 关闭）：前置条件逐项核对（含已完成项标注日期+实跑来源）→ 可执行步骤（含验证方法，如 DevTools 看响应体无 `_dev_secret`）→ 回滚路径。
3. **反馈收集模板**：反馈单四段格式（操作场景/发生了什么/期望/严重程度）+ 归档流程（🔴🟡→五号排查→Bug 进待修复清单/缺失进 REQ；🟢💡→四号收集对照 REQ 池）。
4. **已知限制清单**：逐条标注来源（代码/git log/STATUS/REQ），测前告知防误报。

## 实锤纪律（本批踩过的坑）

### 1. 并行 worktree 合入状态必须先 git log 核实
同一仓库常有多路并行分支（f1f2-frontend / addons / polish）**未必已入 master**。写手册前：
```
git log --oneline -15 --all | Select-Object -First 15   # 看各分支最新提交
git branch -a
```
- 本批实况：F1 后端（publish-artwork API）已合入 master，但 **F1 前端入口 + F2 全部在 f1f2-frontend 分支未入 master**。
- 处置：相关步骤标注「若已合入」条件（如「若已合入（F1 前端批）：画师点发布为作品」），未合入则跳过并在反馈单注明「未测（功能未合入）」；已知限制清单加对应条目。
- 判定依据写进交付报告（含合入 commit 号），证明不是拍脑袋。

### 2. 已有用户文档可能过时——不引用，按代码现状重写
本批发现 `docs/画师使用说明书.md` 标注 v0.36，但登录码机制已随 REQ-027 移除、手动录单旧档位模型已被 REQ-029 新画风模式取代。**手册不引用过时描述**；过时文档的更新建议单独写入交付报告转一号排期（四号无权改技术文档，但有权提出）。

### 3. `.env` 不在 worktree（被 gitignore），现状以 STATUS/维护说明书为准
查 AUTH_DEV_MODE 等环境配置时：`Test-Path .env` 为 False 是常态，生产值在服务器。以 STATUS 已拍板规则、待修复清单 H1、维护说明书为事实来源，不假设 worktree 有 .env。

### 4. 摸底顺序：路由清单 → 关键段落 → 前端页面 → REQ 文档
- 后端：`search_files` 抓 `fastify.(get|post|put|delete)\(` 列出全部接口 → 按需读关键段落（收款/交付/手动录单/工作流）。
- 前端：router/index.js 的路由表一份就能确定所有页面路径与命名。
- 已有说明书（画师使用说明书）快速通读建立操作全景，再对照代码修正过时点。
- REQ 文档（REQ-022 F2 外链规则/REQ-025 动态计价）补齐「若已合入」章节细节。

## 变体：已有用户文档版本同步批（说明书更新类，2026-08-05 第二批实战）

与「从零写手册」同属文档派工，但交付物是**修订版用户文档**而非新手册。触发词：派工「更新 `docs/xxx.md` 至 vX 现状」。

### 与本批的差异点

- 任务 = 逐条对照代码现状修订过时章节 + 更新版本标注（v0.36 → v0.39），**未改章节也要逐条核实并写明"已对齐无漂移"**。
- 交付报告特有内容：**改动章节清单**（表）+ **过时点对照表**（旧文 → 现状 → 实锤来源，本次 6 条）——每个改动点都必须能追溯到代码/REQ/STATUS。

### 开工顺序

1. `git merge master`（派工要求；本次 fast-forward 到 e60144d）。
2. **合入状态核实，与手册批同法但注意方向可能反转**：第一批时 F1/F2 未入 master（写"若已合入"条件）；第二批时**已合入**（e7d3c35），此时要核实新交互的**实际字段**而不是假设：
   - `Settings.vue` F2 链接编辑器：保存只传 `customLinks` 新结构 `[{platformId, url}]`，上限 `MAX_LINK_COUNT = 8`（来自 `linkValidation.js`），platformId 只读（后端重推导）。
   - `OrderDetail.vue` publishArtwork：仅 delivered 显示入口；勾图+标题；一图一作品。
   - `ManualOrder.vue` isStyleMode：画风→尺寸→增项三级选择 + 自定义单提示。
3. **用户文档里的导航分组描述必须有代码依据**：说明书引用侧边栏「门面/经营/工作」分组 → 核实 `ArtistLayout.vue` 菜单数组（group: work/biz/front）。

### 全量重写保全（write_file 警告）

整文件重写时 write_file 会警告"partial view"。处置：重写前用 `git show HEAD:路径` 核对原文件尾部/未读段落（本次 FAQ 焦点图答句原文与记忆不同——原句"从参考图里选一张"已过时，现可从订单图库任意图设焦点图），重写后 `git diff 路径` 逐块核对改动点与派工任务一一对应，防止误删内容。改动量小（36+/16-）不等于覆盖全——靠 diff 验收，不靠自我感觉。

## 交付报告模板要点

交付物 → 内容结构（四段式各一段说明）→ 实锤纪律（列出读了哪些文件、合入状态判定）→ 涉及角色 → 验收标准（每条「当……时，应该……」格式）→ 优先级 → 待确认问题 → 申请（请一号审核）。发现的其他文档问题（如说明书过时）放「待确认问题/建议」转排期，不夹带在手册正文。
