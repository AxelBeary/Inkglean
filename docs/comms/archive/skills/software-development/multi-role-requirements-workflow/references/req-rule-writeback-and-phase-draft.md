# 用户拍板写入 REQ + 分阶段实施草案（四号 REQ 文档轮）

> 派工形态：用户拍板新规则/新状态语义后，一号派「REQ 文档轮」——把决策写入既有 REQ 文档成正式条款，
> 并产出分阶段实施方案草案（供一号终审，不直接实施）。
> 低风险纯 docs，worktree 分支 v0xx-*-spec，授权通常仅 REQ 文档一个文件。交付报告写 comms 转交一号。

## 决策写入条款配方

1. **先对齐**：读 STATUS.md 里已落库的裁决/拍板原文，措辞与派工文件交叉核对；
   写入条款不得与已有裁决矛盾，且要把散落在 comms/STATUS 的裁决同步进 REQ（REQ 自包含）
2. 新增条款（如 R13）结构：
   - **规则出典**：用户场景原文逐字保留（不改写不概括）
   - 状态/概念定义表（如 状态 × 终态级别 × 能力）
   - 操作白名单/黑名单（✅/❌ 列表）
   - 与既有规则交叉引用（"按 R5/R9 冲抵"、"即 R10 语义"）——新规则不孤岛
   - 实施时序/裁决原文落条款（含先后顺序约束，如"守卫必须与负条目机制一起上线"）
3. **同步修订三处**（漏一处文档自相矛盾）：
   - 边界案例：延续已有编号案例（案例 1 的订单走到新状态继续推演），带守恒验证 +
     与既有条款触发场景的语义区别说明
   - 验收标准：新增一条（"当……应该……"格式，同时覆盖允许项 + 禁止项 + 跨状态对照）
   - 文档头状态行：补"✅ X 用户拍板写入（日期，见 Rxx）"
4. 实施映射节加「待放开/待补强点」小节：挡路的 schema 约束（文件+行）+
   缺失的后端守卫（行+现状），每条附代码实锤

## 端点清单自查配方（行号实锤，不凭印象）

1. 定位函数定义：search_files 正则 `^export function (fn1|fn2|...)` 拿定义行号
2. 逐个读函数体：记守卫/校验/写路径现状（拦了哪些状态、漏了哪些）
3. 表格格式：# | 现有入口（文件+行号）| 代码现状（行号实锤）| 改造
4. **审计中发现派工没提的问题 = 最大价值**：如 deleteExtraItem 零状态守卫、
   撤销收款无独立端点（现状即负数流水）、同名组件实为另一物（PaymentBar 是比例编辑器
   不是收款进度展示）——逐条写进草案并在交付报告单列
5. 依赖模块未交付（如引擎纯函数签名）→ 接口用占位符 `〈引擎.xxx()〉`，
   草案头部注明"待合入后终审补实"。绝不编造签名

## 防虚假声明

- 验收标准 → 阶段归属映射表中，✅ 含义是"该条由此阶段范围覆盖"，非"已通过"——
  阶段仍在开发时必须加脚注说明（事实验证原则）
- 所有行号标注"YYYY-MM-DD 自查于 master@hash，实施时以当时代码为准"
- commit 格式 `docs(req): ...`；交付报告必含：新增章节清单 + 行号依据表 +
  「对齐项」节（与 STATUS.md 裁决逐条对应）
