# 四号扩展工作流（2026-08-01 会话总结）

## 外部反馈处理工作流

收到外部用户/画师反馈（非内部角色派工）时：

### 1. 现状盘点（先做，再提问）
逐条对照现有功能，输出覆盖表：
| 用户要的 | 现有覆盖 | 差距 |
|----------|---------|------|
| X | ✅/⚠️/❌ | 具体差什么 |

超出产品形态的需求（如 Web 做本地文件管理）标"架构级差异"，不混入功能追问。

### 2. 拟问题清单（一次给完）
- 只问盘点后真正有歧义的项
- 每题给选项（A/B/C），降低回答门槛
- 告诉用户"不用每条都答，挑能说的说"

### 3. 拍板落文档
- 用户拍板后**即时更新文档 + commit + push**
- 原话逐字记录（尤其是带情绪的决策，如"才不我们给他做这种鬼东西"）
- 决策表标 ✅/🚫 + 日期 + 结论

### 4. 备案 vs 展开
- 用户说"先记下来"→ 占位备案（REQ 文件 + 待排期标注），不展开 spec
- 用户说"展开"→ 走正式 spec 流程

## 跨角色 spec 更新工作流

收到三号/二号技术确认（T1-T5 等）后更新 spec：

1. **状态行**：改为"已确认，可排期"
2. **逐节更新**：按派工要求逐节改（§8 待确认→已确认、§2.4 补发现、§3.3 补调用点、§5 补约束、§9 工时修正、§10 风险更新）
3. **工时修正**：技术确认经常降低工时（如"本来就没耦合"→省 1h），必须更新并注明原因
4. **BUG 发现**：技术确认中发现的现有 BUG 写入风险表（🔴）+ 验收标准 + 排期首要项
5. **comms 回复**：只写结论和待确认项，不重复 spec 内容

## 排期文档结构

`plan-vXXX-schedule.md` 标准结构：
1. 范围表（项/工时/来源/状态）
2. 优先级 + 理由
3. 波次并行策略表（阶段/三号/二号/说明）
4. 关键路径（ASCII 图）
5. 依赖与风险
6. 不在本版本的项（明确排除）
7. 待一号确认项

## 已实现确认的 spec 写法

B5/B6 评估发现功能已实现时，spec 不是空白——写"已实现确认"：
- 代码验证表（文件 + 行号 + 状态）
- 与原始需求的逐项对比
- 建议：从候选清单移除
- 这类 spec 的价值是**留下验证记录**，避免下次又有人问"这个做了没"

## 并行代码调研模式

需要评估多个独立功能时，用 delegate_task 并行派 3 个子任务：
- 每个子任务只查一个功能的代码现状
- 返回简洁结论表（不返回大段代码）
- 主线程等结果后统一写 spec
