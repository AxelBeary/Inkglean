# 交互直觉审计（UX audit，四号执行）

触发：用户问"哪些操作不够好/不够直觉/不顺手"。产出要求：**每条发现带 file:line 证据**，不写主观抱怨。

## 方法（2026-08-04 REQ-024 审计实证，4 项发现全部被采纳）

1. **盘点高频操作页面**逐个读源码：管理后台 CRUD 页、列表/筛选、看板、详情页、下单流程。别只读一个页面就下结论。
2. **五个交叉核对维度**（本次 4 项发现的出处）：
   - **后端能力 vs 前端实现**：后端已有排序/字段 API（如 sort_order update），前端有没有对应交互？没有 = 能力悬空（发现 #1 画风无法排序）
   - **需求动线 vs 实现入口**：SPEC/REQ 里写的用户动线，代码里每一步都有入口吗？（发现 #2 动线 5"加新料→导入画风"在已有画风上断头：importAddons 只在新建弹窗 `v-if="!editingStyleId"`）
   - **同界面保存/提交心智是否一致**：一个卡片里混用"手动保存按钮/行内保存/即时保存"= 心智断裂（发现 #3）；对照项目已确立的模式（如 v0.34 上传即时保存原则）
   - **数据模型枚举 vs UI 枚举**：DB CHECK 约束/状态枚举与筛选条、下拉选项是否对齐？（发现 #4 订单 7 态筛选条只 6 档）
   - **命名一致性**：不同 tab/页面同名不同物（旧"增项"tab 内左列也叫"增项库"，与独立"增项库"tab 撞名）
3. **每条发现的格式**：问题一句话 + 代码证据（文件+行号/SQL 片段）+ 影响（断哪条动线/坑谁）+ 建议归属（并入在途批次 or 小修）。
4. **落盘三件套**：① `STATUS.md 待办池` 加一节表格（#/问题/证据/归属）② 相关 SPEC/REQ 内纠错或补勘误（本次发现 SPEC-025 自己写错"拖拽排序现状已有"，当场勘误）③ comms 转交一号，建议能并入在途批次的明确说"边际成本低"。
5. **自纠优先**：审计发现自己此前文档的错误断言，当场在文档里加勘误并说明核实方式——事实验证原则的现场执行。

## 反模式

- ❌ 只看截图/凭印象说"这里不好用"——必须读代码确认是缺失、断裂还是设计如此
- ❌ 把视觉问题混进交互审计——视觉归设计批次（纸墨颜料盘），本审计只管操作逻辑
- ❌ 发现即要求立即修——按"并入在途批次 / 排小修"分级，派工归一号
