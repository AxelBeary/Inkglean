# REQ 交付前：与在途任务的撞车检查（四号）

> 教训日期：2026-08-03（REQ-024 画风档位统一）
> 时机：REQ 文档写完、提交一号审核**之前**。

## 为什么

多角色并行开发下，新需求很可能与一号已派工的在途任务动同一批文件/组件。
四号若只交需求文档不提撞车，一号排期时可能并行派工，导致同区域返工或合并冲突。
**四号不排期，但必须交付撞车分析——排期决策是一号的，撞车信息是四号的。**

## 操作清单

1. 交付前重读 `docs/comms/STATUS.md`（与"写 spec/排期前读最新 STATUS"同一纪律）。
2. 逐条找在途任务与新 REQ 各 F 项的交集：同组件、同文件、同交互区域、同 API/表。
3. 在 comms 转交文件（`04-to-01-*.md`）里加"与在途任务的重叠"表：
   `| 重叠点 | 在途任务（谁/任务号） | 新 REQ 项 | 建议 |`
4. 建议的常见形态：
   - **在途任务是新需求的子集** → 在途照做，新需求在其上补增量（例：二号任务B的 query 预选是 REQ-024 F4 的子集 → B 照做，F4 补"入口区分 + 跳第三步"）
   - **在途是局部修补、新需求是同区域重构** → 建议新需求排在在途合入后的版本，避免返工（例：任务C 封面 contain 修补 vs F3 展示柜交互重构）
   - **相邻但不冲突**（如同类上传 UX）→ 标注"可沿用同一模式"供实施方参考
5. 建议收口一句："新 REQ 整体排 vX 或之后，不与在途批次并行抢同一批文件。"

## 反模式

- ❌ 发现撞车后自己改需求文档迁就在途任务——四号不改排期，把撞车摆出来给一号裁
- ❌ 只在聊天里口头提撞车——必须写进 comms 转交文件（写下来才算交付）
- ❌ 拿记忆里的旧 STATUS 比对——交付前必须重读最新 STATUS.md（在途状态一轮一变）
