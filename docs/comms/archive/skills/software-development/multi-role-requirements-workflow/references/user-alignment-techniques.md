# 用户对齐交流技巧（拷问/拍板环节）

来源：REQ-013 整理（2026-08-01）。与 requirements-grilling skill 配合使用（该 skill 为手动维护，本文件作为补充）。

## 用户说"不懂"时：读代码画现状图

用户（非程序员）对抽象词（"规划""信息架构""逻辑关系"）没有画面感。当用户说"你说的XX我不是很懂"时：

1. **读实际代码**，搞清当前 UI 的真实结构（页面有几个标签/区块、目标功能排在第几位）
2. **画 ASCII 结构树**把现状摆出来，⭐ 标出痛点的具体位置：
   ```
   设置页
   ├── 基本资料
   │   ├── 头像 / 名字 / 简介 …（前 9 项）
   │   └── ⭐ 名额开关 ← 第 10 项，要滑很久才看到
   ├── 主页模板 ← 用户直觉会来这里找，但只有视觉设置
   ```
3. **用位置说话**："不是没有功能，是藏在第 10 项；用户直觉去找的地方没有"
4. 现状图建立共同认知后再给方案选项——此时用户拍板极快

> 实战（REQ-013 #4）：用户说"你说的'规划'我不是很懂"→ 画出设置页结构树 + 指出名额开关位置 → 用户立刻理解并拍板"独立成'接稿设置'标签页"。

## 方案拍板：mockup + 取舍表 + 直接问

需要用户在多个方案间拍板时：

1. **每个方案给具体画面**——ASCII mockup 或"改完后你会看到XX"，不给抽象描述
2. **一张取舍表**列全部方案 × 好处/坏处/结论（✅/⚠️/❌），推荐项标出来并给理由
3. **结尾直接问**："我建议X。你选A还是B？"——决策项一次摆全（用户偏好"你整个出来我一起看"），拍板很快
4. **用户自提的想法认真接住**：用户会中途抛自己的方案（"像横幅一样左右滑动？""像小标签切换？"）——逐个分析优劣，提取合理内核合并进最终方案。用户的直觉/隐喻描述往往方向正确，需要翻译成可实现的设计，不是驳回
5. **用户说"之后好好探讨"** = 话题超出本批范围 → 记入需求文档"后续专项备案"表，不硬塞当前批次也不丢失

## 反模式

- ❌ 用抽象规划词提方案——"我们得规划一下信息架构" → 用户原话"你说的'规划'我不是很懂"。应该说"现在长这样（画结构图），问题在第N项，我建议挪到这里"
- ❌ 只给推荐不给选项，或选项不给画面——没有 mockup 的选项等于没选项
- ❌ 驳回用户自提方案——先分析优劣再合并，用户抛方案是参与设计不是添乱
