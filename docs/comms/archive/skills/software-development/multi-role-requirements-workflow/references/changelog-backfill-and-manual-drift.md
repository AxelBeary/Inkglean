# Changelog 补全与说明书漂移修复（四号文档轮）

> 派工形态：版本收口后一号派「文档轮」——changelog 补缺失版本段 + 用户说明书漂移修复。
> 低风险纯 docs，worktree + v0xx-docs 分支，授权通常仅两个文件（changelog.md + 说明书）。
> 交付报告写 docs/comms/ 转交一号（区别于"聊天说一声"的常规文档维护，此形态必写交付报告，
> 因为验收要求"每条修正附依据"）。

## 铁律：派工素材与代码不符时，一律以代码为准

派工素材是一号整理的二手清单，可能有记忆偏差。每条写入 changelog 前必须对代码/commit 核实。
实战踩中两处（v0.36 轮）：
- 派工写时间条四档缩放"月/季/半年/年"，代码实锤 2w/1m/3m/6m，UI 文案「两周/一个月/三个月/半年」
- 派工写拖拽守卫"7 处"，grep 实锤 8 处挂载点（6 个文件）——changelog 改用"全部图片上传区"表述，不写死数字

发现偏差的处理：行文按代码写 + 交付报告单列「与派工素材的偏差（以代码实锤为准）」一节，
让一号知情。不静默照抄派工素材。

## Changelog 补全配方

1. `git log --oneline -40` 确认本版本各分支 merge commit（一号通常给 hash 清单，逐个验证存在）
2. `git show <hash> --stat` 看改动范围 → `git show <hash> -- <文件>` 读关键 diff，提取用户可感知行为
3. 行文按 changelog 既有格式（✨功能/🐛修复/🗄迁移/📊测试 分节，加粗标题 + 一句话说清
   用户可感知的变化），不照抄派工素材
4. 测试数字用 STATUS.md 基线（后端 N1→N2，前端 M1→M2），不自跑 vitest
5. 迁移号无新增时写"无（vXX 已记入上一版）"；纯需求文档变更（如用户拍板砍需求）
   单列「📝 需求」小节
6. 插入位置：`# 变更日志` 与上一版 `## vX.XX` 之间（patch replace 头部锚点）

## 说明书漂移修复配方

1. 拿 changelog 各条目逐个搜说明书关键词（search_files grep 中文功能词）
2. 命中项三分类：
   - **漂移**（描述与代码行为矛盾）→ 修正。实例：缩放写旧三档"两个月"、画廊一概写"画册式翻页"、
     价格"留空则使用计算价"（实为脏标记跟随语义）
   - **缺失**（功能说明书从未写）→ 补新小节。实例：订单级收款（多收显示/退款规则）整节新补
   - **描述属实** → 不动。实例："手动录单仍用旧档位模型"经代码 + STATUS 候选核销记录双重确认属实
3. 每条修正记入交付报告表格：# / 位置 / 修正内容 / 代码依据（commit hash 或 文件+行号）
4. 不重构文档结构、不加未实现功能描述（修复原则，派工明文要求）
5. 全局复查：修完后把波次清单所有关键词再 grep 一遍说明书，确认无残留漂移点

## 交付报告结构

- changelog 新增条目数（分节列出）+ 每条附 git hash 实锤（波次 merge hash + 具体 commit hash）
- 说明书修正表（# / 位置 / 修正内容 / 代码依据）+ 「核查过无漂移的点」一节（防一号怀疑漏查）
- 与派工素材的偏差记录（以代码为准的修正 + 理由）
- 自查：git status 确认仅动授权文件、格式对齐既有版本段落
