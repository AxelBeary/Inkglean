# REQ 并行审核冲突：一号审了旧版，用户随后推翻拍板

> 教训日期：2026-08-03（artist-commission REQ-024）

## 场景

四号拷问→提交 REQ→**一号并行会话**审核并提交状态变更（甚至基于用户某句拍板写进文档）→ 与此同时用户还在和四号继续拷问，**推翻先前拍板或追加新功能**。

实例：一号 commit `56d606c` 审核通过 REQ-024 F1-F5，showcase 按用户当时原话拍板"直接迁不提示"；随后用户在同晚与四号的对话中改口"选乙"（showcase 丢弃 + 新增 F6 作品档位标注）。

## 检测信号

- `write_file` 返回 `_warning: file was modified by sibling subagent` → 有并行会话动过同一文件
- 提交前必查 `git log --oneline -5 -- <REQ文件>`，看是否冒出新 commit（尤其 commit message 含"审核通过/拍板"字样）

## 化解配方（4 步）

1. **先读对方改了什么**：`git show <对方commit> -- <文件>`，确认增量后再写自己的版本，禁止盲覆盖。
2. **最终拍板为准**：用户后面的决定覆盖前面的——即使一号已基于旧拍板审核。不因"已审核"而劝阻用户改主意。
3. **状态字段拆着写，不整体打回**：已审部分保持已审状态，新增部分单独标记。例：
   `状态：F1-F5 已通过一号审核（排入 v0.35）；F6 为用户后续新增，待一号确认范围与排期`
4. **交接 comms 写时间线 + 只留一个决策项**：写清"你何时提交了什么 → 用户之后在哪推翻（附逐字原话）→ 文档已同步"，然后只给一号**一个**需要他决策的问题（如"F6 并入 v0.35 还是拆版本"），附四号掌握的信息供参考。不让一号重新消化整份需求。

## 决策变更传播（并行冲突场景的加强版）

变更的决策必须在 REQ 内全量同步：正文功能节、用户原声节（新原话+日期）、相关验收标准、"已确认事项"节（把旧的"已拍板"条目改写并注明被新拍板覆盖）。漏一处 = 五号/二号日后读到旧结论。

## 反模式

- ❌ 发现并行 commit 后悄悄覆盖，交接文件只字不提（一号不知道自己的审核被推翻）
- ❌ 把整个 REQ 状态改回"待审核"（抹杀一号已审部分的进度）
- ❌ 交接文件写一堆背景让一号自己理清（应该直接给时间线+单一决策项）
