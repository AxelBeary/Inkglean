# 文档同步批 TOTP 漂移修复（五号，2026-08-05）——仅 docs/ 授权 + 代码零触碰

## 核心纪律：先 grep 代码再改文档
派工红线「不许凭文档自洽改文档」——每条修复前先 grep 代码确认现状，
交付报告逐条写「改前→改后→代码依据（文件:行号）」。
本批代码事实全部来自 grep/read（如 verify 限流 auth.routes.ts:38、
`_dev_secret` 字段 admin.routes.ts:149、init.js:1678 DROP login_codes）。

## 授权边界：仅 docs/，发现代码问题只报告不动手
- 代码文件一律不碰；发现的代码问题写进交付报告「发现的代码问题」表
  （本批报告了 init.js 建表残留 + rate-limit.ts 注释引用已删接口两处）
- changelog.md 是历史账本不改；archive/ 不动
- STATUS.md 是一号只读文件，即使含目标 token 也不动（且其内容是「已删」正确事实记录）

## token 清零验证的分区判定
grep `send-code|_dev_code|login_codes` 复查时，区分合法残留区：
- ✅ 豁免：changelog.md（账本）、archive/（归档）、comms 派工任务原文（任务描述本身含 token）
- ✅ 豁免：STATUS.md（一号只读）
- ❌ 必须清零：产品文档（维护说明书/开发自参考/切换指南/需求稿/问题清单）
- 迁移史记录不删行，改写为描述性措辞 + 标注「已随 vX/REQ-XXX 移除」（保历史可追溯）
- 历史记录条目（如 P1 审计修复）保护仍存在时：标注继承关系而非删除
  （本批：防枚举保护由 verifyTotpLogin 继承——未注册 QQ 与错码同响应）

## 文档漂移批的交付报告结构
1. 代码现状核实结果表（全部修复的依据，文件:行号）
2. 逐条修复：改前 → 改后 → 依据
3. 验证结果（grep 复查 + 豁免区清单）
4. 发现的代码问题（只报告不动手）
5. 提交纪律记录

## 断点续跑同样适用
本批也曾会话中断后重发派工：`git status --short` 看到已改未提交的文件 = 断点，
先 `git diff` 核对已改内容是否与本批一致，一致则续做剩余条目，不推翻重来。
