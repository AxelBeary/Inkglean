# docs-only 文档同步批工作流（五号，2026-08-05 TOTP 漂移批实战）

> 触发：派工「仅 docs/ 目录 + grep 清零类验证红线」的文档同步/漂移修复批。

## 开工顺序（关键）

1. **先跑验证红线的全量 grep**（如 `send-code|_dev_code|login_codes`），在动手前拿到全部命中清单——而不是只按派工行号清单改。
2. 命中分类（决定哪些改、哪些不碰）：
   - **必改**：产品文档（维护说明书/开发自参考/切换指南/待修复清单/requirements）里的漂移。
   - **豁免区不碰**：changelog.md（历史账本）、archive/（整目录）、其他角色只读文件（STATUS.md 归一号；且「X 已删」这种正确事实记录不是漂移）、comms 派工任务原文（token 出现在任务描述本身）。
3. 分类结果写进交付报告「验证结果」段，让一号一眼看到豁免理由。

## 修复纪律

- **每条修复前先 grep 代码确认现状**（派工原文：不许凭文档自洽改文档）。典型依据：接口清单（fastify.get/post 行号）、限流参数（guardRateLimit 实参）、字段名（响应体结构）、表是否已删（init.js DROP 行）。
- **历史记录不删行，标注式改写**：迁移史、已修复清单等账本性条目保留语义 + 补「已随 vX/REQ-Y 移除/继承」标注。
- **改写会引入残留 token**：第一版改写若仍含待清零 token（如把「send-code 防枚举」原样留下），grep 复查会抓到——清零红线 > 保留原文措辞，需二次改写（描述性措辞替代字面 token）。
- **派工清单外的漂移点自查自修**：grep 全量命中常暴露派工没列的漂移（如数据库表清单仍列已删表、迁移史多处字面表名）。改，并在报告里单独标注「自查发现」。
- **他角色已更新过的行**：派工若注明「L某行已由 X 号更新，不动」——语义不动，但若含待清零 token 可做最小 token 消除（语义本体一字不改），报告中说明。

## 代码问题处置

- 红线：只报告不动手。交付报告固定用表格：`# | 位置（文件:行）| 问题 | 建议`。
- 典型发现：死建表 SQL 残留、注释/JSDoc 示例引用已删接口。

## 验证与提交

- 纯文档改动无需跑测试套件。
- 收尾 grep 复查 + `git diff --stat` 核对全部在 docs/ 内。
- 交付报告与文档改动同 commit 或单独 commit 均可（惯例：一起提），逐文件 add。
- 报告模板段：代码现状核实结果表（事实|代码依据）→ 逐条改前/改后/依据 → 验证结果（含豁免区清单）→ 代码问题表。
