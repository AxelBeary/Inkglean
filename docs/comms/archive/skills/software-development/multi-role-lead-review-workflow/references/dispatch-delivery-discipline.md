# 派工交付纪律与核实预算（2026-08-05 v0.39 派工事故复盘）

## 事故链（三个错，一个根因）

1. **核实磨蹭一小时才派工**：派 v0.39 四路派工前，反复核实死键/模板页脚/admin结构/回收站组件等十余处，角色空等。
2. **派工只落盘 comms 文件**：写完四份派工文件就报告"就绪"，让用户自己去翻文件——用户看不见文件。
3. **补发时贴了一坨**：被纠正后把每角色一大段指令全文贴进聊天，而用户的动作是**每窗口复制一行**。

根因只有一个：**优化自己的完成感，不优化用户的吞吐。**
- 核实 = 用用户的 token 买"派工不会出错"的心理安慰；真实账本是四角色空转四小时。
- 落盘即"完成" = 把"我产出了什么"错当成"用户收到了什么"。交付物是用户能直接复制的那一行，不是文件。
- 字面执行规则（"指令全文贴进聊天"）而没想用户的真实动作（逐窗口复制一行）。

## 规则（已同步进 SOUL 与记忆）

1. **产出定义**：任务完成 = 用户手里能直接用。文件落盘但用户拿不到 = 未完成。
2. **核实预算**：派工前只核实三类——①授权文件现状 ②要写进派工的 API 契约 ③候选项是否已过时（STATUS/候选列表可能过时，这条来自 v0.22 教训）。每类最多一轮查证，同一事实不重复。
3. **派工交付形态**：聊天里每角色一行：「你是X号，先读 STATUS.md 再读 docs/comms/01-to-X-xxx.md 执行，worktree 在 ../xxx，只动自己分支，不推送不合并」。细节全写进派工文件让角色自读。
4. **时间盒**：派工/审核类任务超 20 分钟无可见产出 → 停下向用户报卡点，不默默磨。
5. **双向规则**：单极规则必然过度执行。防"乱派"的同时必须写"核实的上限"；任何新增纪律检查有没有对侧失衡。

## 懦夫优化警告

核实永不挨骂，派错要担责——于是下意识选零风险动作无限重复。owner 的正确算法：敢派 95 分的工，四角色开工后几分钟内即可纠偏；零派工是百分之百的损失。

## 补遗（同日审核/合入环节，2026-08-05）

1. **误删在途派工**：git rm 合入即删文件前逐个核对归属分支已合入；在途分支派工绝不能删（角色 merge master 后文件从 worktree 消失）。v0.39 实例：误删二号/五号在途派工，靠 commit 前 git status 自查发现并 restore。
2. **合入带新依赖的分支后先 npm install**：主 worktree 的 node_modules 不含新分支引入的依赖（如 simple-icons），build 报 `Rollup failed to resolve import`——这是环境状态不是代码问题，install 后重跑即过。merge 后跑测试/build 门禁前先对受影响目录 install。
3. **门控分支一次收**：后端门控分支等前端批一起合时，让前端分支在 worktree 里先 merge 后端分支联调；收工时一号只 merge 前端分支一次即收双分支（先 `git merge-tree --write-tree master <branch>` 预检冲突）。
4. **soul 存放位置（用户多次强调）**：角色 soul 正主 = 仓库 `docs/soul/soul-0N-*.md`（git 持久，角色窗口读这个）；hermes-home 的 SOUL.md 是**多档案共享、随活跃窗口跳变**的，往里写规则会被其他角色的内容覆盖/串档。一号的纪律改动一律落三处：`docs/soul/`（git）+ skill + 记忆。
5. **「X号没在工作」先查 worktree 再定性**：用户报某角色没干活时，先 `git log --oneline -3` + `git status` 查该角色 worktree——常见情况是**活已干完但没转交**（角色窗口闲置/关了，commit 和交付报告都在分支上）。v0.39 实例：用户说"我这五号没在工作"，实际 polish 分支已有 3 个 commit + 交付报告，直接走正常审核合入流程，不需要重新派工。判定三分：分支有交付 commit → 审核合入；分支有半成品 → 问用户是否续；分支无动静 → 重新触发角色（贴触发语一行）或重新派工。
6. **交付报告在 worktree 分支里，不在 master**：角色把 `02-delivery-*.md` commit 到自己分支——主仓路径 `read_file` 会 File not found。读交付报告用 worktree 目录路径（`../<worktree名>/docs/comms/...`）或 `git -C ../<worktree> show <branch>:docs/comms/<file>`。收到转交先 `git -C <worktree> log --oneline -6` 确认交付 commit 存在再读报告。
7. **用户声称"取消过/说好了"但记录无痕 → 查证后不擅自删，待用户拍板**：用户说某在途批"之前取消了"时，查三处证据：①STATUS 当前描述 ②git 里派工文件/提交历史有无作废痕迹 ③相关临时产物（截图等）是否还在。三处都无取消记录 = 该批**从未启动或从未被正式取消**——此时**不擅自删派工文件**，STATUS 记"用户称已取消，待确认"，把证据摆给用户二选一（确认取消→删文件作废；没取消→立刻派工）。宁可多问一轮，不可静默丢弃在途派工。
8. **候选项可能"部分已做"——核实时区分"整项未做"与"残余子项"**：候选清单（STATUS 待派行/核实报告）常把一项工作记成整块，实际代码可能已做了大头只剩残余。2026-08-06 环境批实例：候选项"uploads 区分公开与签名路径"看似整块待做，核实发现签名校验钩子（isPublicUploadPath + verifyFileToken）早已实现，残余只是响应头语义（公开图片被一律 attachment 强制下载）。派工据此改写为"只补响应头，不重做访问控制"——避免角色重做已有逻辑、误删已验证的安全钩子。核实预算第 ③ 类（候选项过时）的升级版：不止查"做没做"，还查"做到哪一层、残余是什么"。
9. **大型派工/交付文档一次写入会超时**：write_file 单次内容过大（数千字中文派工文档）会在 tool call 流中途超时（2026-08-06 三号环境批实例，系统提示勿原样重试）。恢复姿势：拆小——先 write_file 写主体，再用 patch 逐节追加；或写前按节拆分。派工文档随项目演进越写越长是常态，长文档默认考虑拆分写入。
10. **并行批的文件所有权必须互斥写明**：同一轮派多个批时，各批授权文件会重叠（2026-08-06 视觉四批：theme.css 同时是二号动画收敛批与五号约稿页批的波及面；OrderForm.vue 内 scoped 样式两批都想动）。每份派工的「不要动」清单必须点名**其他并行批的文件归属**（如「OrderForm.vue——五号并行批在改」「theme.css——二号批 1 在改，会冲突」），共享样式文件（theme.css/templates.css）指定唯一归属批，其他批只在自己 scoped 样式内收敛。并行审核合入顺序也按归属批先后排。

## 补遗二（2026-08-06：便宜模型时代 + 循环恢复）

11. **施工图派工形态（执行端换便宜模型后）**：用户拍板执行角色窗口切便宜模型、一号留高版本后，派工文件必须写成**施工图**——①每个改动点精确到文件 + 行号（如 `第 106 行`）②给 before 原文 + after 完整代码块（便宜模型直接粘贴，不留判断空间）③写明原理一句话（如"`:root:root` 双伪类提升特异性压过 EP 单 `:root`"，便宜模型不需要懂但改了能对）④自测步骤具体到命令与断言。写施工图的成本压在派工前，收益是便宜模型照抄即对、审核时 diff 干净。
12. **写施工图也会查证过度 → 循环**：2026-08-06 实例——写 topbar 压缩批施工图前，连续 read_file/search_files 十几轮（读了 ArtistLayout 全文、git 历史、ThemeToggle、OrderForm、TplHero、TplStyleGrid、全部模板 heroRef 引用……）想"把每个细节核实到行号"，实际大部分细节施工图根本用不上，用户连发两次"你循环了，恢复"。**写施工图的核实预算与普通派工相同**：只核 ①授权文件 ②要写进派工的 API 契约 ③before 原文（这个必须准确，但一轮 read_file 足够，不需要读关联组件的全文）。写完 after 代码块靠的是设计能力不是查证量。被用户打断后立即停手落盘，不要"再补一轮查证再写"。
13. **循环恢复姿势**：用户说"你循环了/还能不能恢复"时——①立即停下手头所有查证类调用 ②直接产出当前能落的最小交付物（派工文件/commit/回复）③报告当前状态 + 下一步一句话，不再重复解释。循环的心理机制与懦夫优化同源：怕写错施工图挨骂，于是无限加查证；正确算法是"写 95 分的施工图，便宜模型照抄错了再纠"，一次落盘的成本远低于十轮查证。
14. **体检清单/评审缺陷的排期铁律（2026-08-06 A 测失败教训）**：体检清单（如四号模板体检 T1-T9）与外部评审缺陷清单，按类型决定能否挂起：**交互失效类（吸底条不出现、导航死链、按钮无效）必须立即修**，不得以"等真实反馈""A 测为先"为由挂起——真实画师第一眼看到的就是这些，挂了 = 放半成品给真人。观感/设计取向类（配色、布局重排）可以挂起等反馈。判定口诀：**"画师约不了稿/点不动"是 P0 必修，"不好看"是 P1 可排期，"风格喜好"可挂。** 用户对观感的一句抱怨（"好丑陋""浪费空间"）= 最高优先级生产事故信号，立即派工，不当噪声。给真人看之前（A 测/上线/演示）一号必须自己完整跑一遍核心旅程截图验收（详见 visual-quality-gate.md 的 A 测失败复盘）。
