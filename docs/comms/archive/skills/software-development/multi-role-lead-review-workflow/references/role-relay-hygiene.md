# 角色接力卫生六则（2026-08-05 v0.39/v0.40 轮实战提炼）

## 1. 角色 soul 存放位置（用户多次纠正，铁律）

角色 soul 的正主在**项目仓库 `docs/soul/soul-0N-*.md`**（git 持久、各角色窗口读的就是它）。
**hermes-home 的 SOUL.md 是多档案共享的，会随活跃窗口跳变**——一号会话写进去的规则可能被五号会话覆盖（v0.39 实际发生：一号写的全被五号内容替换）。

规则：
- 给角色定规则/补纪律 → 写 `docs/soul/soul-0N-*.md`，随 master commit 推送
- **不往 hermes-home/SOUL.md 写项目角色规则**（那里只放一号自己 profile 的通用行为）
- 发现 SOUL.md 内容与预期不符 → 先想到"被别的档案窗口换了"，不是文件损坏，不急着恢复，确认真实生效位置

## 2. 用户说"X号没在工作" → 先查 worktree 再下结论

v0.39 实例：用户说"我这五号没在工作"，一号去 polish worktree 一查——**3 个 commit 早已完成**，只是角色窗口没转交（用户看不见角色侧动作）。

处置流程：
1. `cd <该角色 worktree>` → `git log --oneline -3` + `git status --short`
2. 有未报告 commit → 按正常交付审核（读交付报告，没有就看 commit message + diff）
3. 审过就合，不等角色补转交——**交付物在 git 里就算数**（comms 通信机制原话：写下来才算交付，反过来 git 里有 commit 也是交付）
4. 确实什么都没做 → 才重新派工

反面：不查 worktree 直接重新派工 = 角色重复劳动 + 用户信任损耗。

## 3. 只读核实报告的消费纪律（合入即删的例外处理）

五号常把只读核实报告**直接落在主 worktree docs/comms/**（untracked，不走分支）。这类文件没有"合入"动作，但同样适用"消费即删"：

1. **先完整读完**——报告可能含未转达的新发现（v0.39 实例：前端检查报告核实 + 垃圾检测核实两份，含 WAL 危险警告、README 过时等此前不知道的事实）
2. **提取行动项进 STATUS 遗留**——逐条写明：什么项 / 归属谁 / 优先级 / 危险项排除（如"宿主 DB 是 WAL 删不得"）
3. **然后 git rm 删除**，commit message 注明"行动项已提取入 STATUS"
4. 绝不未读先删（丢失事实），也绝不读完不删（comms 积累）

## 4. worktree 依赖卫生（新依赖合入 master 后）

master 合入带新 npm 依赖的分支（v0.39 实例：simple-icons）后，**其他 worktree（含主仓）的 node_modules 是旧的**：
- 主仓 build 报 `Rollup failed to resolve import "xxx"` → 不是代码问题，`npm install` 即解
- 角色 worktree merge master 后 vitest 直接退出码 1 → 先 `npm install` 再跑

规则：审核角色交付时若其分支 merge 过含新依赖的 master，复跑测试前先确认该 worktree 跑过 `npm install`。派工文件里"开工第一步 npm install"这条不能省。

## 5. comms 清理防误删在途派工（2026-08-05 实际踩坑）

"合入即删"只适用于**已合入批次**的派工/交付文件。v0.39 实例：一号批量 git rm 时把二号/五号**仍在途**的派工文件（01-to-02-F1F2前端批、01-to-05-打磨第二批、接力指令）也删了——角色 merge master 后派工会凭空消失。

处置流程：
1. 批量删除前逐个文件过一遍：对应批次合入了没有？在途角色的派工**一个不删**
2. 删完立即 `git status --short` 自查暂存区清单（这次就是自查发现的，`git restore --staged --worktree <file>` 恢复）
3. 安全顺序：先 merge+push 合入 commit → 再删该批文件 → 单独收尾 commit

## 7. 用户拍板会随执行角色的交付报告到达（2026-08-06 实录）

用户在各角色窗口直接拍板，拍板记录跟着交付报告回到一号：四号模板体检批报告 §八 带「用户在四号会话直接拍板：1，修…2不进，封面上限设置为6…3，疑似漏网。4先不做」。这类**转交来的拍板与用户在一号窗口亲口拍板同权重**。

处置流程：
1. 审交付报告时逐条识别「用户已拍板」段落（找「用户拍板/用户确认」字样），**不当建议看待**
2. 立即入账 STATUS「已拍板规则」编号续写（如规则 13：T1 修/T8 封面上限 6/T6 修/T9 缓），commit message 注明「用户在 X 号会话拍板，X 号落档」
3. 后续派工按已拍板规则执行（如「封面上限 6」是新需求，要排期落地；「T9 先不做」直接挂起不再问）
4. 报告里的「待确认问题」若已被用户当场拍板划掉，不要重新呈给用户二选一——重复问已答过的问题损耗信任

## 6. 角色窗口消息滞后 → 重复/过时报告（2026-08-05 实例）

三号转交时把**已合入的** addons 清理第一批又报了一遍（他窗口不知道已合入）。处置：
1. 收到报告先对 STATUS.md / `git log` 核实该批次当前状态
2. 已合入 → 向用户说明"重复报告，早已合入，窗口消息滞后"，不重复审核不重复合并
3. 未合入 → 正常走审核流程
4. 多路并行时角色窗口之间天然互不知情，一号是唯一全局视角——**以 git 和 STATUS 为准，不以角色转述为准**

## 8. 批次合入后「分支 + worktree + comms」三件套必须同步回收（2026-08-06 用户主动喊"有大量的分支和细碎的小文件"）

"合入即删"纪律如果只删 comms 文件、忘回收 worktree 和分支，几轮下来堆积成山：本次实录 7 个分支、7 个 worktree、14 个 comms 文件，用户看不下去了才喊清理。**每批合入收尾 = 一个三件套动作**：

1. `git worktree remove ../<worktree>`（回收前 `git status --short` 确认干净，在途分支绝不回收）
2. `git branch -d <branch>`（已合入分支安全删；报"未完全合并"见下）
3. `git rm` 该批派工/交付文件 + 单独收尾 commit

批量清理流程（防误删）：
- 先 `git branch` + `git worktree list` 全量盘点，标注每个分支/工作区状态（在途/已合入）
- 只回收已合入的；在途的（有角色正在跑）一个不动
- 删文件前逐个核对对应批次已合入（role-relay-hygiene 规则 5）
- 收尾 commit message 写明清理范围，`git ls-files docs/comms/` 确认只剩 STATUS + 在途派工 + 有效参考

**只读批（chore/*）分支删除的坑**：只读批交付物（截图/报告）常由一号 copy 进主仓归档，分支本身没有代码合入，`git branch -d` 报"not fully merged"。处置：`git diff master...<branch> --stat` 确认交付物已在 master → `git branch -D`。先验证再强删，不盲目 `-D`。

## 9. 便宜模型时代：接受自测降级，但独立复跑门槛不降（2026-08-06 实录）

执行角色换便宜模型后，自测环节开始出现**环境受限导致的降级**：二号 topbar 批报告"浏览器实测受限（宿主网络连不上 localhost:3000），用 happy-dom 组件测试覆盖渲染逻辑，覆盖率与浏览器实测等价"。处置：
- **接受**：组件测试（模拟 matchMedia 宽度切换）确实能覆盖"顶栏 v-if / footer-tools 存在"这类渲染逻辑，不必强行要求真实浏览器
- **不降**：一号的独立复跑（`npx vitest run` 全绿 + eslint 0）仍是合入门槛；报告声称的组件测试可抽查是否真有（临时测试已删除的话，靠 diff 范围 + 独立复跑兜底）
- 便宜模型自测变弱的信号会越来越多，一号审核更依赖"diff 逐行 + 独立复跑"，而不是角色的自述验证
