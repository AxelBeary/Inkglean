# 角色违反 worktree 纪律的两类形态与处置

## 形态 1：共享主 worktree 时的未提交产物夹带（e04f2f5 事故）

见 SKILL.md 第一节（共享 worktree 提交卫生）。

## 形态 2：角色已直接 commit 到主仓 master（违规但已成事实，v0.38 四号实录）

与形态 1 不同：角色绕过分配的 worktree，**已经**把交付 commit 到主仓 master。处置决策树：

1. **先查扩散面**：`git show --stat <hash>` 确认内容 + `git fetch; git rev-parse origin/master` 对比本地——**是否已推送**是关键分水岭。未推送 = 处置空间大；已推送 = 绝不 reset（合并安全铁律），只能向前。
2. **审内容定性**：纯 docs 零代码 = 低风险，走内容审核（**抽查其中的代码现状声明**——self-report 不可信，search_files 逐条核，如「无导出接口」「QQ 历史面板存在」「客户端无时区处理」）；含代码 = 按正常交付审核清单补审。
3. **内容过关 → 收下，不回滚重做**：reset 一个内容正确的 commit 纯属形式主义浪费（且违反合并安全）。违规记账两处：STATUS 角色状态栏写「⚠️ 流程违规记账：X 未走 worktree 直 commit master，内容已过审合入 `<hash>`，已提醒」+ 回复里点明让用户转达角色下次必须 cd worktree。
4. **内容不过关 → 向前修正**：新 commit 修正/还原（revert 也是新 commit），不 reset。
5. **核心心态**：流程违规与内容质量**分开评定**——违规不自动等于打回（内容好就收），内容过关也不等于不记账（纪律要维护，否则 worktree 隔离体系形同虚设）。实录：四号 AI 头脑风暴拆解是用户交办加急、内容质量高（12 条代码核实全属实），一号收下 commit + 记账 + 把他推回原任务（验收清单还没动）。
6. **区分「用户交办加急」与「自作主张」**：用户直接丢给角色的插单任务，角色情急直 commit 主仓属可谅解违规（记账从轻）；角色自己发起的越权操作属严重违规（记账从重 + 明确警告）。定性写进记账文本。
