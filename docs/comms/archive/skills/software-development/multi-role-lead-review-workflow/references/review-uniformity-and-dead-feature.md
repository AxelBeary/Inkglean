# 审核红线：模板区分度 / 孤立控件 / 文档态功能 / 负数路径回归

来源：2026-08-05 用户报障轮（画廊四问题 + 负数收款）。四条都是"合入后用户实测才发现"的事故，本应在一号审核或派工阶段拦住。

## 1. 多模板改动必须保留区分度（最高优先）

artist-commission 客户端有 4 个主页模板（Classic/Gallery/Folio/Atelier），用户反复强调"不同模板要有区分度"。
波 2-A 派工"画廊改画册翻页"执行成**四个模板全部换成左右翻页**，用户实测后发火："怎么每个模板都用左右滑！！！！我重复了不止一遍"。

- 派工阶段：涉及共享组件（TplGallery 等）的多模板改动，派工书必须逐模板写明各自的布局/模式，而不是"统一改成 X"。
- 审核阶段：diff 里若所有模板文件对共享组件的调用变成同一个 prop 组合，直接打回。验收矩阵：每个模板一行，列出布局模式，要求 ≥2 种（除非产品明确要求统一）。
- 修复形态：给共享组件加 layout prop（album/masonry/grid 双分支并存），模板各自显式传参；同时把键盘/滑动监听用 `isAlbum` 门控，避免非翻页模式被全局键盘事件干扰。

## 2. 移出共享区域 = 附属控件必须跟随

F7 主图去重把 is_cover 作品从网格移到独立主图区，但网格卡片上的「cover_order 序号 + ↑↓ 排序按钮」没跟过去——主图区只剩 ★。用户报"主图之前不是做好的1234吗？排序序号也没了"。

审核检查项：任何"把某类条目从区域 A 移到区域 B"的 diff，逐条核对 A 区域模板里挂在条目上的所有徽标/按钮/交互是否出现在 B 区域。排序类控件（reorder）尤其容易漏，因为它们只在 count>1 时渲染，单条数据测不出来。

## 3. "砍掉 X"先查代码存在性

用户说"砍掉水印"。全仓 grep `水印|watermark`：代码零命中，只存在于 REQ-022 需求文档的 F1 链路规划（从未开发）。

正确动作：grep 确认存在性 → 零命中则执行的是**需求文档编辑**（从链路图删环节、删功能小节、删验收标准、工时 5→4 天、删依赖项、留一行"已拍板砍掉"注记），并如实告知用户"代码里本来就没有，已把需求文档里的规划移除"。不要假装删了代码。

## 4. 前端数值校验别拦死后端设计内的负数路径

order.service addPayment 明确支持负数（schema minimum:-99999999、注释"正数收款/负数撤销"、负数必填 note、撤销不超已收）。但审入的 L3 前端校验写了 `cents <= 0 → 拦截` + `:min="0.01"`，把退款路径整个拦死——典型的"前端校验比后端规则更严"回归。

审核检查项：任何新增金额校验，先到后端 service/schema 确认合法值域；负数有意义的场景（退款/撤销/调账）必须放行负数、只拦 0，并补负数专属约束（必填原因、不超已收）。el-input-number 的 :min 同步放开（注意单位换算：后端分 vs 前端元）。
