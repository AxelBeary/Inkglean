# 外部/第三方测试报告的分诊与派工（A 测反馈批次的预演形态）

触发：用户转来外部测试者（第三方审核者、AI 模拟报告、未来 A 测的真实画师反馈）的 N 条问题清单。

## 分诊流程（先核实再派工，外部报告默认半信半疑）

1. **派给执行角色做「只读核实批」**：逐条对照代码 + 浏览器实测复现，产出三分法结论——真问题 / 误报 / 数据质量或产品决策（非代码 bug）。派工写明「只读核实，未改任何代码」。
2. **一号抽查核实报告**（self-report 不可信照旧）：抽每条「真问题」的代码定位（文件:行号）grep 复验至少一半。实录（v0.38 五号核实第三方 10 条）：A/B/C/D 四条定位全属实才采信。
3. **误报项不静默丢弃**：核实报告写清误报理由（如「空提交可成功」实为三层防线原生 required+trim 守卫+后端 minLength:1），防止用户/下一轮再捞。
4. **真问题打包成低风险打磨批派工**：授权文件逐个列（组件 + locales + 样式段）；需产品拍板的项（如「需求描述可空过」是否加校验）**单列等拍板，不混进打磨批**。
5. **数据质量项给引导不改代码**：如「作品图 alt=文件名」根因是上传时 title 存了文件名——从上传引导解决，不动画廊渲染代码。

## 静态可判定 vs 需实测：三分法派工（2026-08-06 实录，外部前端视觉评审 12 条 → 5 真 3 假 1 待实测 3 页面级暂缓）

外部报告逐条对照代码后，分三类处置，**只派属实项**：

1. **静态证实**（代码里有明确证据，如动画 hover 三档混用 theme.css:120-127、404 推荐无 status 过滤 NotFound.vue:51）→ 直接进修复批派工。
2. **静态证伪**（指控与代码相反，如「avatar null 硬渲染 `<img>` 破图」实为 el-avatar 带首字 slot 兜底、「价格不按 sort_order 排」后端有 ORDER BY sort_order ASC）→ **打回不派**，并在派工文末附「已打回的不实指控」清单，防止执行角色顺手照做。
3. **静态不可判定**（纸面设计正确但渲染效果未知，如「EP 主色覆写没生效」——覆写在 theme.css 且全局引入，纸面应生效；「选中态看不出」——`--on` class 和 ✓ 标记都在，但可能对比度弱）→ 派**「实测优先批」**：核心纪律 = 先 Playwright 截图取证再决定修不修，每项交付 before/after 截图与结论「属实已修 / 不实未改」，**明确写「不实项不许硬改凑工作量」**。这类批的验收物是测量证据，不是代码 diff。

## 有意设计决策被误报为 bug

外部评审常把**有意的默认**当泄漏/缺陷报（实录：徽章 success/warning 用 EP 出厂色，theme.css 注释明写「功能色固定，不跟随主色」= 既有设计决策）。处置：**不进修复批**，单列给用户拍板并附你的倾向（如「保持——功能色跨平台一致是惯例」）。grep 代码注释找「固定/有意/决策」字样能快速识别这类。

## 交付格式：判定表 + 分批原则

- 向用户呈现用判定表：指控 | 判定（✅属实/❌不实/⚠️待实测）| 证据（file:line），末行给总分（「12 条 5 真 3 假」）。诚实记分卡比全盘照收更对用户胃口（外部报告打折看）。
- **跨页通病优先于页面级改造**：「改一处好一片」的通病批（动画纪律/全局色/空态防御）先派；页面级重写（Landing Hero 重做等）工程量大且属设计取向，**A 测后再做**——真实用户用起来之前不值得大改门面。

## 并行批撞诊同一根因：交叉去重，不重复派工（2026-08-06 实录）

多批并行时，两个执行角色会**独立诊断出同一个 bug**：五号约稿页批的 W2（EP 蓝泄漏，根因 = EP base.css 按需注入晚于 theme.css 覆盖 `:root`）与二号视觉批 1 的 V2 是同一根因——五号交付时二号批已用 `:root:root` 双伪类提特异性根治并合入。

审核纪律：
1. 收到交付报告先与**最近合入的其他批**交叉对照根因描述（关键词：文件路径 + 症状），同站点视觉/样式病的根因就那么几个，撞车概率不低
2. 撞车处置：merge message 写「W2 已被 X 批根治，无需重复」，**不另派修复、不要求执行角色返工**——他把方案呈上来等裁决，裁决就是「已有人修了」
3. 执行角色侧正确姿势（五号示范，值得写进派工模板鼓励）：发现要动的文件属其他批授权范围时，**只给方案不动手**，报告里写明倾向方案请一号裁决

## 与真实画师 A 测批次的关系

本形态是 A 测反馈批次的预演。A 测时同样流程，但注意：真实用户反馈优先级高于 AI 模拟候选清单（REQ-031 拍板规则）；反馈条目按严重度分级派工，阻塞类问题插队当轮。

## 外部安全审计类报告：判断与修复方案分开核实（2026-08-05 实录）

安全审计类报告常含两层内容：① 问题判断清单（F1~Fn）② 附带的修复 patch/方案。**两层都要独立核实，修复方案尤其要审**——盲套外部 patch 会继承它的盲点。实录（五号核实安全审计报告）：
- 判断层：14 项逐条对照代码核实，抓出 1 项部分误报（「adminQq 泄露」实为产品功能——查单页联系管理员弹窗在用，删除会断功能，转用户拍板而非照修）
- 方案层：对方 dto-patch 方向正确但**漏修第 4 个泄露端点**（`/api/artist/profile` 也是完整行返回）+ 显式列清单漏前端在用的 `quick_actions` 字段——直接照抄会留泄露 + 断前端
- 派工写法：以外部 patch 为基础，把核实发现的缺陷修正逐条写进派工（「应用到 4 个端点而非 3 个」「显式列补 quick_actions」），执行角色不接触原 patch 的缺陷版本
- 「属实但是产品功能/已知延后项」是常见第三类——别当新发现重复立项（限流进程内 Map 连续两份报告都提，都是同一已知项）
