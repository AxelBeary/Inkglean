# 剩余工作盘点 / 就绪评估（"还有什么要做的"、"搞完就能测了吧"）

用户高频问两类问题：**① 现在还剩什么要做的 ② 某事搞完是不是就能给画师测试了（A 测就绪）**。答错代价大：报多了会派不存在的活浪费角色产能，报少了漏掉上线门槛。**唯一可信来源是代码 + git log，不是任何 docs 状态字段**——需求稿的"状态"行、STATUS 的待办表、候选池清单都可能过时。

## 铁律：盘点前先对账，逐条验证"声称未做"的项

1. **对每个声称未完成的功能**，两条证据链交叉验证：
   - `git log --oneline --all -S "REQ-XXX FN"` —— 找实施 commit
   - `search_files` 在源码里搜 `REQ-XXX FN` 标记注释（本项目惯例：实施时留 `// REQ-022 F4: ...` 标记 + 配套测试文件名）
2. **对"遗留小项"类**（死键、清理项）：全库 grep 引用数，0 引用 = 早已被某批顺手清掉。
3. **版本计划/在途表**：逐行和 `git log` 对照，✅/🟡/未实施 标记以 commit 为准。
4. 验证完才回答；回答里区分「开发项」与「部署/拍板项」——本项目 A 测前开发项清零后，剩余通常是：容器重建、环境批（生产配置需用户拍板）、关 AUTH_DEV_MODE（按四号执行手册）。

## 实证案例（2026-08-06）

用户问"还剩什么"，一号先报了"A 批开发任务：F3/F4/F5 + 死键清理"——**全部是过时信息**：F3 摘要回显 `3b1c609`、F4 回收站分页 `e4bdc4e`、F5 留言三维筛选 `b42a0fd` 早已合入，死键全库 0 引用。根因：REQ-022 文档状态行写"未实施"、STATUS 写"剩余链路待做"，一号先信了文档。靠"派工前验证代码现状"铁律在写派工前拦截，未造成空派工。

## 发现文档过时的修正协议

1. 当场修正过时的状态字段（需求稿 + STATUS 双处），commit message 写明"系文档过时，核实修正"
2. **明确向用户纠正自己上一条的错误**（"纠正：我上条说的 X 不存在"），不默默改口
3. 把真实剩余项重新归类报给用户

## 资金见底时的盘点口径（2026-08-06 用户原话「开发资金快见底了」）

预算收紧时盘点回答要换口径：**唯一硬目标 = 让 A 测跑起来**（能带来真实反馈→真实价值的路径），其余按三档处置：
1. **已派的批照常收**——审核合入，别浪费已花的钱（半途叫停比跑完更亏）
2. **新派工全部挂起**——除非 A 测反馈直接要求；外部评审/研判报告里的十几项 nice-to-have 一律归档成账本（报告入 comms/STATUS 已知遗留），不派新批
3. **给用户的答案要直说取舍**——「这些都能修，但现在修 = 烧钱做 A 测前没人看得到的东西；真实画师骂哪里就修哪里，比 AI 评审猜得准」

对用户的自我怀疑（「买了最贵的模型怎么还这么丑」）回应姿态见 references/visual-quality-gate.md「用户自我怀疑时的回应姿态」——预算与审美焦虑常一起来，分开回应。

## 用户断言"之前取消/拍板过"但记录里没有时

案例：用户说视觉巡检批"之前不是取消了吗"，但 STATUS v8 与 git 里都是"在途/待接"、无取消痕迹。**不盲从也不硬顶**：①查记录如实报告（哪几处查的、各写什么）；②把事实摆清楚（该批实际从未启动过）；③请用户拍板，拍板后立即销账（删派工文件 + STATUS 记"用户拍板取消"+ commit）。记录里没有 ≠ 用户记错，也可能是口头决定未传达——无论哪种，以本次拍板为准并留痕。
