# 用户质疑算法/计价行为时的分诊协议

触发：用户用一句话质疑某个算法行为（"算法不是之前说的 X 吗？""不是说好的 Y 吗？"），语气带困惑或质问。

## 核心原则

用户的质疑可能指向三种完全不同的情况。**先查后答，不空口判断**：不立即当 bug/回归认错（可能规则压根没上线），也不直接否认（可能是真回归）。

## 步骤

1. **读需求文档**：search_files 在 `docs/requirements/REQ-*.md`（及 `docs/archive/`）搜规则关键词。确认：
   - 规则是否成文？在哪份 REQ 的哪条？
   - 有无用户拍板记录（"用户拍板 D*"/"用户已确认"字样）？
   - 排期：当前版本 / 未来版本 / 范围外？（看文档"排期"章节和 STATUS.md 版本计划表）
2. **读代码现状**：search_files 定位相关后端函数（如计价/收款相关），确认当前实际行为。self-report 不可信原则同样适用于自己的记忆——不查代码不下结论。
3. **三分法定性**：
   - **已拍板未实现**（规则在未来版本 REQ 里）→ 回答结构：规则出处（哪份 REQ、哪条、何时拍板）→ 当前排期 → 代码现状（引用函数名+实际行为）→ 结论"这不是 bug，是旧算法预期行为，REQ-XXX 专门解决它"。不认错、不打补丁。
   - **已实现但坏了**（规则在已上线版本里但代码行为不符）→ 按回归处理：查是哪次改动破坏的，评估风险，必要时走 hotfix。
   - **用户记错**（文档无此规则）→ 拿文档证据礼貌纠正，说明实际约定是什么。
4. 结尾给用户两个落点：①如果是终验中撞到的具体现象，请他说出步骤以便定位；②如果这是最痛的点，确认是否调整版本优先级。

## 实例（2026-08-05）

用户："？？？算法不是之前说的收好的节点不再改变的吗？"

分诊结果：
- 规则成文：REQ-025 R4「锁价规则：完成 OR 付清，先到先锁」，2026-08-04 用户拍板 D1③，排 **v0.37**（v0.36 明确"不动计价模型"）。
- 代码现状：线上仍是 v0.31 F4 `recalcInstallmentAmounts`（order.service.ts）——改价/加项后**所有节点**按 basis_points 无条件等比重算，无锁定检查。`updateFinalPrice`、增删增项均调用它。
- 定性：已拍板未实现 → 用户看到的"已收节点金额被改价抬高"是旧算法预期行为，不是六路修复引入的回归（六路均未碰计价算法）。
- 注意：REQ-025 落地（v0.37）后本实例的代码描述过时，届时以代码为准；本协议的方法论不变。

## 相关检查清单（合并审核时联动）

用户拍板过的算法规则清单散落在 REQ 文档里。审核涉及计价/收款/节点的改动时，若发现改动方向与某条已拍板 REQ 冲突（哪怕该 REQ 未实现），必须在审核结论中标注，防止提前引入与未来模型冲突的逻辑。
