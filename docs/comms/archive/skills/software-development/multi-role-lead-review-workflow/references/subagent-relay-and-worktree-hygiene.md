# 子代理接力与共享 worktree 提交卫生（v0.36 实例，2026-08-05）

## 一、共享 worktree 提交卫生（e04f2f5 事故）

当某角色被授权在**主 worktree 直提**（四号修说明书、三号-B 清死码这类单文件低风险任务）时，他的未提交改动就躺在一号的工作区里。

**事故实录**：一号 `git add docs/comms` 提交五号-B 派工时，目录级 add 把三号-B 未提交的 `errors.ts` 改动一并带上 master 并推送，commit message 还只写了派工内容。违反"角色 commit → 一号审 diff → 合并"的正常流程。

**规则**：
1. 主 worktree 有其他角色活跃时，一号 commit 前必跑 `git status`，`git add` **只加具体文件路径**，禁止目录级 add（`git add docs/comms` 这类）。
2. 暂存后 `git diff --cached --name-status` 逐行核对暂存区与本次意图一致。
3. 事故已发生且已推送：**不回滚**（禁 reset/rebase）。处置三步——① 立即补审被带入的改动（对照该角色的派工清单 + grep 零残留 + 重跑测试门）；② 写瑕疵记录 `docs/comms/01-note-合入瑕疵-<commit>-<日期>.md` 进 comms 并推送；③ 给被波及角色带话：改动已在 master，无需再 commit，回报测试结果即可。

## 一-B、角色绕过 worktree 直接 commit 主仓 master（外部窗口模式，2026-08-05 四号实录）

外部窗口执行模式下角色是独立会话，可能不去分配的 worktree、直接在主仓 commit（实录：四号接用户交办的头脑风暴加急任务，没去 acc worktree，直接落 `b3661c4` 到本地 master，未推送）。与第一节（一号自己夹带）的区别：**提交者是角色本人**，一号是事后发现。

处置四步（已验证有效）：
1. **先审内容再定处置**：`git show --stat <hash>` 确认改动范围（纯 docs / 有无代码）+ 未推送状态（`git fetch` + `rev-parse origin/master` 对照）。
2. **内容纯 docs、已过审、未推送 → 不回滚，收下**：`git reset` 重来是形式主义浪费（且主仓禁 reset 是铁律）。按正常审核标准审内容（self-report 不可信照旧——角色声称的"代码现状核实"逐条 grep 复验），审过即认可该 commit。
3. **违规记账**：STATUS 角色状态行加「⚠️ 流程违规记账：<行为>（内容已过审），已提醒」——记账的目的是防再犯，不是惩罚；内容质量与流程违规分开评价，不连坐。
4. **随下一个收尾 commit 一起推送**，转交文件照常合入即删；回复用户时如实说明违规与处置，请用户转告角色下次 cd worktree。

判断边界：若角色直提的是**代码改动**（非 docs）或**已推送**，升级处置——代码改动必须补跑全套门禁（测试/tsc/lint）再认账；已推送的绝不 rewrite，按既成事实补审。

## 二、子代理迭代预算耗尽的接力模式（二号三轮接力实录）

长任务派给子代理（delegate_task）可能撞 `max_iterations` 中途停止，代码写一半、没测试、没 commit。

**接力流程**：
1. **重发前先查 worktree 实况**（`git status` + `git log` + `git diff --stat`）——上一轮实际落盘的往往比摘要说的多。实录：第二轮摘要自称"只完成侦察"，实际主体代码全写完了，只是没跑测试没 commit。
2. **一号把已完成部分先固化**：审 diff + 跑测试门后亲自 commit，缩小下一轮剩余范围。
3. 重发 prompt 明确写"第 N 次接力：A/B/C 已完成并 commit（hash），本轮只做剩余项 D/E，**禁止重新侦察**"——防止新一轮重复劳动耗预算。
4. 新旧两轮子代理时间上重叠是常态（旧的还在跑、新的已发出）。发现重叠先查 worktree 有无互相踩踏痕迹（文件内容矛盾、意外改动、第三方修正记录），再决定由谁收尾。
5. 子代理做不完的收尾（浏览器实测、交付报告、commit）**归一号兜底**，不是旁观者。
6. **预算耗尽但产出已暂存未 commit**（v0.38 三号实录）：交付摘要诚实写明"报告已 git add 但 commit 未执行，绝不伪造提交记录"。一号处置：① `git -C <worktree> status --short` + `diff --cached --stat` 核实暂存与自报一致；② 审核内容；③ 一号代执行 commit（message 照角色拟好的写）+ 走正常合并推送。这类诚实申报是正反馈对象——比"声称全部完成"可信得多，审核可适当从宽（证据抽查即可）。
7. **90% 完工只剩收尾（截图/报告/commit）时：一号亲自收尾，不再拉接力子代理**（v0.38 五号 F3 实录）：与第 2 条「半成品接力」不同——代码+测试已就绪、自报测试全绿，只差浏览器实测、交付报告、commit 三步机械收尾。此时再 delegate_task 一个子代理纯属浪费（交接成本 > 收尾成本，且新子代理还要重新理解现场）。一号收尾协议：① worktree 实况核实（status/diff 与自报一致）；② **独立复跑测试**（不信自报数字，npx vitest run 实测）；③ 一号亲自浏览器实测补齐截图证据（子代理死后其浏览器会话也关了，重开新会话从头走流程，几分钟的事）；④ 代写交付报告（注明"代码与自动验证由 X 号完成，收尾由一号代"，不抢功）；⑤ 逐个 add 白名单文件 commit + 合并推送。commit message 与报告如实记录分工。

8. **悬空成果的「抢救 commit」（连暂存都没有的形态，v0.38 三号 F2 实录）**：第 6 条覆盖「已 git add 未 commit」；更糟的形态是子代理**连 add 都没做**就撞上限——改动以 ` M`（修改未暂存）+ `??`（未跟踪新文件）散落工作区，随时可能被下一轮误操作覆盖/夹带。处置：① `git -C <worktree> status --short` 列出全部悬空项；② 清掉明确的临时垃圾（如 `.tmp-check-*.py` 这类自建的探测脚本，Remove-Item，不进 git）；③ **一号逐个 add 白名单内的悬空文件并 commit**，message 写明「阶段成果锁定（进行中：X/Y/Z 待续；N 号迭代上限中断由一代为 commit 防丢）」；④ 超白名单但属必要配套的改动（如 errors.ts 加错误码）一并 commit 并在 message 注明「已批准/待确认」，不丢也不静默放行。抢救 commit 的目的只是**防丢**（锁进分支 ref），**不等于审核通过**——该批仍按正常流程审核后才合入。注意：抢救发生在独立 worktree 的分支上，master 零风险，可放心先做再继续其他调度。

## 三、用户与子代理的可见性边界

用户明确说过："右边子代理我完全看不见，得你自己监视。"含义：
- 子代理的启动/进度/交付/异常全部由一号主动汇报，用户侧零可见。
- 监视手段：`live_transcripts` 路径（delegation 返回）`Get-Content <log> -Tail 5` 看尾部动作。
- 每轮向用户汇报盘面时用"当前并行盘面"小表：谁在干什么、在哪个 worktree、什么状态。
- **派出子代理的回合必须以盘面表收尾**（角色 | 任务 | worktree/分支 | 活体证据），绝不允许 delegate_task 发完就结束回合——v0.38 实录：一号连派两路后回合被截断、未给盘面，用户直接发火"你现在一个工都没有派出去，所有人都在待命"。子代理对用户完全不可见，**没汇报 = 没派**。
- **用户质疑"没派工/全员待命"时 → 先验活再答复，绝不直接重派**：① `Get-Item <live log>` 看 LastWriteTime（一分钟内更新 = 活着）+ Tail 看在干什么；② `git -C <worktree> status --short` + `git log --oneline -2` 看产出；③ 确认活着就带证据呈现盘面表（log 时间戳 + worktree 分支）。盲目重派 = 同一 worktree 两个子代理撞车（分支占用、文件互踩）。v0.38 实录：验活发现两路 log 持续增长、worktree 完好，是汇报缺失不是派工缺失。
- **回合中断 ≠ 子代理死亡**：delegate_task 已成功 dispatch 的批次跨回合继续跑（除非宿主进程被杀）。会话重新开局的第一动作 = 扫 delegation live 目录确认存量批次（今天日期的目录）的存活与进度，再决定推进/补派。
- **派工最后一公里核对：派工文件 ↔ live delegation 对账**（v0.38 实录）：「派工文件已 commit+push + worktree 已建」≠ 已派工——delegate_task（或给用户的开工指令）才是最后一步，链条中途被截断时任务实际没发出去（实录：五号 F3 派工 ac3eb53 已推送、worktree 已建，但 delegate_task 没调用，下一轮用户对账才发现）。对账方法：列出今日 comms 里的派工文件（01-to-0N-*.md），逐个核对 delegation live 目录有无对应 goal 的存活/已完成 log；缺的立即补发。每次回合恢复、每次用户质疑「没派工」，先跑这个对账再答复。
- **子代理完成通知可能丢——不能只靠通知**：撞 max_iterations 退出的批次，其完成消息可能永远没送达一号（v0.38 实录：二号视觉批 08:35 已诚实上报中途退出，一号以为它还在跑，10 分钟后查 log 才发现）。规则：凡有疑点（log 时间戳超 5 分钟不更新、长时间无完成通知），主动翻 live log 找 `final` 标记——`final | status=completed` 即已结束，读 exit_reason（max_iterations = 预算耗尽）与 summary 里的诚实汇报，按第二节接力流程处置。日志停止增长只是疑似，final 行才是判据。
- **完成通知延迟到达 + 摘要被截断——读全文再行动，先核状态再动手**（v0.38 实录）：① 完成通知可能延迟几十分钟才送达（一号早已通过 log 监控处理完现场），收到时**先核实当前状态**（worktree/合并情况/接力是否已发），已处理过的按第十二节「重复消息处置」不重做；② 通知里的 summary 超长时中间被截断（`[... middle omitted — see footer ...]`），截掉的往往是**关键遗留清单**（已引用未定义的 i18n 键名单、未换肤的子组件列表、必须保留的测试 class 名）——必须 `read_file` 通知给出的 `subagent-summary-*.txt` 全文路径，把遗留项逐条并入接力 context 或审核清单，不可只凭截断版行动。
- **左右双通道角色错位**（v0.38 实录，用户连发两次「所有人都在待命」）：用户左侧并行开着 Hermes 角色会话（真实「角色窗口」），一号的子代理在右侧、用户不可见——两个通道的角色不是同一批，用户看到左侧待命是真的。当用户坚持「没派工」而子代理证据在跑时，不要只重复证据——点破机制：左侧会话待命 = 用户没贴开工指令；右侧子代理 = 一号已发的活。并给方案 A/B 让用户选：A) 子代理继续干到底、左侧会话别启动（推荐）；B) 停掉子代理，一号给出逐角色可复制的开工指令（见第九节），用户手动启动左侧会话。**无论选哪个，同一任务两通道不能同时开工**（同一 worktree 两个执行者 = 分支占用/文件互踩）。选 B 时先停干净所有在跑子代理再给指令。
- **同一抱怨连发三次 = 停止解释，直接切机制**（v0.38 实录）：用户第三次发「你现在一个工都没有派出去」时，再验活、再贴证据表已无效——前两轮都这么做了用户仍不买账，说明他认定的事实框架（左侧会话 = 唯一工作通道）不可动摇。此时正确动作：① 不再重复证据陈述，一句话承认双方视角差异；② 直接执行通道切换——请用户 `/stop` 杀掉一号侧子代理（或一号等用户停），然后给出逐角色可复制的开工指令；③ 在途半成品按第二节第 7 条由一号亲自收尾合入，不因通道切换丢弃已验证的产出。判断标准：同一质疑第 2 次出现时点破机制+给方案，第 3 次出现时无条件切方案 B，不再辩论。
- **派工能力会随宿主消失——先验工具还在再承诺并行**（v0.38 实录）：delegate_task 是子代理工具，**宿主会话被 /stop 或异常退出后，当前会话的派工能力可能直接消失**（工具列表里没有 delegate_task 了）。实录：用户 /stop 后一号连续敲了 5-6 条无意义的 terminal 命令（echo go / dispatching / final-check）试图重新派工，全部空转，几轮后才承认工具已不在。规则：① 会话恢复后若计划继续并行派工，**第一个动作确认 delegate_task 仍在工具列表**，不在就立刻切串行模式；② 串行模式的两种形态——a) 一号亲自当执行者按序做（先旗舰任务），每个断点做完成功锁定一段再续下一段；b) 写好逐角色开工指令交给用户手动启动左侧会话（见第九节），一号保留审核合并；③ **绝不空转**：发现自己在反复发没有实质内容的命令（echo/占位符）= 能力缺失的信号，立即停下向用户说明现状 + 给出 a/b 选项，而不是继续敲。

## 四、前端浏览器实测快速通道（画师端）

验证画师端交互（时间条、看板等）时的最短路径：
1. 后端不用本地起——容器 `commission-web` 已占 3000（本地 `npm run dev` 会 EADDRINUSE），vite proxy `/api` → localhost:3000 直接通容器。
2. worktree 的 `web/` 起 vite（`npm run dev`，5173）；server 依赖缺失不影响前端实测（除非要测后端新代码——那必须等合入后容器重建）。
3. 登录：浏览器进 /login → 输 QQ 10001（Alice）→ 获取登录码 → `docker logs commission-web --tail 5 | Select-String 登录码` 读码 → 登录（开发模式页面 alert 也直接显示码）。
4. 会话易掉（navigate 后回到 login 页）：掉了就重走登录，一分钟的事，别纠结。
5. 合成 PointerEvent 拖拽要先 patch `setPointerCapture`（详见 playwright-ui-diagnosis 技能）。
6. 实测改动了演示数据（拖日期等）要在交付报告里披露，或测完撤销恢复。
7. **不可见效果用 getComputedStyle + 尺寸差取证**（v0.38 F3 实录）：截断/隐藏/覆盖这类肉眼难判定的效果，浏览器工具截图说服力弱，用 `browser_console` 跑 JS 取硬证据——如验证 CSS 多行截断：`getComputedStyle(el).getPropertyValue('-webkit-line-clamp')` 读数 + `el.scrollHeight > el.clientHeight` 判实际被截（154 > 58 即截断生效）+ 元素存在性/可见性断言。返回的 dict 直接写进交付报告/审核记录，比截图客观。同理适用于：z-index 遮挡（elementFromPoint）、sticky 生效（position 计算值）、暗色主题色值（backgroundColor 计算值对照 token）。

## 五、派工前冲突核查（并行盘面下的必检项，v0.36 实例）

给任何角色（子代理或左边角色）派工前，逐文件核查是否与**正在运行的子代理**冲突：
1. 列出所有活跃子代理的授权文件清单（各自的派工文件/comms）。
2. 新任务涉及的文件与之有交集 → **不派**，标记"等 X 合入后派"写进 STATUS 波 2 候选。
3. 典型撞车点：locales/zh-CN.js + en.js（几乎每个前端任务都改）、QueueBoard.vue、api/index.js。
4. 零冲突的活优先派给空闲角色：纯 server 小修（死码/校验）、纯 docs（说明书/changelog）、独立组件新文件。
5. **派工前核销候选清单的过时项**（v0.22 教训的持续重演）：STATUS/波 2 候选里的"待做项"可能早已完成——派工前逐个 search_files/read_file 核实代码现状。实录（v0.36 波 2）：候选有"四号归档清单执行"，核实发现三个文件**已在 archive/**，再派即重复劳动；"task-0 四项小修"逐项读行号确认真实存在后才派。核实后把过时项在 STATUS 候选清单里划线核销并注明，防下轮再捞。
6. **同文件不同区域可并行，但必须写明合入顺序**：两任务改同一文件的不同区域（实录：五号改 OrderDetail 收款弹窗区、三号-B 改 picker/备注/滑块区）不必串行等待——两路都派，但后合者的派工文件里明确写"**交付后不要自行 merge/合入，等一号安排合入顺序**"，STATUS 角色状态表同步标注顺序（先合者合入 → 后合者 merge master 确认无冲突 → 再合）。授权文件段落同时互相点名"XX 区域一行不许动（某号在改）"。

**用户期望**：一号要**主动盘点并填满并行产能**，不等用户问（用户会问"还有什么别的不阻塞能干的吗"——这是期待你早已想到的信号）。盘点清单：清账池死码、文档漂移、容器重建验证、已拍板待派项、交付报告的遗留项。

## 六、后端改动合入后的容器重建验证（标准门，v0.36 确立）

后端服务层/API 改动合入 master 后，跑一次容器重建 + 真数据验证（不能只靠单测）：
```powershell
# 1. 备份（v38 事故后铁律）
Copy-Item data\commission.db data\commission.db.bak-<版本>-verify -Force
# 2. 重建
cmd.exe /c "docker compose build web 2>&1" | Select-Object -Last 3
cmd.exe /c "docker compose up -d web 2>&1" | Select-Object -Last 2
# 3. 健康 + 数据完好 + 关键路径冒烟
cmd.exe /c "docker compose ps web"   # healthy
cmd.exe /c "docker exec -w /app/server commission-web node -e `"const db=require('better-sqlite3')('/app/data/commission.db');console.log(关键表行数)`""
# 删掉的 API 探 404、新读路径用真数据调一遍
```
v0.36 实例：五号改读路径 + 三号删 API 合入后重建，顺手发现演示订单分期全空（demo-data 绕过 createOrder）→ 派五号-B 修复。容器验证是单测覆盖不到的盲区的探测器。

3. **部署验证（v0.36 六路收口轮新增）**：`healthy` 状态只证明进程活着，**不证明镜像带上了新代码**。容器内通常无 curl/wget（`curl -s http://localhost:3000/api/health` 会报 `curl: not found`），别在这上面耗时间。可靠验证：容器内 grep 本轮新代码的关键标识符——
```powershell
# 先 find 容器内实际路径（可能是 /app/server/src/... 而非 /app/server/dist/...，tsx 直接跑源码）
cmd.exe /c "docker exec commission-web sh -c `"find /app/server -name 'order.routes*' | head -3`""
# 再 grep 关键函数名出现次数，与 master 源码对比（如 24 处 = 一致）
cmd.exe /c "docker exec commission-web sh -c `"grep -c enrichOrderForArtist /app/server/src/features/order/order.routes.ts`""
```
grep 次数与 master 一致 = 镜像确实带入本轮全部修复，可以请用户终验；不一致 = 构建用了旧缓存/旧代码，重查。多路收口轮（6 路合入一次重建）尤其要做这步——用户接下来会按终验清单逐项点，镜像若缺任何一路就是现场翻车。**注意计数口径陷阱（v0.37 实例）**：`grep -c` 数的是「含匹配的行数」，本地 `Select-String | Measure` 数的是「匹配次数」——同一标识符出现次数在两端口径不同时（如一行多次出现）会误报不一致，引发不必要的排查。文件完整性验证用 MD5 哈希才是铁证：`docker exec md5sum /app/server/src/...` vs 本地 `(Get-FileHash <file> -Algorithm MD5).Hash`，一致即确认。

### 两个实测教训（v0.36 画廊灯箱热修，2026-08-05）

1. **重建时机陷阱**：`docker compose build` 必须在**热修 commit 之后**启动。实录：一号先发构建（等合并期间省时间），构建进行中发现新 bug 打了热修——那次构建产物不含热修，白跑一轮，必须重发。规则：发现要热修 → 先 commit + push → 再发 build。宁可串行，不要拿一个不确定包含修复的镜像。
2. **用户重复报同一个 bug ≠ 缓存问题**：用户连发三次"灯箱飘出窗口"，第一轮热修（append-to-body）上线后还在报。不要先归因浏览器缓存——先 grep 容器 dist 确认修复真的在产物里（本例确实在），再用**最坏情况**复测（动画最狠的模板 + 窄视口）。实录：复测发现弹窗已居中，真正的问题是**第二个独立 bug**——el-image 的 preview-src-list 在弹窗上叠了第三层全屏预览被截断（用户截图里的"三层嵌套"）。同一症状两个根因是常见形态：修完一个、用户还报，先验部署、再找下一个根因，别甩锅缓存。

### 容器内 DB 只读取证脚本配方（v0.37 轮，2026-08-05）

需要查容器内 SQLite 实况（如"终态订单的分期数据长什么样"）时，**不要**用 `docker exec ... node -e "...多行SQL..."` 内联——JS 模板字符串的反引号会被 PowerShell 转义吃掉，嵌套引号必碎（实测同一命令三连失败，浪费一轮）。上方第六节的内联示例只适合单行 console.log 冒烟，带子查询/模板字符串就换脚本文件。固定四步：

1. `write_file` 写脚本到 **OS 临时目录**：`C:\Users\<user>\AppData\Local\Temp\hermes-verify-<topic>.cjs`——**不要放项目 workspace-temp/**（v0.37 实录：workspace-temp 下的临时脚本会被会话安全扫描反复标记为「未验证的代码改动」，触发 tool loop warning + 系统反复要求验证/跑测试，浪费多轮）。OS temp 目录干净避开。**必须 .cjs 扩展名**：server 的 package.json 是 `"type": "module"`，`.js` 被当 ESM，`require` 直接 ReferenceError。write_file 的 lint hook 对这类临时脚本会报 MODULE_NOT_FOUND 假错（Windows 路径转义），忽略即可，文件实际已写入。
2. `docker cp <本地路径> commission-web:/app/server/<name>.cjs`——**必须放 /app/server/**：better-sqlite3 的模块解析依赖该目录的 node_modules，放 /tmp 会 Cannot find module。
3. `docker exec -w /app/server commission-web node <name>.cjs` 执行。
4. 收尾三清理：`docker exec commission-web rm -f /app/server/<name>.cjs` + 本地 Remove-Item + `Test-Path` 双确认 False——临时诊断脚本不进 git、不留在容器里。清理后若系统仍重复标记，只做只读确认（Test-Path False + git status 干净），不为已删文件重建任何东西。

脚本骨架升级（v0.37 确立）：**断言式输出**优于裸 console.log——每项检查 `checks.push(['描述', 布尔])`，结尾逐行打印 PASS/FAIL + 汇总 `=== ALL PASS ===`，`process.exit(pass ? 0 : 1)`。好处：一眼判读、exit code 可供命令链判断、可重跑。

### 双库陷阱：相对路径查库会查错库（v0.38 实录，2026-08-05）

仓库里存在**两个** commission.db：
- `data/commission.db`（仓库根）= Docker 挂载的**真实运行库**（迁移版本高，如 v41，演示数据全）
- `server/data/commission.db` = 本地开发遗留旧库（迁移版本停在很早，如 v9，种子数据）

实录：一号在 `server/` 目录下用相对路径 `data/commission.db` 查库验证三号的存量数据统计，打开的是 server/data 旧库（price_addons=0、orders=3），与三号报告（1 行、8 订单）对不上，差点判定三号虚报。换绝对路径查根库后**逐项吻合**。

规则：
1. 查库脚本一律用**绝对路径**打开 `D:/.../artist-commission/data/commission.db`，禁止相对路径。
2. **查库脚本不要 import 项目自己的 `src/db/connection.js`**（v0.38 新形态实录）：connection.js 内部是 `process.env.DB_PATH || './data/commission.db'`——相对路径按**脚本运行时的 CWD** 解析，在 server/ 目录下跑就连到 server/data 旧库，且错误信息（no such column: totp_secret）看起来像迁移没跑，极易误导。两种安全写法：a) better-sqlite3 直接打开绝对路径（`new Database(绝对路径, { readonly: true })`，用 createRequire 从 server/package.json 解析模块）；b) 坚持用 connection.js 则 import 前先 `process.env.DB_PATH = 绝对路径`。
3. 查库前先 `SELECT MAX(version) FROM schema_migrations` 自报家门——版本号与 STATUS 记载的当前迁移版本不符 = 打开错库，立即停。
4. 独立复核角色交付的存量数据结论时，若数字对不上，第一嫌疑是**自己查错库**，不是角色造假——先排除自身误差再下结论。
5. 临时查库脚本写进项目树（即使随用随删）仍被安全扫描标记（v0.38 实录：两轮重复标记 tmp-audit-verify.mjs），印证本节铁律——**脚本放 OS TEMP 目录**（`$env:TEMP\hermes-verify-*.cjs`），不放项目内。

## 七、用户终验反馈轮：取证先行派工（v0.36 终验轮，2026-08-05）

用户逐条报终验问题（"005 订单价格莫名其妙变 200""加项目后收款区变 0"）时，一号**先取证再派工**，把实锤根因写进派工文件，角色拿到即可修，不用重复侦查：

1. **取证工具箱**（按序）：
   - 操作日志表（order_activity_logs）：`SELECT * WHERE order_id=? ORDER BY id`——看 action 序列 + detail_json + created_at 秒级对齐（同秒发生 = 同一代码路径自动触发）。
   - DB 现状：orders/order_notes/order_payments/installments 快照对账。
   - 代码侧 grep 调用方：谁调了 updatePrice / addPayment 等——自动触发路径 vs 手动入口。
   - 容器内跑诊断脚本（docker cp + docker exec -w /app/server，见 windows-agent-environment 技能）。
2. **派工文件格式**：「根因（一号已实锤，不要重新查）」段落写清证据链（日志 id、行号、触发链路）+「任务」+「授权文件」+「验收」。角色省下的侦察预算全用在修复与自测上。
3. **拆并行**：终验反馈往往横跨前端/后端/多页面——按文件授权拆成 N 路（每路独立 worktree + 独立分支），文件交集为零才并行；有交集的排进波 2。STATUS.md 里用一张表列全：角色 | worktree/分支 | 派工文件 | 内容 | 风险。
4. **待用户拍板项单列**：取证中发现的产品决策点（如 done 是否算终态、模板布局调整）不阻塞派工，写进 STATUS「待用户拍板」段，回复用户时逐条呈现。

## 八、杀掉卡死的旧一号会话前的安全检查 + 诊断

用户报"分身（另一个开着一号提示词的会话）卡了几小时/一直在思考/重开也没用"时，先诊断再答复，顺序：

1. **查死因**：`logs/errors.log` + `logs/agent.log` 搜该会话 id 或 `APITimeoutError|Stream drop|timed out`。典型死因组合：API 反复超时/流中断（incomplete chunked read）+ 会话历史膨胀（几百条消息，单轮 latency 上百秒）。重开没用是因为新会话还扛同样的大上下文——杀完后建议用户 /new 开干净会话。
2. **查落盘**：delegation live 目录最新 manifest.json 看子代理批次状态；`git log --oneline -5` + `git fetch` + `git rev-list --left-right --count master...origin/master` 确认产出是否已 commit 且**已推送**（0 ahead/0 behind）+ `git status --short` 主 worktree 干净。
3. **接力复核其产出**（关键，别只做机械检查）：卡死会话若已写了派工文件/commit，一号必须**逐份读派工文件并抽查其声称的根因行号**（search_files/read_file 对照实际代码），实锤才放行。实录（v0.36 终验轮）：卡死的分身写了四路派工，一号抽查全部行号一字不差后才答复"可以杀"，并指出它卡死时"派工已落库但未通知角色开工"——用户需拿着开工指令去各角色窗口。
4. 全部干净才答复"可以杀"；若有半成品（新分支/未提交改动/未推送 commit），先抢救（一号代为 commit+push 或评估）再杀。

```powershell
git status --porcelain        # 主 worktree 无未提交改动
git worktree list             # 所有 worktree 都停在预期 commit/分支（无新分支冒头）
git log --oneline -5          # HEAD 位置符合预期，无新 commit
git fetch origin --quiet; git rev-list --left-right --count master...origin/master   # 0 0 = 已推送
search_files docs/comms       # comms 无半成品派工（只有 STATUS = 干净）
```

判断标准：旧会话若"思考中"未产生任何落盘产物（无 commit、无文件、无分支），杀掉零损失。杀完第一件事：更新 STATUS.md 声明"接力完成，现场已核实干净"，防止下一轮重复排查。

## 九-甲、角色 worktree 混入他人改动的诊断与恢复（五号 enrich 污染实录）

角色报"别人的活出现在我的 worktree"+"大量测试失败（如 32 个 500）"时，一号先取证再答复，**不要让角色继续自行侦查**（他会追错误假设耗预算）：

1. **判断污染模式**：`Select-String <文件> -Pattern "函数名\("` 数调用次数，`-Pattern "function 函数名"` 数定义次数。「有调用无定义」= 别处的改动被**部分**带进了他的文件（调用在、定义丢），不是谁漏写。
2. **查 HEAD 位置**：`git log --oneline -2` 对比 master——污染常发生在角色 worktree 基线落后于 master 期间，他人改动经某种中间态渗入工作树。
3. **恢复步骤（写进打断指令）**：① `git checkout -- <被污染文件>`（只还原这一个文件，角色自己的其他改动全保留）；② `git merge master` 拉入完整版；③ 重跑测试确认基线；④ 继续原任务。
4. **打断格式**：「一号打断：停止侦查，根因已实锤」+ 事实链（编号列证据）+ 照做的恢复步骤 + 顺带确认角色自己的工作无受影响的部分。让角色立刻从侦查态切回执行态。
5. 事后核查：角色 merge 后再去现场确认（调用/定义次数恢复、被污染文件不再出现在 git status），确认自愈才不再跟进。

## 九-乙、交付文件位置不固定——审核前先定位

角色说"转交一号，文件：docs/comms/0X-to-01-..."时，该文件可能在三个位置之一：① 角色自己的 worktree 的 docs/comms/（已随 commit 落库，三号模式）；② **主仓**的 docs/comms/（角色直接写进主 worktree 未提交，五号-B 模式）；③ 两边都没有（只在消息里）。定位顺序：先 `git show --stat <角色分支最新commit>` 看 commit 里有没有，再 `Get-ChildItem` 主仓 comms 目录。找到前不要假设内容，更不要基于文件名猜。

## 九-丙、两类交付的专属审核清单（v0.36 实录）

**A. 抽取共享函数覆盖 N 个端点的重构**（B1：enrichOrderForArtist 统一 21 个端点）：
1. 函数定义必须在 diff 内（防"只写调用没写定义"——这正是五号撞的污染形态）。
2. grep 残留：`return.*旧包装函数|return orderService|return orderGalleryService...` 确认无漏网端点；唯一例外（如创建端点）要求交付说明里写明理由并核对消费者确实不覆盖页面数据。
3. 语义零变更核对：新函数体逐行对照原实现（`?? 0`、`final ?? total`、不为负等兜底必须原样）。
4. 顺手修的隐藏缺陷（如某端点此前连签名 URL 都没有）要在交付说明里显式声明，一号单独确认该改动合理。

**B. 前端校验放宽/收紧**（P 批：收款弹窗去钳制）：
1. **逐条对照后端规则**（读 service 源码而非凭记忆）：0 拒/负数带 note/负数不超已收/正数无上限——前端必须是后端子集。
2. 被删的拦截分支，确认其错误提示键**没有变死键**（grep 该键的其他引用点）。
3. 保留的守卫要亲眼看到（grep payRefundExceed 等仍在提交校验路径里）。
4. 用户点名的禁词（如"小费"）全局 grep 确认——**警惕英文子串假阳性**：`tip` 会匹配 multipliers/timeout，看匹配行内容再下结论，别只看匹配数。
5. 新增的边界测试（如多收节点推算 TC-INST-06）读断言细节：数值、回退路径都要覆盖，不是只断言"不报错"。

**C. 纯文档轮交付**（四号：changelog 补段 + 说明书漂移修复）：
1. 先读交付报告里的「角色自报偏差」——角色核代码常会纠正一号派工文件里的事实错误（实录：一号派工写时间条缩放"月/季/半年/年"，代码实锤 2w/1m/3m/6m；写"拖拽守卫 7 处"，代码实锤 8 处挂载点）。一号要**认可并抽查**这类纠正（抽 1-2 处代码确认），代码为准，派工文件不为准，没有面子问题。
2. changelog 条目逐条对照 git 实锤（交付报告应列每条的合入 hash）；格式对齐上一版本段落（分节/加粗/测试数箭头）。
3. 说明书漂移修正逐条读改动前后文案，确认改后描述与代码现状行为一致；同时看「核查过无漂移的点」段——角色要声明核查范围，不能只报改了什么。
4. 授权边界：`git show --stat` 确认只动授权文件（文档轮容易顺手改别的）。

**D. 新增后端限制性守卫**（五号：updateFinalPrice/deleteExtraItem 终态校验）：
1. **唯一路径检查（派工前就要做，审核时复核）**：被拦动作在目标状态下是否还有替代路径——逐条核对同类操作的全部入口与 schema 约束。实例：done 减价，负增项被 `priceCents minimum:0` 拦死、负收款只退钱不调总价 → updateFinalPrice 是唯一减价路径 → done 守卫不能先上，必须与替代机制（负条目）同批，本批只拦 delivered/cancelled。
2. 时序裁决写进派工 + STATUS「裁决」段：为什么现在不拦、什么条件解锁（与 X 机制同批上），防止下轮有人"顺手补全"把窗口封死。
3. 「有意不拦」三重钉死：① 代码注释写明设计意图与解锁条件；② 显式**正向**测试断言不拦状态返回 200（防将来误锁，比"没写拦截测试"可靠得多）；③ commit message 写明。
4. 守卫位置与顺序：错误返回顺序不泄露信息（如先 404 item 归属再 400 终态，与鉴权链一致）；复用现有错误码，不新增（除非派工明确授权——其他角色可能在改错误码文件）。
5. 测试断言质量：被拦截用例要断言**数据确实未动**（再查 DB 核对），不是只断言状态码。

**E. 需求草案/spec 文档轮交付——时效漂移检查**（四号 REQ-025 第二阶段草案实录）：

角色写草案时基于**派工时刻的 master 快照**，期间并行角色的修复可能已合入——草案中「现有代码缺口」类描述（如「XX 零状态守卫，需补」）会过时。实录：四号草案两处标「deleteExtraItem 零守卫」「updateFinalPrice 零校验」，而五号守卫批已在草案写作期间合入 master。

1. 审草案时凡涉及「现有代码缺口/现状」的描述，**逐条对照当前 master 核**（grep 守卫/函数是否已存在），不信任报告写作时点的快照——草案自带的行号实锤表也要抽查，行号准≠现状描述新。
2. 发现漂移：**合入后一号直接修正文档**，改成「已由 XXX（commit hash）合入，剩余缺口仅 YYY」——漂移是时序问题不是质量问题，退回重写浪费一轮，还会打击角色自查行号的积极性。
3. 修正在收尾 commit 落库，message 写明「修正 N 处时效漂移」，给后续读草案的第二阶段执行角色留审计线索。
4. 预防：派工文件写「行号以合入时 master 为准」（角色通常自发会写），但审核时仍要核——角色无法预知并行合入。

**G. 纯函数引擎/算法核心交付**（三号：REQ-025 计价引擎第一阶段，440 行引擎 + 49 测试 + 迁移）：
1. **逐行读实现**（不跳过任何函数）：对照规格文档逐规则核对语义——锁价"先到先锁"、分摊取整方向（floor vs round）、尾差归属、负值下限、镜像方向。算法命门（守恒断言、取整尾差）必须亲手推演一遍数值。
2. **逐条读测试断言**：边界案例是否全覆盖（规格里的案例 1~N 逐案例对应）；守恒破坏用例是否**分别**破坏每条断言（不能只破坏一条就声称覆盖全部）；显式正向断言（如"done 不拦 → 200"）比"没写拦截测试"可靠得多。
3. **独立重跑全套测试门**（worktree 内）：测试 + tsc + `npm run lint`（**必须用项目配置的 lint 脚本**，直调 `npx eslint <file>` 在 flat config 下会报 "no matching configuration" 假 warning）。注意项目可能无 build script（如 tsx 直跑源码的 server），别浪费时间找 `npm run build`。
4. **merge master 后在 worktree 重跑**：角色基线可能落后 master（并行角色已合入守卫/文档等），合并态测试确认无交互冲突。
5. **迁移验证**（容器重建后）：schema_migrations 有版本记录 + 表/索引存在 + 既有数据完好（行数/关键表非空）。写只读 .cjs 脚本跑（见第六节配方），**不要用内联 node -e**（模板字符串反引号会被 PowerShell 吃掉）。
6. **容器文件完整性用 MD5 哈希**：`grep -c` 按"含匹配的行数"计数，本地 `Select-String` 按"匹配次数"计数，口径不同会误报不一致。`docker exec md5sum` vs 本地 `Get-FileHash` 一致才是铁证。
7. **角色声明的超授权改动逐条审**：如 setup.js 加一行 cleanDb——测试隔离必要可接受，但交付报告必须声明，一号确认合理性。
8. **角色上报的规格修正要验证**：如三号指出 R11.2 守恒公式在关单后场景不严格成立，改为含额外项版本——一号要拿数值推演确认修正合理（不是盲信也不是盲驳），合理的记入 STATUS 踩坑段 + 规格文档待修订标注。

**F. 零代码实测/回归验证报告**（二号：v0.36 六路回归实测，纯浏览器操作 + 报告）：
1. **数据还原声明必须查库对账，不信报告**：角色声称"演示数据已还原"时，用容器内只读脚本（见第六节配方）逐项核：基线订单金额/已收回到基线值、造的测试单已 cancelled、收款流水净额 = paid_total（收撤成对）、增项无本轮残留。实测实例：报告声称 ALICE-006 还原基线，查库确认 final=31000/paid=17640 与基线一致 + 3 个测试单全 cancelled + 流水净额归零，才采信。
2. **意外残留数据用时间戳溯源再下结论**：对账发现报告未提及的数据（如莫名增项）不直接判角色遗漏——查 created_at：早于本轮开工时间 = 更早轮次（用户终验等）遗留，排除嫌疑并在收尾说明里记一笔，防下轮再疑。实测实例：ALICE-006 两条 teasttt/testtta 增项，时间戳 08-04 早于本轮，排除。
3. 实测证据质量分级认可：页面文本断言 / 请求计数断言（连点 3 次仅 1 个请求）/ 合成事件 + 对照组（拦截路径与放行路径都测）是强证据；报告应逐条附证据形态。
4. 「非阻塞观察」段单独收进 STATUS（文案误导、疑似自动化环境问题），不进 bug 清单，随下轮捎带。

## 九-丁、角色上报「顺手发现的预存问题」——先对 master 验证，再谈立项（v0.36 实录）

角色浏览器实测中常顺手发现与本任务无关的预存 bug（三号-B：删备注后响应缺 currentStageId 导致操作条跳分支）。处理纪律：

1. **不直接进 backlog、不直接派工**——先对**当前 master** 验证该问题是否还存在。同轮其他合入可能已经修掉它（本例：B1 的 enrichOrderForArtist 已让 deleteNote 走统一增强，getStageInfo 返回值就含 currentStageId，master 上问题已消失）。验证方法：追代码链路（端点 → 包装函数 → 字段来源），不要只看字段名 grep。
2. **容器时滞视角**：角色实测用的容器/环境往往是本轮合入**之前**的镜像，他的观察是准确的但可能已过时。判断"观察真 + master 已修"的形态：他的复现细节与旧代码行为完全吻合，而新代码路径已覆盖。
3. 验证为"已被覆盖修复"的处置：不立项，在 STATUS 写一行「该问题已被 X 覆盖修复，容器重建后可验证」+ 把容器重建列为待办（多轮合入期间容器持续滞后于 master，**不要每合一路重建一次**——攒到一轮收口一次性重建，STATUS 记录滞后范围，重建时一并验证）。
4. 验证为 master 仍存在的：进已知遗留表或波 2 候选，注明发现者（给角色正反馈，鼓励继续上报）。

## 九-戊、同文件两路并行的合入仪式（第二合者的完整动作链）

约定"五号先合、三号-B 后合"（同改 OrderDetail.vue 不同区域）时，第二合者的放行仪式（一号主导）：

1. 第二合者交付后**不自行 merge**（派工文件已写明）。
2. 一号先审 diff（照常规清单），通过后**代跑**：在第二合者 worktree `git merge master`（预期无冲突——第一合者已合入，两路改不同区域；有冲突则退回让角色解）。
3. merge 后**在 worktree 重跑测试**（web/server 全量）确认合并态绿——第一合者的改动与第二合者的改动共存后可能有语义交互，单看各自 diff 不够。
4. 回主仓 `git merge <分支>` 合入——第二合者已 merge 过 master 时通常是 fast-forward，属正常形态，不必担心没有 merge commit。
5. 立即推送 + comms 清理 + STATUS 刷新（同常规流程）。

## 九、开工指令的交付格式（用户"轻松复制"要求）

多路派工落库后，用户要逐窗口去给左边角色发开工指令。一号直接给出**每角色一段、整段可复制的纯文本块**（code fence 包裹），每段包含四要素：① 派工文件路径 ② 工作目录/worktree（未建则附自建命令）③ "第一步 git merge master 再读派工" ④ 风险等级 + 授权边界提醒。不要让用户自己拼。同一轮所有角色的指令一次性全给。

**外部窗口执行模式下：派工文件落库 ≠ 已派工，指令文本必须出现在给用户的回复里**（2026-08-05 第二轮实录）。执行模式切为"用户外部窗口开工"后，交付链条是：worktree 建好 → 派工文件 commit+push → **回复中贴出每角色可整段复制的指令段**。实录教训：五号文档同步批的派工文件 commit 并推送了、worktree 也建了，但回复里只写了"文件已落盘"没贴指令文本——用户根本没看见，下一轮用户说"五号或者其他的开工指令我还没看见，所以现在 2345 都空闲了"，四个角色白等一轮。规则：**凡本轮 commit 了新派工文件，同一轮回复必须附上该批的粘贴用指令**；落盘只是交付的一半，指令文本到用户手里才是派工完成。用户报告"没看见指令/全员空闲"时，第一反应先补发指令文本（不辩解），并核对该批 worktree/派工文件仍有效。

## 九-己、合入/推送动作链不要前置 `cd`——靠 workdir 参数定位（v0.37 实录）

在主仓执行 merge/push 时，terminal 的 `workdir` 参数已经把 cwd 设到主仓。**不要在命令前加 `cd ..` 或 `cd <path>` 链**——实录：`cd ..; git merge ...` 把 cwd 带到了 workspace 上级目录（不是 git 仓库），整条链报 `fatal: not a git repository`，白跑一轮还要重发。

规则：git 操作一律靠 `workdir` 参数指定仓库根，命令体里不写 cd。若确需跨目录（如先在三号 worktree merge 再回主仓），分两次 terminal 调用、各自带正确 workdir，不用一条 cd 链串起来。

## 十、开局轮派工三实例（v0.37 轮，2026-08-05）

### 1. 用户质疑「之前说好的规则」——先查代码再查规格，定位版本归属

用户问「算法不是之前说的收好的节点不再改变的吗？」时，两种错误反应都要避免：① 否认用户记忆（「没这个规则」）；② 把设计内的旧行为误判成新回归（「这是 bug 我去修」）。

**查证三步**：
1. `search_files` 全 docs/ 搜规则关键词 → 定位规格文档（本例：REQ-025 R4 锁价规则，用户拍板记录在文档「对齐记录」节）。
2. 读当前代码的实际实现逐行确认现状（本例：`recalcInstallmentAmounts` 全节点无差别重算，无任何锁定检查）。
3. 对照规格文档的**排期章节** → 确认规则属于哪个版本（本例：REQ-025 明确写「v0.36 清账版不开发本模型」，排 v0.37）。

**回复结构**：规则确实拍板过（引用出处）→ 但排在 vX 未实现 → 当前线上行为是什么（刚读代码确认，不是凭印象）→ 本轮修复是否碰过它（排除新回归嫌疑）→ 给出处置（把该需求提为下一轮第一优先级）。

**要点**：用户的记忆往往是准的（规则真拍板过），差的是「已实现」和「已拍板」之间的版本差。查证后如实说清版本差，既不让用户怀疑自己，也不把设计内行为当 bug 返工。

### 2. 高风险重写派工的分阶段隔离（REQ-025 计价引擎实例）

高风险任务（动计价核心这类命门代码）不一次性派全量，拆两阶段：

- **第一阶段派**：纯函数引擎 + 全量测试 + 建表迁移。派工文件写**死命令清单**：禁改任何现有端点/调用点、禁切现有函数的调用方、禁动前端、禁动 demo-data。交付物合入 master 后**线上行为零变化**（因为没有任何调用方）。
- **第二阶段审过再派**：接端点 + 切流 + 前端展示改造。

收益：① 高风险审核降维成「纯函数 + 测试」审核，守恒断言/取整尾差这些算法命门可以逐行抠；② 合入零风险，不必等发布窗口；③ 第一阶段测试自然成为第二阶段的回归网。

派工文件必写三段：**阶段边界**（越界即打回）+ **实施裁决**（有疑义以规格原文 + 裁决为准，不要自行扩大解释；裁决包括表设计、函数签名划分、哪些写入动作推迟到第二阶段）+ **测试硬指标**（规格里的边界案例逐案例落测试，数值以规格中的纠正值为准——用户口述场景常有算术笔误，规格已纠正的不要用原稿值）。

### 3. 候选清单核销的第三种形态：对撞未来重写

派工前核销候选时，除了「已完成」（过时）形态，还有**对撞形态**——候选任务与已立项的未来重写撞同一片代码：
- 会被重写自然覆盖的（本例：createOrder 分期段去重、旧写路径评估）→ **核销**，并入重写版本的派工验收项，不单独立项（派了就是重复劳动 + 合并冲突）。
- 会生成新数据结构与重写撞车的（本例：ManualOrder 接画风会生成分期，撞新引擎）→ **推迟**到重写切流后。

核销/推迟理由逐条写进 STATUS「候选核销记录」段，防下轮再捞。

### 4. 文档轮取证：git log 重建 changelog 素材

changelog 缺整段时，给文档角色的素材不凭记忆拼：`git log --oneline -1 -- docs/changelog.md` 定位最后一次 changelog 提交 → `git log --oneline <hash>..HEAD` 拉全量合入历史 → 按波次分组、逐条转成用户可感知描述，作为派工素材清单。派工文件注明「这是素材清单不是成稿，行文按既有格式组织；拿不准的条目读对应 commit diff 核实（附合入 hash 列表）」。

## 十一、拍板项处置的两条纪律（v0.37 轮，2026-08-05）

### 1. 用户对拍板项回复极简时，警惕输入法吞字

实录：拍板项「Classic 画廊位置要不要调整」，用户回「Classic 画廊位置。ok」——一号理解为"确认要改"开始取证派工，用户下一条纠正「可能是输入法吞字了，Classic 是正确的」。若当时没先取证直接派工，就是一轮返工。

规则：
- 拍板项收到单字/极简回复（"ok""行""改""可以"）时，**先查代码现状再行动**，用事实核对用户意图是否自洽（本例：现状代码里画廊位置与用户历史拍板的"模板区分度"原则对照）。
- 回复与代码现状明显冲突、或与用户已知原则矛盾时，**一句话反问确认**，不自行选一种解释闷头派工。代价对比：多问一句 vs 一轮返工。
- 确认后在 STATUS 拍板项上写明结论 + 关闭理由（如「用户确认现状正确，输入法吞字，关闭」），防止下轮再捞。

### 2. 拍板项「细说」= 影响面全取证后再呈现

用户说「第二个要展开」时，不是复述问题描述，而是**把该决策的全部影响面查成事实链**再给选项。取证模板（done 终态实例）：
1. 定义源：终态在哪里定义（前端 isTerminal computed + 后端状态机 STATUS_TRANSITIONS + SQL 片段 ACTIVE_ORDER_SQL），三处口径是否一致。
2. 逐守卫点 grep：改价/加项/收款/取消/交付各入口对目标状态的放行与否（服务层校验 + 路由层校验都要看，缺一可能漏判）。
3. 下游消费者：队列计数、名额占用、仪表盘待办、看板——目标状态改动会波及谁。
4. DB 实况对账：容器内跑只读脚本（见第六节配方）查目标状态订单的真实数据形态（如"done/delivered 订单是否带分期"实锤）。
5. 呈现格式：现状事实链 → 改动波及面清单 → 选项（每个选项的行为差异 + 工作量 + 风险），让用户对着事实选，不替用户选。

## 十二、重复消息处置：先核状态，不重做（v0.37 轮，2026-08-05）

用户（或转交链路）有时把**同一条消息重复送达**——实录：四号交付消息连发两次、"敲定 done 半终态 + 四号交付"打包消息重复。一号若闷头按新消息重做一遍，会重复 commit、重复清理、污染盘面。

**处置三步**：
1. **先核实落库状态**，不假设"已处理"也不假设"未处理"：`git log --oneline -6`（合入/收尾 commit 是否已存在）+ `Get-ChildItem docs\comms`（派工/交付文件是否已删）+ `Select-String` 关键结论是否已在 STATUS/changelog。
2. 已办结 → 不重做，一句话告知"该事项已办结（commit hash），刚已复核"，然后继续推进盘面下一步。
3. 半办结（如审核了没合入、合入了没清理 comms）→ 补齐剩余动作，不从头重审。

**关键心态**：重复消息是常态（转交损耗/用户手滑），不烦躁也不加倍干活——它只是一次"免费的状态复核机会"。

## 十三、拆轮派工：零依赖拆路核查 + 高风险接线派工的决策钉死（v0.37 二阶段实录，2026-08-05）

### 1. 零依赖拆路核查：拆路前先验证依赖是否真实存在

把任务拆成 A/B/C 路时，对每个"看起来依赖另一路"的任务，**先 grep 当前 master 验证依赖是否真实**。你以为要等后端新增的字段，可能早就在响应里了——实录：二阶段 B 路（订单级待收总横幅）看似依赖 A 路新 API 契约，grep 发现 enrich 响应已有 `remainingCents`（= 总价 − 已收），B 路实际完全独立、可先合入，不必排在合入顺序后面。这一步直接决定并行产能，跳过它会把能并行的活串行化。同理也用于识别"可提前独立合入"的子任务（如把依赖后端的展示任务拆成"已有字段部分"先做）。

### 2. 高风险核心接线派工：设计决策全部钉死，执行者不另起方案

把已交付的引擎接入现有端点这类高风险任务，派工文件由一号钉死**全部**设计决策：
- **schema 变更与事务安全性判定**：如 locked 持久化 = ALTER TABLE ADD COLUMN（事务内安全；对照 v38 教训——仅重建父表才事务外），显式写明是哪种形态，防执行者误判。
- **真相源归属**：如条目账本是总价真相源、原字段降为冗余缓存 + 守恒断言兜底。
- **旧函数退役清单**：点名（删除函数本体 + 全仓 grep 调用点零残留）。
- **双写策略**（旧表保留做展示层时）：哪一层写哪个表、条目语义（正/冲正）。
- **守卫时序**：哪些状态拦、哪些有意不拦（对照既有裁决段，如 done 减价窗口）。
- **守恒挂载点清单**：所有变动出口逐个列出。

派工结构模板：**引擎函数签名清单**（已交付，import 复用，"不要重写引擎"）→ **编号设计决策**（"照做，不要另起方案"）→ **任务清单分必做/加分**——必做 = 核心规则生效的最小闭环，加分 = 预算允许再做；**每完成一项立即 commit + 跑测试**，防子代理预算耗尽丢失整批进度（接力模式见第二节）→ **授权文件 + 禁碰文件** → **验收**（高风险接线必须要求**守恒实证数值推演**：给一个端到端场景逐步数值 + 每步状态，证明核心规则真正生效，不是只报测试绿）。

### 3. 轮中需求注入的路由（用户在某路进行中追加需求）

实录："注意到如果画师前一个节点忘记收钱，不能把所有待收加起来提示"。四步：
1. 读现状代码确认实情（本例：横幅只显示第一个未收节点的待收）。
2. 复述理解 + 给方案，方案明确就直接定（写明"不阻塞"），不必等回复才动。
3. **写入规格文档**（REQ 文档对应小节）并立即 commit 推送——需求先落文档防丢失。
4. 路由到现有零依赖路（本例：B 路加任务 1），不新开与在途任务冲突的路。若需 patch 已发出的派工文件，必须告知用户转达角色「先 git merge master 再读派工」（追加派工条目教训，见 SKILL.md 检查清单）。

## 十四、STATUS 维护纪律：头部行与正文必须同 patch（v0.37 实录）

两个漂移形态：
1. **头部漂移**：patch STATUS 只改正文段落，文件顶部「最后更新」行还停在上一轮状态（实录：正文已是二阶段四路并行，头部还写"轮开局两路派工"）。新会话开工先读头部，误导恢复判断。规则：**每次 patch STATUS = 头部行 + 当前阶段段 + 角色状态表三处一起改**，无例外。
2. **同名小节堆叠**：STATUS 按轮追加维护，"本轮踩坑记录（下轮派工前必读）"这类标题会出现多份。新写小节标题带轮次标签（如"v0.37 轮踩坑记录"），或并入当前轮已有小节。

## 十五、轮次收口后用户问「我要做什么」的汇报格式

一轮多路全部落库后用户常问下一步。回复模板（不堆盘面细节）：
1. **一件必做**（如终验）：给可逐项点的清单 + 注明哪路已预验过及可信度背书（"二号预验通过，我背书"）。
2. **一件拍板**（如下一版本开工）：给拍板项 + 明确说"拍了我立刻派工"。
3. **快速通道**：允许用户跳过非强制项（"信任预验就直接说开工"），减少用户操作负担。

**变体：用户在某角色转交到达的同时问「我有什么要去做的」**——此时一号要**同回合并行做两件事**：① 正常审该转交（读报告/定位文件/审 diff/合入）；② 给用户一份**按紧急度分级的待办清单**（🔴 今天必须 / 🟡 有空就做 / 🟢 知情即可）。关键：用户不会编程、全靠 AI，**操作类待办必须写成逐步可点的 UI 动作，不是技术指令**——实录：管理员 TOTP 绑定写成「管理后台→画师管理→找到 Admin→点绑定→手机 App 扫码→填 6 位码」，而不是「调用 totp bind 接口」。分级判据：🔴 = 不做会锁死/丢数据（TOTP cookie 过期即锁门外）；🟡 = 推进产能（开 N 个窗口贴指令）；🟢 = 已处理或无需用户动作、只需知情（违规记账、未来某时点一号会再确认）。

## 十六、需求深聊批派工：把所有待对齐话题打包丢四号（v0.37 轮，2026-08-05 用户点名）

用户原话："还有qqbot（或者说消息网关），所有要办的全部写comms丢四号 让他和我深入交流"——用户要集中处理全部需求对齐项时的派工形态。与功能派工的区别：四号此轮的产出是**与用户逐题深聊 + 需求稿**，不是代码。

1. **一号先做完所有能做的取证**（四号不从零查）：每个话题 grep 代码实锤写进派工「现状实锤（一号已查证，不用重新侦查）」段。实例（QQ Bot 话题）：auth.service.ts L63 全项目唯一 TODO + orders.client_notify 字段已在但零消费方 + REQ-014 桌面登录依赖它 + AUTH_DEV_MODE 关闭以它为前提（上线门槛链条）。
2. **话题排序按紧迫度**：上线门槛（阻塞发布）> 已排期等需求稿（聊完即开工）> 下一功能开工前的待确认 > 远期备案（用户主动提才展开，不主动聊）。
3. **每个话题列「要深入对齐的点」**：把真正需要用户拍板的决策项枚举出来（定位抽象 vs 直连、场景范围、技术路线选型、部署/运维形态、风险容忍度、版本归属），四号照单和用户聊，不用自己猜该问什么。
4. **工作原则写进派工**：四号能内部解决的技术核实别转交一号（用户原话原则）；产出为 docs/requirements/ 需求稿（含用户拍板记录：日期+原话要点）；**全部聊完统一转交一号审核，不边聊边合入、不自行 commit 推送**——纯需求任务在主仓工作，不需要 worktree（与功能派工的 worktree 纪律区分开）。
5. **STATUS 同步**：角色状态表更新（四号：进行中 + 话题清单）；既有的「待用户与四号交流话题」盘点段同步核销/更新。

## 十七、worktree 回收的两个陷阱（v0.37 轮实录）

1. **`git worktree remove` 对含 node_modules 的 worktree 可能假报失败**：角色 worktree 里跑过 `npm install` / vite dev（残留 2 万+文件）时，remove 可能报 `error: failed to delete ... Invalid argument`——但实际内容已删净。核实方法：`git worktree list`（该 worktree 已不在列表）+ `Test-Path` 看磁盘残留。**不盲目重试删除**；git 侧干净（分支已删、worktree 已注销）是关键状态，磁盘空壳目录不影响仓库，留给用户手动清或下次会话处理。
2. **手动 rmdir 大目录会触发审批拦截**：对残留大目录发 `cmd /c rmdir /s /q` 这类破坏性命令，可能触发用户审批超时被 block（"The user has NOT consented"）。block 后**不重试、不换命令绕过**——转只读核实（目录里还剩什么、git 侧是否干净），把残留状态如实报告用户（「git 侧已全部注销，仅剩磁盘目录 X 待手动清理」）。git 仓库状态干净才是交付标准，磁盘卫生是次级目标。
3. **删除分支的正常报错是完成证明**：重复执行收尾命令时，`git rm` 报 `pathspec did not match`、`git worktree remove` 报 `is not a working tree`、`git branch -d` 报 `not found`——都是上一轮已完成的证据，不是需要修复的新失败（见第十二节重复消息处置）。

## 十八、web/server 测试命令差异（v0.37 轮确立）

两个子项目的规范测试脚本不同，重跑测试门前先确认：
- `server/`：`npm test`（vitest run，~30s，当前基线 769）
- `web/`：**没有 `npm test` 脚本**，用 `npm run test:web`（vitest run，~2s，当前基线 173）；在 web/ 下跑 `npm test` 会报 Missing script（不是交付问题）。
- server 无 build script（tsx 直跑源码），质量门 = vitest + `npx tsc --noEmit` + `npm run lint`（**必须用 npm run lint**，直调 eslint 单文件在 flat config 下报假 warning）。
- **主仓跑合并态测试前先核 node_modules 新鲜度**（v0.38 实录）：worktree 里开发并 npm install 过的新依赖（如 TOTP 批的 qrcode），合入 master 后**主仓的 node_modules 不会自动更新**——主仓直接跑 vitest 会大面积报 `Cannot find package 'X'`（实录 243 例失败），看起来像合并引入的回归。鉴别：失败全是 import 错误且指向某个新依赖 = 主仓依赖陈旧，`npm install` 后重跑即恢复，不是代码回归。规则：**每轮第一批合入后、跑主仓合并态测试门之前，先 `npm install`**（server 和 web 各一次，耗时几秒），再判绿红。

## 十九、引擎/守恒类接线交付的专属审核清单（v0.37 A 路实录，2026-08-05）

纯函数引擎审核见九-丙 G；**把引擎接入现有端点**是另一种形态，命门不同：

1. **严格断言上线前的存量数据审计（必做，交付角色发现不了）**：守恒断言用严格相等（`!==`）时，引擎合入**之前**生成的数据可能带历史取整漂移（旧代码各自 Math.round，±1~2 分）——这类存量数据一进变动出口就会被误杀。角色写测试只用种子数据，**存量真数据的漂移只有查库能发现**。审核时用第六节配方跑只读脚本：遍历全部订单算 Σ节点价 − 总价 的漂移分布 + Σbp 过滤（断言适用范围），零漂移才放行；有漂移则要求方案带自愈路径（懒回填/首变动时归一）。
2. **跨模块守卫追踪（交付角色视野外）**：新加的状态守卫（如 done 禁改价）可能拦死**其他模块的既有流程**。审核时 grep 该 API 的全部调用方，逐个走一遍状态空间：调用方能否到达被拦状态？本例：ManualOrder「createOrder→updatePrice」两步流，若初始状态可设为 done 则第二步必 400——实锤排查发现状态选项只到 wip，风险排除。排除过程写进 STATUS 验证链（防下轮再疑）。
3. **条目落账收口核对（防双重记账）**：delta 类接线的典型 bug 是「调用方写原因条目 + 引擎函数又写额外项条目」双写击穿守恒。审核点：条目写入是否**单点收口**（一个函数按 delta 去向决定条目类型，互斥分支）；拿交付角色自报的 bug 修复当审核线索——他写测试时发现的 bug 正是最可能漏的形态。
4. **存量测试适配的性质甄别**：接线改语义后存量测试被改动是常态，但要甄别是「语义变更的合理适配」还是「改测试迁就代码」——逐条读改动前后断言：新断言是否是规格文档要的行为（如「定金付清锁后加项只摊尾款」正是 R4/R5）。是合理适配则放行并在 STATUS 记一笔，是迁就则打回。
5. **懒回填机制审核**：存量数据接入新模型的过渡设计（如无账本订单首次变动时补 base 条目）要核对**时序**——本例：ensureBaseEntry 必须在 UPDATE final_price **之前**调用，否则补录的 base 取到新价。这类顺序依赖 diff 里一行注释，漏看就是隐蔽 bug。

## 二十、函数退役验证的注释假阳性（v0.37 A 路容器验证实录）

验证「旧函数已退役删除」时，容器验证脚本用朴素 `content.includes('函数名')` 会**命中注释里的提及**（如「替代 recalcInstallmentAmounts」）误报 FAIL——实录：容器验证 7 PASS 1 FAIL，排查发现残留全是注释，函数定义与调用实际零残留。

**正确验证法**（本地 git grep 双查）：
```powershell
# ① 定义 + 调用残留（函数体是否真删）：exit code 1 = 无匹配 = 已删除
git grep -n "function 函数名\|函数名(" -- server/src
# ② 排除注释行的真实调用残留
git grep -n "函数名" -- server/src | Where-Object { $_ -notmatch "//|/\*|\*" }
```
容器验证脚本里的字符串断言同理改为「正则匹配定义/调用形态」而非朴素包含；或接受误报后按上面双查复核再下结论，不直接判交付失败。

## 二十一、他角色在主仓的在途产物——commit 纪律 + STATUS 标注（v0.37 实录）

需求深聊批这类「无 worktree、主仓 docs/ 直写」的角色，其未提交产物（REQ 草稿、文档修改）会长期躺在一号的工作区里，比共享 worktree 直提（第一节 e04f2f5）更隐蔽——`git status` 里混着 `??` 未跟踪文件和 ` M` 修改，极易被目录级 add 夹带。

规则（第一节纪律的强化版）：
1. 有他角色主仓在途产物时，**每次 commit 前显式核对**：`git diff --cached --name-status` 与本次意图逐行比对，在途文件一个都不进暂存区（本次只 add 具体文件路径，从不 add 目录）。
2. **STATUS 显式标注**：master 状态段写「工作树：干净（X 号在途产物除外：REQ-027/028 草稿 + Y 文档修改，未提交，勿动）」——给下个会话/其他角色留边界。
3. 他角色产物何时合入由一号与其约定（深聊批是「全部聊完统一转交审核」），一号不代提交、不代改。

## 二十二、容器验证脚本的断言措辞（v0.37 实录）

第六节断言式脚本骨架的补充教训：断言项的**语义要精确到能区分合法形态**——
- 「recalcInstallmentAmounts 已退役」这类断言，判定条件写成「无函数定义且无调用」而不是「字符串不存在」（见第二十节）。
- 数值断言带上下文：订单计数断言写 `> 0`（演示数据行数不固定）而非硬编码具体数，除非你刚查过且确认重建不会变。
- 脚本失败（exit=1）时**先本地复核再判交付失败**：容器脚本是探测器不是裁判，FAIL 项逐个用 git grep / read_file 复核，确认是真问题才打回。

## 二十三、全站视觉重设计批的派工形态（v0.38 REQ-026 实录，2026-08-05）

「画师后台整体换肤、客户端零影响」这类跨页面视觉批，派工前必须做的侦查与派工必写的铁律：

1. **派工前侦查共享 CSS 变量的消费面**（决定整个实施策略）：`search_files output_mode=count` 数客户端 views/client + components/templates 里 `var(--xxx)` 的引用数。v0.38 实录：theme.css 变量被客户端 170+ 处引用 → 派工铁律定为「新 token 建独立文件 + scoped 到后台容器，**不改现有变量值**」。不侦查就派工，角色大概率直接改 :root 变量，客户端全破。
2. **冲突裁决写进派工**：设计文档之间、设计与现状的冲突点逐个列出并钉死结论（如侧栏底色 REQ 说按主题切换 vs 提案固定深色 → 以 REQ 为准），不给执行者留裁决空间。
3. **范围外清单显式写进派工**（提案里的新功能形态 ⌘K/通知铃铛等一律不做）——视觉提案 HTML 里的演示功能对执行者是强诱惑，不写就会顺手做。
4. **拆批原则**：token + 骨架 + 核心高频页为第一批（统一组件本批建成供第二批复用），其余页面第二批按 token 推导。两批同 worktree 同分支接力，第一批合入后才派第二批（第二批要 merge 第一批的 token 层）。
5. **审核要点前置写进 STATUS**（一号自己照此验收）：语义色一对一映射不破、统计数字不上色、字体分工边界（文楷只落标题/数字）、客户端零影响（对照验收条款逐条浏览器实测截图）。
6. **关键 UI 决策用 vision_analyze 逐张核截图，不靠肉眼扫**（v0.38 第一批实录）：视觉批交付的截图验收是审核重头（本次 16 张），逐张 `vision_analyze` 提问要**具体到验收点**——不是"看看对不对"，而是"日期卡头右侧 chip 文字和颜色是什么/除逾期提示外其余是否安静克制/客户端页是否完全不像纸墨风格"。高价值核法：
   - **零影响反证**：拿客户端页截图问 vision"是否与后台风格零重合"，比看代码作用域更有说服力（本次实锤青绿现代风 vs 纸墨国风零重合）；
   - **铁律对照**：统计数字是否上色（vision 会指出 `--color-primary` 导致的浅蓝数字——读代码容易漏的映射层溢出效应）；
   - **双主题结构一致性**：问"与宣纸版相比布局是否一致（纯换色不改版）"；
   - 发现的非阻塞瑕疵（数字上色、留白偏大）**写进下一批派工**（"跟进修复（一号审核记的账）"段），不当场退回——视觉批退回成本极高，瑕疵记账随下批修。
7. **派工必写增量 commit 纪律**（v0.38 教训）：大视觉批（token + 骨架 + 4 核心页）几乎必然撞穿子代理约 50 迭代预算——实录二号写完 12 个文件（含 ArtistLayout 重写 519 行）未 commit 退出，全靠接力 salvaged。派工写明「**每完成一个页面/组件立即 commit + 跑测试**，别留未 commit 烂摊子；若撞迭代上限，把已写部分 commit 掉（message 注明进行中）并诚实报告完成度」。派工范围按可独立验收的段切分（token 层/骨架/每页），接力时一号把「现场侦察结论」（已写文件清单 + 未做清单 + 未验证提示）压进下一轮 context，禁止重新侦察耗预算。

## 二十四、只读评估/研究批的派工与审核形态（v0.38 addons 评估实录）

遗留问题「X 表能不能 drop / Y 路径是否合规」这类**决策前置调研**，适合派只读批（风险低、不占代码带宽、产出是结论 + 证据链）：

1. **派工钉死问题清单与结论形态**：每个问题给候选结论枚举（如 Q1 三选一：可 drop / 保留但冻结 / 仍是活表），要求逐结论带证据（文件:行号）+ 存量数据只读统计。执行者不能自由发挥成"顺便重构一下"。
2. **纪律段写死**：零代码改动、零迁移、数据库 readonly 打开只 SELECT、临时统计脚本放 OS TEMP 不进仓库。
3. **审核动作**（v0.38 实录，全部独立复现）：
   - 代码证据抽查：角色报的关键行号/注释（如"v0.36 已删旧 API"）read_file 亲眼看；
   - 全仓 grep 复现唯一性结论（如"INSERT INTO order_payments 仅 1 处"用 search_files 独立数）；
   - **存量数据独立查库对账**（绝对路径 + 迁移版本自报，见第六节双库陷阱）——角色报的每一组数字至少抽查 2-3 组；
   - 报告里的清理草案**只收不执行**：评估批与执行批严格分离，草案排后续版本批次（避免评估者自己既当裁判又动手）。
4. **报告合入后 STATUS 遗留表核销**：把「待评估」项替换为结论 + 处置去向（如"保留但冻结，清理草案排 v0.39+"），防止下轮重复评估。

## 二十五、缓合门控：跨层批次的延迟合入（v0.38 F2 外链后端实录）

后端批改动**现有存储结构/响应形状**而前端消费方尚未同步改造时（F2：链接两列合并，客户端 4 模板页脚 + 设置页还在用旧结构），审核通过 ≠ 立即合入——合入即破坏真实用户环境。派工形态：

1. **派工文件首段写「合并门控」**：明确"本分支交付后不立即合入 master + 原因 + 解锁条件（等 X 前端批就绪后一号统一安排）"。执行者的任务定义改为"做到随时可合状态"（测试全绿 + 交付前 merge master 重跑），不是"合入"。
2. **执行者侧配套纪律**：分支等待期会落后 master（并行批持续合入），执行者若被二次唤起（接力/补漏），第一步仍是 merge master + 重跑测试门，防等待期腐化。
3. **STATUS 角色状态表标注门控**：如「F2 后端已交付，缓合（等前端批）」——防下轮一号自己忘了门控顺手合掉，也防其他角色基于该分支干活。
4. **解锁时合并顺序**：后端先合（契约就位）→ 前端基于新契约开发 → 前端合入。后端含纯 CREATE TABLE 类安全迁移可提前跑；DROP/改列类必须与前端同批。
5. **适用判断**：只增不删（新接口/新表）通常可直接合；**改现有契约形状**（字段合并/重命名/删读路径）才门控。拿不准就门控，代价只是分支多等几天。

## 二十六、计划/拆解文档轮的审核与拍板项拆分裁决（v0.38 四号 REQ-022 拆解实录）

四号产出「实施拆解 + 验收清单」这类为后续批次铺路的文档时，审核要点（区别于九-丙 C 的 changelog/说明书轮）：

1. **代码现状声明逐条验证**：拆解文档的「现状核实表」是后续派工的地基，每条"X 表已存在/Y 接口已有/Z 字段是审核态"都要 search_files/read_file 独立抽查至少一半（本例：artwork_size_tags 已建 ✓、guestbook 三态 ✓、custom_links/platform_urls 两列 ✓ 全属实才放行）。地基错了后续整批派工全歪。
2. **待确认项的拆分裁决**：角色汇总的 N 个待确认项，一号**先自己分掉技术项**——纯技术裁决（删平台的存量链接处理、URL 端口解析、死代码回退分支去留）由一号定案写进下游派工（标"一号已定案"），只把真正的产品决策项（状态门槛、多图语义、已读语义）一次呈全给用户。技术项丢给用户 = 浪费拍板带宽。
3. **开工前置门控要真执行**：拆解文档标了"F5 语义未定不开工"，一号派下一批时核该门控——F5 确实不进本轮派工。文档写的前置若派工时不核，等于没写。
4. **审核工具类文档合入后保留**：验收清单是一号审交付时的操作工具，**不适用 comms 合入即删**——保留到被消费（交付验收完成）后再删。派工/交付文件合入即删，工具/计划文档按用途保留，两类别混。
5. **合入后发现文档与已拍板结论冲突的过时表述，一号直接 patch**：本例验收清单还标"缓冲位用色待对齐"而一号已在二号派工拍板 --buf 灰。直接修正 + 随下个 commit 落库，不退回重写（同九-丙 E 时效漂移处置）。

## 二十七、空闲产能盘点 + 决策项呈现（用户问「还有什么能派的 / 要我决策的吗」，v0.38 F5/F2 收口实录）

主力批次在途（如二号视觉批还要很久）、部分角色空闲时，用户会主动问「还有什么可以派的 或者要我决策的吗」。这是期待你早已盘好的信号（见第五节用户期望），标准应答流程：

1. **盘之前先查证，不信候选列表**：对每个「看起来可派」的项 search_files/grep 验证代码现状（见第五节第 5 条过时项核销）。实录：死键 sendCode/codeSent 核实确实还在、addons 冻结结论未变，才敢往下安排。
2. **结果分三桶**：
   - **(a) 现在就能派**：低风险 + 与所有在途批次零文件交集 → 当场派掉。典型安全形态 = **docs 同步批**（授权仅 `docs/`，零代码风险）：一号先 grep 出全部漂移点（文件:行号 + 改前改后方向）写进派工文件，角色不用从零侦查；建 worktree → 派工文件 commit + push（角色开工 merge master 拿得到）→ STATUS 角色状态更新。
   - **(b) 要用户拍板**：真正的产品决策项（语义选择 a/b/c、配置开关时机）**一次性全部呈现**（用户偏好「整个出来一起看」），每项给选项 + 工作量/风险 + 一号倾向（让用户对着事实选，不替用户选，见第十一节第 2 条）。呈现代理/配置类决策前先查实际值（如 AUTH_DEV_MODE：读 .env + `docker compose exec -T web sh -c 'echo $AUTH_DEV_MODE'` 单引号防本地展开），让决策框定在事实上。
   - **(c) 真没活**：技术依赖造成的等待（F1 等 v0.38 合入防撞车、F2 前端等门控解锁）如实说清是依赖不是没排——**不硬造活**，给空闲角色编任务反而添乱。
3. **回复结构**：已安排表（项/状态）→ 要拍板项（编号，含倾向）→ 顺带观察（不用用户管的小事，如角色 worktree 里的临时文件会在交付时核对）。
4. **docs 漂移批的取证模板**（派工文件主体）：每条漂移写「文件 + 大致行号 + 旧描述 + 要求按代码现状改 + 代码依据位置（grep 哪个文件确认）」，并注明「行号可能随版本漂移，改前先 grep」；验证段要求 grep 复查关键词在 docs/ 的残留（changelog 是历史账本不改、archive/ 不动）；交付报告逐条「改前→改后→代码依据（文件:行）」。
