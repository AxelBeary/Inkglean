# 子代理接力重派 + 用户侧并行角色（"左边"）协作

> 2026-08-05 v0.36 波 1 实战总结。SKILL.md 已超尺寸上限，新知识存此处。

## 一、子代理撞迭代上限（max_iterations）的接力恢复

delegate_task 子代理会在半路停住：侦察做完没落码，或代码写一半。判定：live transcript 末尾出现 `end status=completed exit_reason=max_iterations (iteration budget exhausted)`。

恢复流程（本次三轮验证有效）：

1. `Get-Content <live_transcript> -Tail 8` 看停在哪一步
2. 进 worktree `git status --short` + `git diff` 盘点已落盘内容
3. **审核半成品 diff：质量过关就先固化为 commit**（一号亲自补完缺口部分，如子代理改了组件但漏了 i18n 键，一号补键后一起 commit）——进度不落空；质量不行才 `git checkout -- <file>` 丢弃
4. 重发 delegate_task，context 里必须写：
   - "**侦察已完成，本轮直接编码，禁止重新大量读文件，把预算留给编码和测试**"
   - 附前一轮侦察结论（精确文件+行号+改法），任务清单只列剩余项
   - 明确"第一步只做一个动作：git merge master"
5. 若任务两次撞顶 = 任务太大，**拆小分轮派**（本次：四档缩放一轮、撤销 toast+小修一轮）
6. 子代理最终 summary 可能不落盘（文件为空）——以 worktree 实际 git 状态为准，不依赖 summary

## 二、用户侧并行角色（"左边"）协作

用户常在另一个聊天窗口开着同编号角色实例（"左边"）。

**红线**：
- 左侧角色绝不许进一号子代理正在使用的 worktree——派工前把 `git worktree list` 结果报给用户
- 一号的子代理对用户完全不可见（用户原话："右边子代理我完全看不见 得你自己监视"）——定期 tail live transcripts、主动汇报进度是一号职责，不等用户问

**派活判定**（用户问"还有什么能并行做的"时逐项对照）：
- 与在途子代理**零文件交集**（locales、api/index.js、QueueBoard.vue 这类高频文件尤其注意，多个波次都会碰）
- 不违反合并顺序（改同一文件的任务必须等前一波合入，哪怕逻辑上独立）
- 冲突的任务记入 STATUS 波 2 候选并标注"等波 N 合入"

**左侧角色适用任务类型**：
- 单文件低风险（文档修正、changelog、死码清理）→ 特批**主 worktree 直提 master**（soul 权限外的文件在派工里写明"一号特批授权，仅限本文件"）
- 多文件功能 → 独立 worktree + 分支，仍走一号审核合并

## 三、派工前验证的补充（本次新踩）

- 清单里的"待做项"可能已被前序版本完成或已不存在（本次：L5 i18n 空字符串实际为 0、TplCoverShowcase 已不存在）——派工里直接写"一号已验证：实际状态 X，照此执行/跳过"，不让角色盲做
- 死代码删除清单必须逐项给出引用核实结论（哪个文件仅被测试引用→连测试一起删）
- **波次候选清单同样要逐项核实现状再派**（2026-08-04 终验轮实战：STATUS 波 2 候选 5 项，核出 1 项已完成——归档三文件早已在 archive/、1 项需缓派——与在途分支文件冲突，真正可派只有 2 项；不核实就会重复派工浪费角色）。核实手段：grep 行号锚点 + read_file 看现状。候选清单是"当时记的想法"不是"当前可执行清单"；核销项在 STATUS 里划掉并注明原因，防止下轮重复核实
