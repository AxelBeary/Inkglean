# 并行角色会话协调（用户自开的"左边"角色 / "触发口令"）

用户常在别的 Hermes 会话自开二号/三号/五号（口头："我左边也开了2345"）。角色执行窗口的派工触发语格式 = **每角色一行**（见 `templates/user-side-dispatch-template.md`，旧的子代理 delegate_task 模板已废弃删除）。两路角色并存时的协调协议（2026-08-05 v0.36 开工实战总结）：

1. **worktree 互斥**：一号子代理各占独立 worktree（`git worktree add -b`，命名如 artist-commission-02 / -w3 / -w5）；必须明确告知用户左边角色**禁止进入这些目录**——两路同改一个 worktree 必互相踩踏。汇报里把红线说清楚（哪几个目录、为什么）。

2. **左边角色派零冲突活**：文档类最安全（changelog 补全、docs 归档盘点、需求整理——如本次四号补 v0.28~v0.35 八个版本断档的 changelog）。与波 1 改同一批文件的执行类角色让左边待命，波 1 合入后再派波 2。判断标准：波 2 候选若触碰波 1 在改的文件（locales、同一组件如 QueueBoard.vue），现在并行必撞车。

3. **多份派工互查**：派工 A 引用了角色 B 的配套任务（如三号写"前端封装由二号删"）时，写完全部派工后必须交叉核对 B 的派工确实含该条目，漏了立即 patch 补上（本次实战：三号派工引用了二号的 L0 删封装任务，二号派工初版漏写，写完互查发现后补 patch）。

4. **验证结论写进派工**：派工前 search_files 实证清单项的时效——组件是否已删、行号是否漂移、处置是否被用户拍板改变（如"死代码"清单里某项已被方案转正不能删）。把验证结论直接写进派工（如"一号已验证：前端零消费"、"TplCoverShowcase 已不存在跳过"），并要求角色执行前各自再确认零引用。盲信旧清单 = 角色删错东西或白干活。

5. **子代理拉起后的汇报**：告知用户并行盘（谁在哪个 worktree 干什么），以及用户侧可做的零冲突事项。子代理结果以单条汇总消息回流，勿轮询。

6. **四号类文档任务的授权特批**：changelog.md、docs 归档移动等不在四号默认文件权限内，派工时需在文件里写明"一号特批授权，仅限本次"。

7. **需求深聊批与开发派工同域 = 先定稿再派开发（D 路时序缺口实录，2026-08-05）**：当需求整理角色（四号）正与用户深聊**某功能**的需求稿（REQ-029 录单接画风），而同一功能你又要派给开发角色（二号）实现时，**绝不能**用"早期不完整派工"先把开发拉起来。实录：一号基于早期派工给二号 D 路（只含三级选择/单画风退化/算价等基础项），四号与用户聊完才定稿 REQ-029（新增 R2 自定义提示 / R5 自定义增项 / R6 图片开关 / B2 取消选中四项用户拍板功能）。二号实现全部漏掉这四项——**不是质量问题，是派工早于需求定稿的时序问题**，根因在一号，需另发补漏批返工。
   - **规则**：需求稿未定稿的功能点不进开发派工；若开发确需先动（如基础接线不依赖新拍板项），派工里必须显式写"本派工仅覆盖 X，REQ-XXX 其余功能以需求稿定稿为准，定稿后一号补派"，并在 STATUS 记录该欠账。
   - **审核侧配套**：开发交付后，若其间需求稿已定稿，审核必须**逐条对照需求稿 grep 实证**（不能只看"跑通了"），缺口单列成补漏批，且向用户讲清"根因是派工时序，不是角色失误"。
   - 判断标准：派工引用的功能域，是否有一个**尚未定稿**的 REQ 正在被四号与用户讨论？是 → 缓派开发，或限定派工范围 + 标注欠账。

8. **审核四号的需求文档批（含重大决策变更的传播核对）**：四号与用户深聊后一次交付多份 REQ 稿 + 对既有文档的回写/传播。审核与代码不同，重点是**决策一致性**而非逻辑正确性。实录（2026-08-05 登录 QQ Bot → TOTP 变更）：
   - **逐份通读新 REQ 稿**，重点看：决策是否有用户原话锚点、边界案例是否覆盖、"待确认项"是否已显式标注并指明由谁拍板（不要把悬而未决项当成已定）。
   - **传播核对（关键）**：一个重大决策会波及多处文档/代码。核对四号的传播是否**完整**——它改了哪些（REQ-014 登录描述 / REQ-022 回写 / 待修复清单 L4 消解）、它**无权改而转交**的（技术文档 CONTEXT.md、开发→生产指南 → 一号/三号；代码 TODO → 实施角色）。把这些转交项记入 STATUS 待办，别丢。
   - **回写类用 git diff 看**（REQ-022 四个待确认回写、外链 F2 重写），确认回写的是用户拍板内容而非四号臆测；注意范围扩大项（外链"打磨"→"重做"、工时 1 天→2~3 天）要向用户复述确认。
   - **决策变更的连锁影响**要主动替用户点明：如 TOTP 使"QQ Bot 发码"这一原上线门槛消解、AUTH_DEV_MODE 关闭不再依赖主消息渠道——这类"门槛易主"是用户最需要知道的，写进 STATUS + 汇报。
   - 落库时把新 REQ + 传播修改 + 交付报告一起 commit，派工文件删除（合入即删）。

9. **角色窗口静默 = 先查 worktree 再催（2026-08-05 两次实录）**：用户说「X号没在工作」或某角色迟迟不转交时，**先自查证据再问用户**：
   - `git log` 该角色 worktree 分支——可能活已干完（commit 都在）只是窗口没转交（五号打磨第二批实录：3 个 commit 静静躺在 polish 分支）。
   - 主 worktree `git status` 的 untracked——只读核实批的角色常在主仓跑，交付报告会直接落在主仓 docs/comms/ 未入库（五号三份核实报告实录）。发现即读+消费（行动项提取进 STATUS 后合入即删）。
   - 角色重复报告已合入的旧批次 = 窗口消息滞后，排除即可不必重审（三号重报 addons 第一批实录）。
   - 查完确认真没产出，才请用户重发触发语或重开窗口。
