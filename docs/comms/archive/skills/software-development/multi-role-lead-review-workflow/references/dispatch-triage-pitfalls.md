# 分诊/派工陷阱速查（v0.36 波 1 增补）

一号在派工阶段的五个高频陷阱与对策。

## 1. 「之前提的 X 做了吗」状态核实

用户问某功能做没做时，两步走：
1. search_files 全 `docs/`（**含 archive/、视觉提案 HTML、specs、changelog、待修复清单**）定位决策出处
2. grep 代码验证是否真实现

**提案里拍板过的功能可能从未落地**。实例（v0.36）：撤销 toast 在 `画师工作台视觉提案-v2.html` 拍板且有演示代码，QueueBoard.vue 零实现。汇报要诚实：「没做」+ 决策出处 + 本轮安排，不粉饰。

## 2. 派工前逐条复验过时清单

候选/待做清单每条派工前重新 search_files 验证。三种典型过时：
- 死代码可能已删（清单里的 TplCoverShowcase 早已不存在）
- 行号会漂移（L5 空字符串清单行号全部失效，需让角色自行扫描）
- 「死代码」可能即将转正（computeInstallmentStatuses 被 BUG-1 方案 b 吸收，不能删要吸收）

派工文件里用三列表呈现：**项 | 一号验证结论（带日期） | 动作**。执行者照表做，不盲删。

## 3. 跨角色配套项必须写进双方派工

A 角色任务依赖 B 角色删改某处（如后端删 API 六端点 + 前端删对应封装），**两个角色的派工文件都要写明该条目**。实例：三号派工写「前端封装由二号删」，二号派工却漏了，一号自查发现后补 patch（加 L0 条目）。写完全部派工后通读一遍交叉依赖。

## 4. 派工前批量建 worktree

```
git worktree add <path> -b <branch>   # 每个角色一条，一次建齐
```
复用旧目录名先查内容清理残留（artist-commission-02 曾是旧会话残留空壳，Remove-Item 后再 add 成功）。派工文件头部写明 worktree 路径 + 分支名 + 「开工第一步 git merge master 再读本文件」。

## 5. 用户跳过终验直接开下版

终验清单没走完但用户直接派新活 → 按开工处理。STATUS 记录终验状态（「未逐项终验，v0.X 问题 hotfix 插队」），不追着用户补终验，也不阻塞下版。
