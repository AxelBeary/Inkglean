# 用户视觉投诉分诊（"做得好丑/错位/空白"类反馈）

> 2026-08-05 v0.38 画师后台投诉实例沉淀。触发：用户看着部署实例说视觉不行、发截图、甚至提"外包重做"。

## 第一原则：症状先定性，再谈方向

用户口述「错位 / 空白 / 动画缺失 / 不该出现的东西」= **实现缺陷症状**，不是审美问题。审美问题的表现是"配色不舒服/气质不对/太素太花"。定性不同，处置完全不同：
- 实现缺陷 → 修代码，成本低，轮不到外包
- 方向不对 → 才谈设计调整；外包接手同样要先做缺陷定位且不懂 token 体系，成本更高

**用户拍板过的视觉方向被投诉时，默认假设是"落地走样"而非"方向错了"**——推翻重来是最贵选项，先拿证据。

## 无 vision 能力窗口的处置（本会话实录）

一号会话可能没有图像解析能力。**不装懂、不凭文字附和**。流程：

1. 把用户截图从桌面复制到工作区：`Copy-Item C:\Users\<user>\Desktop\QQ_*.png workspace/temp/visual-complaints/user-shot-N.png`（角色外部窗口可读图）
2. 派五号**只读视觉巡检批**（不需要新 worktree，主仓代码即可；与五号其他批按序排队，派工写明优先级）：
   - 先看用户截图定位症状与页面
   - 逐页浏览器巡检画师后台全部页面
   - 对照三份基准：视觉规范 md + 设计提案 HTML（浏览器打开对比）+ 该版本合入时的交付截图（docs/audit-screenshots/）
   - 每缺陷截图存档 + 页面/症状/差异/初步定位（到行号更好）
   - 分类：① 实现走样（违反规范，可修）② 基准缺失（规范没写，需补规范）③ 数据态问题（空数据观感，非缺陷）
   - 对照交付截图判定：交付时就有 = 当时审核漏了（如实写）；交付正常现在异常 = 后续批次改坏（定位哪批）
3. 巡检清单出来后：走样 → 按清单派执行角色修；结构性烂 → 这时才与用户谈方向调整

## 必查的部署侧干扰项

用户看的是容器部署实例时，"错位+空白+动画缺失"也可能是**构建产物问题**（字体没打进镜像、CSS chunk 加载失败、构建版本落后 master）。巡检时本地 dev 与容器各测一遍对比，区分代码问题 vs 部署问题。

## 外包决策的回应模板

不直接否决也不直接同意：说明症状定性（实现缺陷证据）+ 外包真实成本（不懂 token/模板架构，接入成本高于修复）+ 给出证据链节点（"等巡检清单出来，若证明结构性烂，你再提外包我不拦"）。
