# 用户侧接力派工模板（2026-08-05 起，取代子代理模板）

执行角色由用户在外部 Hermes 窗口开启。用户的动作是**每个窗口复制一行**——所以一号的交付物 = ①comms 派工文件（已 commit+push 到 master）②聊天里每角色一行触发语。两者缺一不可。

## 触发语（用户复制的那一行，每角色一行，不多一字）

```
你是{N}号（{角色名}），先读 docs/comms/STATUS.md 再读派工 docs/comms/01-to-0N-{主题}-{日期}.md 执行，worktree 在 ../{目录名}，只动自己分支，不推送不合并，交付写报告。
```

要素检查（缺一即不合格）：
- 「你是X号」——防身份混淆（曾有二号窗口冒充一号 4 小时）
- STATUS.md——全局状态自包含，角色新会话零记忆
- 派工文件路径——细节全在这里，角色自读
- worktree 路径——相对主仓的 `../` 路径即可
- 纪律尾巴——只动自己分支/不推送不合并/交付写报告

**禁止**：把派工内容内联贴进聊天（用户不会复制一坨）；只落盘文件不给触发语（用户看不见文件）。

## comms 派工文件结构（01-to-0N-{主题}-{日期}.md）

1. 头：日期/派工/执行角色/worktree/分支/基点 HEAD/验收依据文件
2. 〇、开工第一步（npm install → git merge master → 其他前置）
3. 任务清单：后端契约（端点+字段+错误码，一号已核实的原样写入）→ 改动点逐文件
4. 明确不做（防越界：哪些留下批、为什么）
5. 铁律（授权白名单外文件清单 + 测试基线数字 + 交付报告文件名）

## 派工序列（顺序不可颠倒）

1. 核实预算内完成验证（三类各一轮，见 references/dispatch-delivery-discipline.md）
2. write_file 写全部派工文件（并行一个 turn 写完）
3. `git add docs/comms/ && git commit && git push`——**未 push 的派工文件角色看不到**（v0.20 事故）
4. `git worktree add` 建好每个角色的 worktree
5. 更新 STATUS.md + commit + push
6. 聊天里给触发语（一行一个）

## 派工后追加条目（v0.35 教训）

patch 派工文件后必须：①commit+push ②在触发语或单独消息告知用户转达角色「先 git merge master 再读派工文件」——角色 worktree 里还是旧版文件。审核交付时对照最新版派工逐条验。
