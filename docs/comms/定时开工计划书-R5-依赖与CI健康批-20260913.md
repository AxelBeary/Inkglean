## 一、🔵 关键策略：为什么走「本地升级 + 关 PR」而非「合并 PR」

这是本批最重要的决策，施工会话必须先理解再动手：

1. **PR mergeable = UNKNOWN，且 base 是旧 master**：`gh pr view 7/8 --json mergeable` 均返回 `UNKNOWN`；两个 PR 的 base 是 9-11 的 master，**早于 9-12 AGPL 许可批**（那批改过 `server/package.json` 的 license 字段 + `package-lock.json` 自身包条目）。dependabot PR 的 lock 改动与当前 master 的 lock 分叉，`gh pr merge` 有**冲突/不可合并**风险。
2. **vitest PR #7 直接合必红**：PR #7 的 server job = FAIL（vitest 4.x 揪出 `publish-artwork.test.ts` TC-PA-07 漏 await）。**盲合会把红的 server 测试带进 master**——必须本地升级 + 修测试 + 验证绿，不能直接合。
3. **本地升级 git 状态更简单**：不合 PR、不 pull，remote master 保持 `d4984edf` 不变；本地在 `de923472`（已含 P1~P5）基础上升级 server 依赖，与 R1/R3 的工作区改动（web/e2e）不重叠。R4 收口提交、用户 push 时是 **fast-forward**（本地领先 remote），无 merge 冲突。升级 push 到 master 后，dependabot 重扫自动关闭 sharp/vitest 的 6 条警报。

**结论**：R5 = 本地 `npm install` 升级 sharp+vitest → 修 vitest 4.x 揪出的漏 await → 跑 server 门禁验证绿 → `gh pr close` 关掉两个 PR（附说明"已本地升级验证"）→ dismiss glib 警报 → 重跑 flaky CI。**全程不 `gh pr merge`、不 `git pull`。**

## 二、🟢 施工步骤（做什么 · 怎么做，按序）

### 步骤 1 · 重跑 flaky 的 docker CI（清红叉）
- **做什么**：CI run `34700257030`（master `d4984edf`）的 docker job 因 `npm ci` 撞 `ECONNRESET` 网络重置而红（已确诊 flaky，非代码问题），重跑清掉红叉。
- **怎么做**：`gh run rerun 34700257030 --failed`（只重跑失败的 docker job）→ 等 3~5 分钟 → `gh run view 34700257030` 核验 docker 转绿。
- **降级**：若重跑又因网络 flaky 红，再重跑一次；**连续两次仍红则停下记 ledger 报用户**（可能非纯网络问题，需人看）。

### 步骤 2 · 本地升级 sharp（消 2 条 high 警报 #24/#25）
- **做什么**：sharp `0.35.3 → 0.35.4`（patch 升级，PR #8 已验证全绿，低风险）。
- **怎么做**：`cd server && npm install sharp@0.35.4` → 核验 `server/package.json` 的 `sharp` 变为 `^0.35.4` + `package-lock.json` 的 sharp 条目更新。

### 步骤 3 · 本地升级 vitest（消 4 条 medium 警报 #19/#20/#22/#23）
- **做什么**：vitest `3.2.0 → 4.1.11`（**major 升级 v3→v4**，连带传递依赖 `@vitest/mocker` 一起到 4.1.11）。
- **怎么做**：`cd server && npm install -D vitest@4.1.11` → 核验 `package.json` 的 vitest 变 `^4.1.11` + lock 里 vitest 与 @vitest/mocker 均更新到 4.1.11。
- ⚠ **major 升级风险预告**：vitest 4 除"未 await 的异步断言现在会 fail"外，可能还有其他 breaking（配置项、mock API、environment 默认值）。步骤 4/5 会暴露，逐个按 vitest 4 迁移指南处理；**若 breaking 面过大当批解决不了，走第五节的降级路径**。

### 步骤 4 · 修 vitest 4.x 揪出的漏 await 断言（核心）
- **做什么**：vitest 4.x 收紧了异步断言——`expect(...).rejects/resolves.xxx(...)` **未 await 会直接 fail**（旧版静默放过 = 假绿）。逐个修被揪出的漏 await。
- **已知第一处**：`server/tests/publish-artwork.test.ts` 的 **TC-PA-07**（service 层二次防护，直接调用返回 `ORDER_NOT_OWNED` 403）——`expect(...).rejects.toMatchObject(...)` 漏了 `await`，加 `await` 即可。
- **怎么做**：`cd server && npm test` → vitest 4 会报出**所有**"Promise returned by `expect(actual).rejects/resolves...` was not awaited"的位置 → **逐个给漏 await 的断言补 `await`**（可能不止 TC-PA-07 一处，vitest 4 会把全仓的同类假绿一次揪清）→ 每修一批重跑，直到 server 测试不再报"not awaited"。
- 🔴 **诚实纪律**：补 await 是**修正真实的假绿测试**（那条断言此前没真正验证），不是绕过。**若某处补了 await 后断言真的 fail**（说明该防护逻辑本就有 bug、一直被假绿掩盖），**停下记 ledger 报用户**，不掩盖、不删断言、不改回旧 vitest 蒙混。

### 步骤 5 · 跑 server 全量门禁（验证升级不破坏）
- `cd server && npm run typecheck && npm run lint && npm test`，**完整贴出输出**（typecheck 无错、lint 0 错、测试 passed 数）。
- 基线：server 当前 **1801**（156 文件），修漏 await 只加 `await` 不增删用例，**理论上仍 1801**，但以实测为准（若 vitest 4 改变了用例计数方式，记实测数交 R4 同步 baseline）。

### 步骤 6 · 关闭两个 dependabot PR（附说明，用户已授权）
- **做什么**：本地已升级并验证，PR 无需再合并，关闭并留说明。
- **怎么做**（**关前复核 PR 号对应**：#8=sharp、#7=vitest）：
  - `gh pr close 8 --comment "sharp 0.35.4 已在本地升级并通过 server 全量门禁，随本轮提交入 master，无需单独合并此 PR。"`
  - `gh pr close 7 --comment "vitest/@vitest/mocker 已本地升级到 4.1.11，并修复 4.x 揪出的漏 await 假绿断言（publish-artwork.test.ts TC-PA-07 等），server 门禁全绿，随本轮提交入 master。"`

### 步骤 7 · dismiss glib 警报 #10（已备案不做 Linux）
- **做什么**：glib 是 Linux 原生依赖，本项目 9/3 已备案不做 Linux 原生支持，该漏洞路径不适用 → dismiss。
- **怎么做**：`gh api -X POST repos/{owner}/{repo}/dependabot/alerts/10/dismiss -f reason="not_used" -f comment="glib 为 Linux 原生依赖，本项目已备案不做 Linux 原生支持，漏洞路径不适用"`（`{owner}/{repo}` gh 自动替换为 AxelBeary/Inkglean）。

## 三、警报清除链路说明（施工会话须理解，别误判"没消"）

- **sharp/vitest 的 6 条警报**（#24/#25/#19/#20/#22/#23）：靠**升级 commit push 到 master 后 dependabot 重扫自动关闭**。R5 本地升级时警报仍 open，**要等 R4 提交待令 → 用户下令 push → dependabot 重扫**才关。R5 不手动 dismiss 这 6 条（升级=真修，走自动关，不用 dismiss 掩盖）。
- **glib 的 1 条警报**（#10）：R5 步骤 7 **直接 dismiss**（不依赖 push）。
- 故 R5 收工时：open 警报从 7 → 1（剩 sharp/vitest 6 条待 push 后自动关，glib 已 dismiss）；**push 后 → 0**。ledger 要写清这个链路，别把"还没 push 所以警报还在"误报成"升级失败"。

## 五、降级路径（遇阻不硬来，停下报用户）

- **vitest 4.x breaking 面过大**（除漏 await 外还有配置/API 破坏，当批改不干净）：**降级为"只修既存假绿测试、暂不升 vitest"**——保留 vitest 3.2.0，单独修 `publish-artwork.test.ts` TC-PA-07 的漏 await（这条假绿与升不升级无关，本就该修），vitest 的 4 条 medium 警报暂留（dev-only 不紧急），记 ledger 报用户"vitest 4 升级需单独一批深做"。sharp 升级（patch，低风险）照常做。
- **sharp 升级后 server 门禁红**（patch 升级理论上不该红）：停下记 ledger 报用户，不强行提交。
- **任一 remote 操作失败**（rerun/close/dismiss 报错，如权限不足、PR 号对不上、警报号变了）：停下记 ledger 报用户，不重试硬来。
- **补 await 后断言真 fail**（防护逻辑本就有 bug）：停下记 ledger 报用户（见步骤 4 诚实纪律）。
