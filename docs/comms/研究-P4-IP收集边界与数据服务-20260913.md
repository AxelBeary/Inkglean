# 研究 · P4 附带议题：IP 收集的边界与「给画师卖数据」的可行性

> **缘起**：2026-09-13 用户在批 P4 停等期间追加三问 —— ① 举报要不要也收 IP？② 留言要不要收 IP？③ 访问（浏览）要不要收 IP，未来能不能专门做数据服务卖给画师？
> **性质**：只研究、只出结论与建议，**未改任何代码、未建迁移、未动数据库**。
> **免责**：涉及法规的部分是**工程侧常识性提示，非法律意见**（本仓库 REQ-042 §九 自述口径：条款为「模板改+人工审校，非法律意见」）。

---

## 0. 三句话结论

| 问 | 结论 | 一句话理由 |
|---|---|---|
| ① 举报收 IP | **建议收**，并入本次 v75 一起做 | 举报是"指控性"内容，恶意举报要能追溯；取 IP 的 `request.ip` 现成就在手边（已用于限流），成本几乎为零 |
| ② 留言收 IP | **建议收，但只给管理端看，不给画师端看** | 留言是公开发言，出事要能查；但把 IP 摆在画师界面上等于递刀（人肉/私刑），画师不是执法者 |
| ③ 访问收 IP | **建议不收**，维持现有匿名凭证路线 | 8/7 你已亲自拍过「埋点不采集 PII、匿名凭证不得升级为追踪访客的标识」，而**卖数据这件事根本不需要 IP**，需要的是聚合结论 |

## 1. 项目已有的 IP 收集先例（三条，口径各不相同）

这不是"要不要开始收 IP"的新问题——**平台已经在收两处 IP**，且都已公示。新议题只需照既有口径延伸：

| # | 场景 | 列 / 迁移 | 取法 | 谁能看 | 隐私政策是否已披露 |
|---|---|---|---|---|---|
| E1 | 交付文件下载取证 | `deliverables.download_ip`（**v66**，815 拍板 #4 用户亲裁） | `request.ip`（`order-client.routes.ts:306`） | 纠纷处理时查库 | ✅ 已披露：「交付文件下载记录（下载时的 IP 与时间，用于一次性下载的纠纷取证）」（`zh-CN.ts:2275`） |
| E2 | 画师登录留痕 | `artists.last_login_ip`（**v72**，登录留痕批） | `request.ip`（`auth.routes.ts:216/269/378`、`invite.routes.ts:94`） | **仅管理后台**（`publicArtistDTO` 默认剔除，两处管理端点显式重附） | ⚠ 清单里**未见对应条目**（现有清单只写了"QQ号/联系方式/订单/作品图/浏览行为/Passkey 公钥/下载记录/Sentry"） |
| E3 | 全站限流 | 无列（内存计数 key） | `request.ip`（upload/order/anon-token/reports 等十几处） | 不落库，用完即丢 | 不需要（不存储） |

**可复用的既定范式**（照抄即可，不用重新发明）：
- **取证类 IP** → 学 E1：加一列可空 TEXT + 隐私政策清单补一条披露 + 注明用途。
- **仅管理端可见** → 学 E2：DTO 默认剔除，只在管理端点显式附带；前端不渲染就不算"对外提供"。
- **取法** → 三条全用 `request.ip`（CF/Caddy 已在反代层换算成真实用户 IP，`Caddyfile:21-23` + `tests/cf-real-ip.test.ts` 锁死）。

**顺带查出的既有缺口（只登记）**：E2 的登录 IP **在隐私政策里没有披露**，而项目有专门盯着"告知与实际能力一致"的诚实性测试（`web/src/locales/__tests__/honestyCopy.p1-0912.test.ts`、`complianceCopy.req028-transition.test.ts`，9/12 用户拍板批次立下的）。→ 建议本批一并补进清单，一次改文书搞定，别攒着。

## 2. ① 举报收 IP：建议做

**为什么值得**
- 举报是**匿名可提交**（`POST /api/public/reports`，无需登录），已有防滥用只有一道"同 IP 每分钟 2 条"的限流，用完即丢，**事后零证据**。
- 现实风险：竞对互相刷举报、同一人批量举报施压、恶意举报消耗管理员精力。有 IP 才谈得上识别与自证。
- 与批 P4-1 是同一件事：管理员处理动作要留 IP（v75 主线），**举报来源 IP 是它的另一半**（一头是"谁处理的"，一头是"谁举报的"）。

**改动面（小）**
- `reports` 表 +`report_ip TEXT`（**并入同一个 v75**，省一次迁移）；`schema.ts` 同步。
- 写入点唯一：`createReport()`（`compliance.service.ts:41-49`），调用方 `compliance.routes.ts:48` 已握着 `request.ip`（同一个值刚用于限流）。
- 读取侧（实测好处理）：`reports` 只在 `compliance.service.ts:50/57/60/65/74` 被 `SELECT *` 读，而这些函数**只服务 `/api/admin/reports*` 管端**（全仓无其它读取路径）→ 举报人 IP **天然只在管理端可见**，无需额外剔除。只需加一条测试锁住「将来新增举报读取口不得把 `report_ip` 带到非管端」。
- 测试：迁移幂等 + 写入断言 + 「非管理端口不得外泄 `report_ip`」1 例。

**留存期建议**：与举报行同生命周期（不单独 TTL）。理由：举报是纠纷证据，`app.ts:92-93` 既有注释已定调「`guestbook_messages` 等为业务与审计数据，永久保留」；举报同理。

## 3. ② 留言收 IP：建议做，但**只到管理端为止**

**为什么值得**
- 留言是**挂在画师主页上公开展示**的内容（有 pending/approved/rejected 审核态 + 画师回复 + 管理员软删 `deleted_by_admin`），审核链路齐全，**唯独没有来源 IP**——出现辱骂/侵权/威胁留言时，管理员除了删掉什么也做不了。
- 页脚合规链接（隐私政策 + 条款 + 举报）在**全部 4 个主页模板 + Landing 都渲染**（`ComplianceFooterLinks`），公示路径现成，不需新做同意流程。

**为什么不给画师看（这条是本报告的主要判断）**
- 画师不是执法者，也没有处置权。把「这条留言来自 113.xx.xx.xx」摆在画师后台，可预见的后果是画师自行去查 IP 归属/在社交平台上挂人，**把平台拖进二次纠纷**，责任反而回到平台头上。
- 现行同类口径已有先例可循：`last_login_ip` 就是"仅管理后台可见、DTO 默认剔除"（E2）。
- 画师的正当诉求（骚扰/威胁留言）应由**管理员**受理 → 管理端举报/留言处理界面可见 IP 即可满足。

**改动面（小）**
- `guestbook_messages` +`ip TEXT`（**并入 v75**）；`schema.ts` 同步。
- 写入点：留言提交口（`guestbook.routes.ts:39` 已取 `request.ip` 做限流）→ 透传进 service 的 INSERT。
- **读取侧要逐个把关（这才是真风险，实测已确认）**：`guestbook.service.ts` 三处全用 `SELECT *` —— `getMessageById`（:23）、公开列数据查（:48）、`getArtistMessages`（:68）。**一加列，画师后台与公开端会顺带把 `ip` 返出去**。施工必须改为显式列清单（或出口剔除），并加“画师端/公开端响应体不含 `ip`”的断言。
- 测试：公开端与画师端断言响应体**不含** `ip`；管理端可见。

## 4. ③ 访问收 IP：建议**不做**（三条硬理由）

1. **会顶到你已拍板的隐私边界。** REQ-033（2026-08-07，用户亲拍）白纸黑字：
   - §六「**不做**：不采集 PII」；
   - §2.2 匿名凭证「**隐私边界（重要）**：凭证是匿名随机串，不关联 QQ 号/订单号/需求文本；**不得升级为"查询某访客下了哪些订单"的追踪标识**」。
   - 落地事实与之一致：`events` / `anon_tokens` 两张表（v44）**都没有 IP 列**，访客识别全靠 anon token；`events` 还有 180 天 TTL（`app.ts:94`，M-1 审计批接线）。
   - 一旦给埋点落 IP，"匿名统计"就变成**可关联的个人信息追踪**，同一条数据链上 anon_id ↔ IP ↔ 下单事件全部可串——正是当初明令禁止的那件事。
2. **对外文书要跟着改，而且有测试盯着。** 隐私政策现在的公示口径是「浏览行为（埋点：**只记录访问了哪些页面、点了哪个功能**…；日志保留 180 天）」。加了 IP 就是公示与实际不符，须改清单 + 改更新日期（`honestyCopy.p1-0912.test.ts` 会断言日期与正文对齐）。
3. **卖数据这件事不需要 IP。** 见 §5——买家要的是结论，不是原始地址；把 IP 卖/交给画师，在 PIPL 下属于**向第三方提供个人信息**，需要单独同意，法律成本远高于其商业价值。

**如果确实想要"访客来自哪里"**：唯一相对稳妥的中间路线是**不落原始 IP**，在入库那一刻一次性派生粗粒度地域（省级/国家级）后立刻丢弃原值，派生列与 anon_id/订单事件不建关联。但——省级归属仍可能被认定为个人信息，且这条路线要新写解析（本地 GeoIP 库，须走第三方依赖登记纪律 `THIRD-PARTY-NOTICES.md`）。**建议现在不做**，等"数据服务"真立项时再单独评估。

## 5. 「专门给画师卖数据服务」可不可行：可行，但不靠 IP

**现有底子已经够用**（都是已实施的工程，不用新建采集）：

| 数据源 | 已有内容 | 能算出什么（画师愿意付钱的） |
|---|---|---|
| `events` 埋点（v44/v45） | 页面进入、功能点击、下单漏斗四事件、换色、`artist_id`/`anon_id` | 主页访问量、各板块点击热区、**下单漏斗哪一步流失最多**（REQ-033 §3.3 指标定义已写好） |
| `orders` + `order_price_entries` | 金额、档位、增项、交付周期 | 客单价分布、最赚钱的档位/增项、淡旺季 |
| `artworks.like_count` + 点赞事件 | 作品受欢迎度 | 哪类作品引流有效 |
| `client_profiles`（v46） | 画师给客户打的标记、老客召回 | 回头客比例、客户结构 |
| `guestbook_messages` | 留言量与回复率 | 互动度 |

**三条必须提醒的门槛（不是技术问题）**
1. **小样本会骗人。** 个人站访客量级下，"漏斗流失 40%"可能只是 5 个人里走了 2 个。任何对外报表**必须带样本量**，否则卖的是噪声，砸的是口碑。
2. **画师端统计已有开关与三态**（`statsMode` off/hidden/on，`tracking.routes.ts:184-190`；且 9/12 拍板把"个人可自行关闭埋点"改成"管理员全站开关"并已把文书改成实话）。卖数据服务要与之共存，别做出第二套互相矛盾的口径。
3. **商业与条款**：现服务条款只有「画师内容责任 + 平台处理权」，**没有任何数据服务/收费相关章节**。要卖就得先补条款（并明确"提供的是聚合统计，不含任何访客个人信息"）。

→ **建议路径**：本批**只补齐取证类 IP（举报/留言/管理动作）**；「数据服务」**另立 REQ** 做产品规划（卖什么、定价、口径、条款），技术上走"聚合统计导出"而非"原始数据交付"。
