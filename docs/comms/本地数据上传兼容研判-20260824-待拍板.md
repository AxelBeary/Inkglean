# 本地数据上传兼容研判（去重 / 上传 / 防冲突）

> **状态：待拍板（仅研判，不构成工程决策依据）**。产出日期 2026-08-24。
> **议题来源**：用户（项目主人）未来议题——桌面端本地模式的记账数据，未来能否"上传兼容"到平台？
> **定位**：**重评材料**。本议题若落地，等于修改 810 用户拍板的「双模式完全分离」「本地记账与平台订单不做任何关联/合并」铁律。本文把"改铁律的代价"与"不改铁律的替代方案"都摆出来，不预设结论。
> **输入**：`docs/requirements/REQ-014-桌面端伴侣应用.md`（§模式设计 / §F2 / §数据迁移与备份 / §数据可见性规则 / §安全口径三条 / §二轮功能研判拍板）+ `server/src` 订单域只读核实（见第五章）+ `docs/comms/桌面端第三方接入研判清单-20260824-待拍板.md`（交互口径参照）。
> **任务边界**：纯研判，零代码、零既有事实源改动。所有不确定项均标注「待复核/待用户确认」。

## 一、先说人话（结论速览）

1. **能不能做？** 技术上能，而且比想象中省事——平台现有的"手动录单"接口自带**防重复提交机制（幂等键）**，"同一张单传两次不会变成两张"这件事平台已经防住了，不用新写。
2. **真正的坎不是技术，是三笔"翻译损失"**：本地记账没有客户 QQ 号（平台订单**强制要 QQ**）、本地的价格是手填的一个数（平台价格来自计价档位，且**免费/0 元单在平台上没有入口**）、本地的状态很粗（平台是严格的流程状态机，"已交付"得一步步流转过去）。所以上传永远做不到"原样搬"，每条单都要画师补料或接受降级。
3. **最大风险**：一旦做"上传"，810 铁律（本地与平台零关联零合并）就事实上被触碰；且历史单批量涌入会**污染平台的名额占用、收入统计、老客判定**。这不是写代码的风险，是产品口径的风险——**必须用户亲裁**。
4. **建议方案一句话**：**默认不动铁律；若将来要做，只做"单向、一次性、逐条辅助搬运"**——桌面端帮画师把本地单在平台**逐条新建**（复用现有手动录单 API，服务器零改动），本地原件原封不动，不合并不回写不同步。它不是"数据合并"，是"帮你省打字"。
5. **完全不做也有退路**：本地记账本来就能导出 Excel（F2 既有能力），画师对着表格在网页端手动录单即可——历史单少（<20 条）的场景这样最干净。

## 二、研判尺子（判断依据全部来自已拍板口径）

1. **双模式完全分离**（810 拍板）：本地记账与平台订单**不做任何关联/合并**；在线/离线完全独立；登录后平台为准（F7 档案对比整体砍掉的先例）。
2. **数据可见性规则**：一条规则管所有——**来源决定可见性**。本地创建永远在；平台来源切出账号即隐藏。
3. **复用既有 REST API，无需桌面端专用端点**（2026-08-02 二号研判已拍板，REQ-014 第二轮结论 6）。
4. **安全口径三条**：记账式会话/凭证进系统保险箱；桌面端不新增服务器攻击面；更新防投毒。任何方案不得新增专用特权端点。
5. **交互基准**：网页端/桌面端录单均为「解析→预览→回填」三步（F10 已拍板）——**用户确认后才动数据，永不静默合并/静默上传**。
6. **导出边界**：仅本地来源数据可导出；平台数据不进导出。
7. **免费路线偏好**：优先复用既有能力，新增服务器能力需明确理由。

## 三、场景盘点（研判点①）

### 场景 A：本地模式画师转登录模式，一次性搬运历史账（主场景）

- 画师先用了一段时间本地模式（没登录），积累了若干条本地记账；后来登录了平台，希望这些历史单"也进平台"，好让收入统计、排期历史、老客档案完整。
- 特点：**一次性、存量、大多已是完结态**（已交付/已收款）。这是本议题唯一真实的需求来源。

### 场景 B：登录后，本地单与平台单并存的日常

- 画师已登录，联网时新单直接走 F10 录单进平台；**断网时**脱网兜底记在本地（断网保命链条款）。联网恢复后，这批"离线单"要不要自动上平台？
- 研判结论：**这个场景就是双向同步的入口，复杂度爆炸**——它要求"中间态识别 + 增量判定 + 冲突合并"，正面撞 810 铁律和"登录后平台为准"先例。第三方接入研判清单里 Notion/Trello 类双向同步被列为不接，理由同款（冲突处理复杂度过高）。
- **倾向**：场景 B 不做自动上传。离线单要么留在本地（可见性规则天然允许共存），要么画师愿意的话对个别单手动走一次"搬运"（与场景 A 同一工具）。**日常不产生需要系统解决的上传需求。**

## 四、方向拍板素材：单向一次性 vs 双向同步（研判点②）

| 维度 | 单向（本地→平台，一次性搬运） | 双向同步 |
|------|------------------------------|----------|
| 与 810 铁律的关系 | 轻触（仍需改"零关联"字面，见第八章） | 正面击穿（合并+中间态+双向写） |
| 与"登录后平台为准"先例 | 兼容（上传即"画师手动在平台新建"，平台天然为准） | 冲突（本地侧要能接收平台变更） |
| 冲突处理复杂度 | 低：只有"建不建、跳过谁"一个问题 | 高：字段级合并、删除传播、离线队列、两端各自修改 |
| 对数据可见性规则 | 不破坏（两边各记各的，来源各自清晰） | 破坏（"这条单到底算哪边来源"无法回答） |
| 对安全口径 | 无新增（复用现有录单 API） | 需要持久同步引擎+状态存储，面扩大 |
| 真实需求覆盖 | 覆盖场景 A 全部、场景 B 的自愿手动部分 | 覆盖全部，但场景 B 需求本身存疑 |

**明确倾向：只做单向，且是"一次性搬运辅助"，不是持续同步通道。** 理由：
1. 真实需求收敛在"转登录模式那一刻"，一次性的事不值得建同步引擎。
2. 单向语义可以完全解释为"画师在云端模式下逐条手动录单，只是桌面端帮他预填了字段"——这是**现有已拍板行为的延伸**，不是新模式。
3. 双向同步在本项目架构下没有任何不流血的落点（双模式分离、离线隐藏、平台为准、导出边界四条口径全部受创）。

## 五、服务器侧现状核实（只读，2026-08-24；本章为技术底稿，可后读）

> 核实范围：`server/src/features/order/` 全部路由与 `server/src/db/schema.ts`。以下每条都直接影响方案可行性。

1. **现有录单端点**：`POST /api/artist/orders/manual`（画师手动录单，F10 桌面端录单未来也走它）。
   - **必填 `clientQq`**：纯数字 5~15 位，JSON Schema 强校验。**本地记账（F2）字段里没有 QQ**——这是搬运的第一道硬坎。
   - 可选：clientName、description、priority、references（≤5 张，须为服务器已存在文件）、discountCode、styleSizeId、styleAddons。
   - **创建时不接受 deadline / start_date / 手填价格**——截稿日与开稿日要建单后分别 `PUT /:id/deadline`、`PUT /:id/start-date`；价格要建单后 `PUT /:id/price`。
   - 建单副作用多：订单号服务器生成（画师身份码+序号，**客户端不能自带单号**）、生成客户追踪令牌、占排队位次、挂工作流首节点、生成收款分期计划、活动日志留痕。
2. **幂等现状（防重复的关键事实）**：
   - `idempotency-key` 请求头 + `idempotency_keys` 表（scope+key 复合主键）。手动录单 scope = `manual-order:{画师id}`：**同 key 重放原样返回首单结果，不重复建单**；失败（校验错/下单错）不缓存、允许重试；幂等行 24 小时 GC。
   - key 格式 `/^[A-Za-z0-9-]+$/` 且 ≤64 字符——**本地给每条记账生成一个 UUID 当 key，正好天然合规**。
   - 收款同样有幂等键（scope = `payment:{orderId}`）。
   - 但注意：schema 注释写明「UNIQUE order_no 只兜单号不兜业务重复」——**平台没有任何"两张内容相同的单视为同一张"的业务去重能力**。幂等只防"同一次提交重放"，不防"内容雷同的两条单"。
3. **状态机**（`order-status.ts` STATUS_TRANSITIONS）：新单固定 `pending`；到 `delivered` 最少要 `pending→wip→delivered` 两步流转；`delivered/cancelled` 是终点不可再动；取消已收款订单需显式确认。**本地历史单的"已交付/已收款"状态只能靠多次调状态接口流转出来，不能一步落位。**
4. **价格与收款**：
   - 无档位自定义单（styleSizeId=null）建出来**无价格**；改价走 `PUT /:id/price`，**`finalPriceCents` 最小值为 1 分**——**0 元/免费单改价会被拒**（待复核：唯一零元路径是建单时计价结果为 0，自定义单 + 折扣码组合已被显式拒绝）。
   - 收款 `POST /:id/payments` 支持正负金额，允许超付（压成尾款负数），每次收款后跑**守恒自检**（总价 ≡ 节点价 + 额外应收退）。
   - 收款流水 `created_at` = 当前时间，**没有"补录历史收款时间"的能力**——历史已收款单搬上来，收入会记在搬运当天（见第七章风险）。
5. **名额分区（SPEC-004）**：建单时统计画师未完结订单数，正式区满进缓冲区，缓冲区满直接 `BATCH_FULL` 拒绝。**批量搬历史"进行中"单可能瞬间占满名额、顶掉正在进行的单**——搬运预览必须把这件事摊开给画师看。
6. **来源字段**：`orders.source` CHECK 只允许 `'self' | 'manual'`。**复用现有手动录单 = 天然 `source='manual'`，语义完全正确（就是画师手动录的单），不需要新值、不需要迁移。** 若未来想加 `desktop-import` 之类第三值，则要动 CHECK 约束（迁移、重建表级改动）——本研判不建议。

## 六、去重策略（研判点③）

**前提事实（第五章）**：本地单没有平台认可的身份标识（本地自增 id 对平台无意义、无订单号、无 QQ）；平台也没有业务级去重。因此——

**结论：自动精确去重不存在可行方案，唯一稳的路是"模糊匹配提示 + 人工裁决"，且永不自动跳过。**

### 匹配字段与阈值（初始建议，待复核）

| 字段 | 匹配方式 | 权重 |
|------|----------|------|
| 客户名 | 归一化（去空格/全半角/大小写）后模糊匹配 | 主锚点 |
| 价格 | 精确相等（本地元 → 平台分） | 强信号 |
| 截稿日 | ±3 天窗口（待复核窗口大小） | 辅助 |
| 描述/委托类型 | 关键词模糊 | 弱辅助 |

- 建议裁决规则：**客户名+价格双命中 = 标"疑似重复"**，进人工裁决界面逐条过；仅客户名命中 = 弱提示不拦截。
- **QQ 缺口直接拉低匹配质量**：平台侧订单可按客户 QQ 精确聚类，本地单给不出 QQ，匹配只能靠名字——重名客户、名字写法的差异都会产生误报/漏报。**宁可多报疑似、不可自动跳过。**

### 人工裁决界面（向 F10 三步口径看齐）

```
搬运预览（解析）
 ├─ 待上传本地单列表（可勾选/全不选）
 ├─ 每条旁挂"疑似与平台单重复"提示卡（左：本地单 / 右：平台单）
 └─ 逐条裁决：[新建] [跳过] [改改再建]
确认上传（预览 → 回填）
 └─ 进度清单：成功 / 跳过 / 失败（含原因，可重试）
```

- **永不静默**：默认不替画师做"跳过"决定；疑似重复的默认动作是**展开对比**，不是跳过。

### 一个减压判断

场景 A（转登录模式搬运）发生时，平台侧往往还很干净（画师刚转登录，平台上单很少），**真实撞车概率低**。因此去重不必做成重型系统：第一版可以只做"按客户名列出平台已有单供画师肉眼对照"+ 上述轻量提示，够用。（待用户确认：是否接受第一版轻量去重）

## 七、防冲突（研判点④）

1. **谁为准**：**平台为准**（"登录后平台为准"先例的直接延伸）。上传是本地→平台的单向写，本地单永远不接收平台侧的任何变更。
2. **幂等（防重复建单）**：本地为每条记账生成稳定 UUID 作 `Idempotency-Key`（格式天然合规，第五章），重试/断点续传重发同 key = 平台原样回放首单结果。**平台侧现成机制，零开发。**
3. **上传失败回滚——建议不做自动回滚**：
   - 理由：平台建单副作用链长（令牌/位次/工作流/分期/日志），"撤销一张已建订单"本身要走取消状态机，已收款的取消还需显式确认——自动回滚比失败本身更危险。
   - 替代：**逐条独立 + 失败不停**（每条单独立事务，一条失败不影响后续）+ 结果清单（成功/跳过/失败+原因）+ 失败可重试（幂等键对失败不缓存，修复后原 key 重试天然安全）+ 真建错了由画师在平台走既有取消流程（现有功能）。
4. **部分成功处理**：本地 SQLite 记录「本地单 UUID ↔ 平台订单号」搬运台账，中断后从断点续传；已成功的凭幂等键保证重发不炸。
5. **名额冲突（必须预览）**：搬运前显示"本次选中 M 条进行中单，平台当前正式区余位 X、缓冲区余位 Y"，满员风险当面讲清再让画师选（待用户确认：是否允许把历史进行中单标为"取消"再导入以避名额，还是宁可拒收）。
6. **收入统计冲突（两难，待用户确认）**：历史"已收款"单导入必须补录收款流水，而流水时间=搬运当天 → **历史收入会集中在搬运月爆出来，月度收入统计失真**。两个都不完美的选项：
   - A：照录（统计失真，但订单收款状态真实）；
   - B：只建单不录收款（统计干净，但订单显示"未收款"，画师看着难受，且守恒/付清语义不全）。

## 八、上传后数据身份：可见性规则如何不被破坏（研判点⑥）

**核心机制：两边各自记各自的，来源各归各。**

| 数据 | 来源 | 免登录 | 登录后 | 切出账号后 |
|------|------|:---:|:---:|:---:|
| 本地原件（上传前后都不动） | 本地创建 | ✅ | ✅ | ✅ 永远在 |
| 平台新建单（上传产物） | 平台 | ❌ | ✅ | 界面隐藏（规则原样） |

- 平台侧新单 `source='manual'`——语义正确、零迁移（第五章第 6 条）。
- 可见性规则**原封不动**：上传只是"在平台世界多了一张新单"，没有产生任何"混合来源"的数据。
- **唯一的敏感点：本地原件上要不要记一笔"已上传，对应平台单 CODE-xxx"？** 这是本议题对铁律的触碰程度之争：
  - **档位①（零关联，铁律原文不动）**：上传完本地单一个字节不改，防重复全靠搬运台账界面和画师记忆。铁律无损，体验略糙。
  - **档位②（弱关联）**：本地 SQLite 给该条单记一个"平台对应单号"标记，界面显示"已上传"、再点上传时拦一句"这条已经传过了"。**关联信息只存本地、单向、平台永远不知道本地单的存在**——但铁律字面「不做任何关联」需要改写为「不做任何合并；允许本地侧单向上传标记」。
- **待用户确认**：选①还是②。（研判倾向②，因为"防重复上传"是画师真实会踩的坑，代价只是铁律改一句话；但若用户对铁律字面有洁癖，选①功能上也成立。）

## 九、接口需求：复用现有 API 逐条建单 vs 新增批量导入端点（研判点⑤）

### 方案 A：复用现有手动录单 API，逐条建单（推荐）

每张单的调用链：

```
POST /api/artist/orders/manual      建单（幂等键=本地单UUID）
PUT  /api/artist/orders/:id/deadline 补截稿日
PUT  /api/artist/orders/:id/price    补手填价格（0 元单除外，见缺口③）
PUT  /api/artist/orders/:id/status   状态流转 ×1~2 步（按本地状态映射）
POST /api/artist/orders/:id/payments 补收款流水（仅已收款单，可选）
```

- 成本：每张单 3~5 个请求；几百条历史 ≈ 千余次请求，串行执行、一次性任务，分钟级可接受。
- **服务器零改动、零新增端点、零新增攻击面**——同时守住三条已拍板口径（复用既有 REST API / 安全口径"不新增攻击面" / 免费路线）。

**字段缺口清单（"翻译损失"，必须让画师知情）**：

| # | 本地（F2） | 平台（现有 API） | 处理 |
|---|-----------|------------------|------|
| ① | 只有客户名 | `clientQq` 必填、纯数字 5~15 | 逐条补 QQ；补不出的单**不上传**（待用户确认：是否允许占位 QQ？研判倾向不允许——占位号会污染客户档案与 F9 老客快查卡的判定） |
| ② | 价格手填 | 计价引擎/改价接口最小 1 分 | 走"自定义单+改价"；**0 元/免费单无入口**（待复核：是否存在零元通路；若无，搬运时对 0 元单只能跳过或写备注） |
| ③ | 状态四态（草稿/进行中/已交付/已收款） | 七态状态机 | 映射表（待复核细节）：草稿→不流转（留 pending）；进行中→wip；已交付/已收款→wip→delivered；"已收款"另补收款流水 |
| ④ | 截稿日是字段 | 建单接口不收 | 建单后单独 PUT（API 已有） |
| ⑤ | 委托类型=自由文本 | style_sizes 档位档案 | 不强映射，并入描述文本（待用户确认：搬运时要不要顺手做一次性"类型→档位"映射配置） |

### 方案 B：新增批量导入端点

- 需要：服务器新端点 + 批量/部分成功语义设计 + 大概率放松 `clientQq` 必填（语义变更，影响客户体系）+ 可能新增 source 值（迁移）。
- 与三条已拍板口径**全部相抵**（2026-08-02「无需桌面端专用端点」/ 安全口径「不新增攻击面」/ 免费路线），且批量事务语义（全成功还是部分成功）本身是新的设计难题。
- **结论：不推荐。** 唯一优点是请求数少；但方案 A 的千次请求对一次性任务完全可接受。
- **重评条件**：方案 A 实测不可接受时（如几百条单失败率过高、画师等待体验差），再评估"薄批量封装"——即便如此也必须保持逐条幂等与全量校验，不放松任何字段要求。

## 十、不改铁律的替代方案（研判点⑦）

| 方案 | 做法 | 体验 | 成本 | 铁律影响 |
|------|------|------|------|----------|
| **零（维持铁律，本研判默认）** | 不做上传。画师用 F2 既有的 **导出 Excel**，对着表格在网页端/桌面云端模式手动录单（F10 粘贴解析、首期 CSV 导入均可搭把手） | 全靠人力，历史单多时累 | 零开发 | 铁律完整 |
| **弱（本研判若动则推荐）** | 单向一次性搬运辅助：桌面端逐条帮建平台单、本地原件保留、不合并不回写（或仅档位②的单向标记） | 预填+防重+断点续传，画师只做确认和补 QQ | 桌面端搬运 UI + 字段翻译层；**服务器零改动** | 档位①=字面不动；档位②=改一句话 |
| **强（真合并，仅列作对照）** | 本地单与平台单同列表、自动去重合并、双向同步 | 看似最爽 | 同步引擎+字段级合并+删除传播+两端改写；服务器大动 | 击穿（可见性规则、来源判定、F7 砍掉先例、导出边界全受创） |

**对比要点**：方案弱与方案强的体验差距，集中在"画师要不要点确认"——方案弱每张单多点一下，换来的是**不产生任何跨模式数据、不出任何合并事故**。对一个一次性任务，这个交换极其划算。方案零与方案弱的分界线则是"历史单数量"：<20 条手动干完更快；上百条才值得工具。

## 十一、建议方案 + 重评条件（研判点⑧）

### 建议（不预设结论，供拍板）

1. **当前默认：不做。** 桌面端尚未开工 F2，"转登录模式搬历史"的需求在时间线上还很远；铁律是 810 用户亲裁，动它必须有真实需求拉动。
2. **若将来拍板要做**：采用**方案弱（单向一次性搬运辅助）+ 档位②弱关联标记（或用户改裁档位①）**，复用现有手动录单 API（方案 A 调用链），交互严格走「预览→逐条裁决→确认上传」三步，永不静默。**期次建议桌面端主体功能施工批之后**（二期或更后），开工前先观察真实需求量（待用户确认）。
3. **永不做**：双向同步、自动合并、批量静默导入、放松 `clientQq` 校验、新增平台侧"导入来源"标记。

### 重评条件（满足其一才重新摆上桌）

1. 出现真实画师反馈"历史单搬运是刚需"（且量级 >20 条/人，手动方案不划算）；
2. 平台获得"收款流水补录历史时间"能力（第七章收入失真问题自然消解）；
3. 方案 A 逐条调用在实测中被证明不可接受（届时评估薄批量封装，而非放松口径）。
